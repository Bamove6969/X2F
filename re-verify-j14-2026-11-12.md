## S1: a hold ending under a compromised-account lock dropped the partner's recorded buyer-cancel

**Fixed at the cause** (`apps/api/src/trades/held.ts`, `syncHeldTrades`, released-row branch):
- A `409 trade-held` on the `resume` or on the recorded `buyer-cancel` now sets `lockHeld`.
- When the resume was refused that way, the cancel is not tried.
- A lock-held row is not deleted (`if (lockHeld) continue`). Before, the row was deleted unconditionally, and its `cancel_requested_at` with it.
- The released row is picked up again on every pass (`released_at is not null` in the select). Once staff unlock, the next pass resumes the trade and carries the cancel out, then deletes the row. This is the same "wait, then decide" pattern the file already uses during maintenance.

**Why keying on `trade-held` is right.** `trade-held` is raised in only two places: the compromised-lock check in `applyEvent` (`store.ts:381`) and the dispute route. So a refusal for any other reason (a closed trade, a dispute opened meanwhile) still deletes the row as before. Only the lock makes it wait.

**Edge cases checked, by reading the code:**
- **The timer loop resumes first after the unlock.** It only treats *open* rows (`released_at is null`) as held (`timers.ts:55`), so it may resume the paused trade before the sync runs. The sync then sees `paused = false`, skips the resume, carries out the cancel and deletes the row. The cancel is still applied once, and there is no double resume.
- **A new hold on the same account while the row is kept.** `holdTrades` uses `on conflict (code, account_id) do update set released_at = null`, which reopens the same row with its `cancel_requested_at`. The trade is still paused, and the cancel then waits for that hold's end. Correct.
- **A trade that closes while still locked.** `applyEvent` checks the lock before the machine rule, so the kept row's `buyer-cancel` keeps getting `trade-held` and the row is retried every minute until the unlock. At that point the machine refuses the cancel on the closed trade and the row is deleted. This is harmless: one cheap query a minute per such row.
- **No coin path changes.** The lock refuses every trader event and the system `resume`, as before.

**Pinned by a test that is red on the old code.** `holdV3.test.ts` has a new test, "J-14 review S1: a hold ending while a compromised-account lock holds the trade keeps the partner's recorded cancel until the unlock". It:
- puts a secured trade under a recovery hold;
- records the partner's `buyer-cancel`;
- locks the held seller;
- ends the hold by moderator, then runs the sync. The trade stays paused and `secured`, and the cancel is still recorded;
- unlocks and syncs again. The trade is `settling` / `buyer-cancel` and unpaused, and the row is gone;
- syncs a third time. `trade.buyer-cancel` was logged exactly once.

At 22935bd8 (the test without the fix) it fails at `holdV3.test.ts:942`: `expected [] to deeply equal [ true ]`, meaning the recorded cancel was deleted. That is the bug, at the right assertion (1 failed, 45 passed). It passes at 08588fba.

One small gap: the test unlocks by SQL (`update account_locks set unlocked_at`) rather than through the staff unlock route. The route only sets `unlocked_at` (and clears `disabled_at`), and the sync reads the lock state, so this doesn't weaken it.

## S2: migration 451 left a writable plaintext `body` column

**Fixed at the cause, by option (a), the recommended one.** Migration 451 is folded into 450:
- `ticket_messages` is created with `body_sealed bytea not null` and `ticket_messages_sealed_size` (32..16031 bytes, first byte 0x01). It has **no `body` column**, so no code path can store ticket text in clear.

- `jabber/changePaths.ts` only had a comment updated.
- 450 and 451 have never been on main, so folding needs no data step; only dev databases that ran the branch need recreating. The commit says so.

**Pinned by tests that are red on the old code.** In `ticketSealing.test.ts`:
- "the table has no plaintext column; a row without sealed text, or not in the sealed format, is refused": `information_schema` shows exactly one `body%` column, `body_sealed`, NOT NULL. An insert without it gets 23502, and a blob with format byte 2 hits `ticket_messages_sealed_size`.

`schema.test.ts` drops 451 from its three migration lists. `tickets.test.ts`'s leak scan now dumps `to_jsonb(m)`, every column of the message row, instead of `m.body`, so it is broader than before.
