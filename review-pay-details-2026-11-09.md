## Verdict

**APPROVED WITH MINOR.** No Critical and no Important finding against the security promises the branch makes. The payment details never reach the API in the clear (every body is a sealed envelope; the boxes cross only the page-to-worker postMessage), a package is signed by the sender's chat identity and the moderation identity cannot forge one, the reader refuses malformed and lying packages without moving the guard, the held-package path cannot be used to desync or replay, `tradeSecuredAt` is party-only and comes only from `trades.secured_at`, the buyer's "Send exactly" card fills only from seller packages of the chat the API links to this trade, nothing of a package is persisted on the device, and the rendered card is React text with the hidden-character classes refused. The Minor findings are a cost-of-service issue that this branch widens (M1), a defence-in-depth gap on the sending side (M2), a wasted-work loop in an edge case (M3), hygiene (M4, M5) and the table's deviations from the research pack (M7), plus three owner questions.

## Findings

No Critical. No Important.

### Minor

**M1. A malformed `chat.msg` (now also a mod-signed or lying package) stalls the reader's cursor for good, and every later sync re-fetches everything after it.** Pre-existing behaviour, widened by this branch.
- `apps/web/src/chat/engine.ts:361-368`: a `bad-message` sets `advance = false`, so `held = true` and the cursor never passes that envelope ("tried again on a later sync"). `:300`: the next sync starts at `rec.cursor` again. Everything after the stalled envelope already has a receipt, so it is cheap to skip in code, but it is fetched again from the API on every sync: up to `MAX_PAGES` (20) pages of 100 envelopes of up to 16 KiB.
- This branch adds three new ways to produce a `bad-message` that can never become valid: a package whose text is not the rendering of its boxes (`chatCrypto.ts:300`), a malformed `pay` (`:295-298`) and a mod-signed package (`:292`, which a moderator could post during a dispute). Before it, only a payload of the wrong shape did this, which also needed a tampered client.
- Scenario: the counterparty posts one envelope `{ text: <rendering>, pay: <boxes with another email> }` with a tampered client. The victim's device polls every 15 s (ChatPanel `:171`) and, in a trade room, a second time from payDetailsFeed (`:292`), each time re-downloading every envelope after the bad one for the life of the chat. Over Tor that is a real cost to the victim; the API side is only a GET each.
- Why Minor: the attacker is a trade party with a tampered client, the victim loses bandwidth and battery, never a line (later lines still flow: the guard did not move, and receipts show them), and nothing is leaked.
- Fix (cheap): tell apart "may become valid later" from "never valid". Only `mod-not-allowed` and a well-formed package refused because the trade is not yet secured (which `:339` already handles by holding) can change on a later sync; every other `bad-message` is decided and should be skipped with the cursor advancing, the guard untouched (so the sender may reuse the seq, as chatCrypto's contract says). A test: a lying package at id 2, a good line at id 3; the second sync must call `listEnvelopes` with `after = 3`.

**M2. The worker seals and posts a package before the trade is secured when asked; the gate lives only in the page.**
- `apps/web/src/chat/engine.ts:422-451` (`post`, used by `sendPay` at `:469`) never looks at `s.view.tradeSecuredAt`. The only gate is the page's `PayBoxes`: the button is `disabled={!secured}` (`ChatPanel.tsx:459`) and `onSubmit` returns on `!secured` (`:408`).
- Safe today because the reading side refuses to show a package before secured (`chatCrypto.ts:292`, the held path `engine.ts:336-342`), so an old or tampered client posting early changes nothing for the buyer. It is a defence-in-depth gap, and it has a user-visible side effect: a race between the click and the trade becoming secured (or a `chat-send-pay` from anything else in the page) posts a package that the seller's own device then holds; the boxes clear (`ChatPanel.tsx:421`) and no card appears until the trade is secured, with no word why.
- Fix: in `post`, when `make` is `sealPayDetails` and `s.view.tradeSecuredAt === null`, throw `ChatSendFailed('not-ready')` before sealing (no seq used), and let `payErrorText` say the existing "You can send these once the escrow is secured." line. Test: `sendPay` with `tradeSecuredAt: null` posts nothing.

**M3. A held package the server stops serving makes every later sync a full cold re-read.**
- `engine.ts:296`: `cold` is true on every sync while the trade is secured and some `heldPay` receipt is not in `shown`. `reopen` (`:266-277`) fills `shown` only when the server still serves that same envelope. If it no longer does (a drop by the API, review I2's case), `shown` never gets it, and every sync reads the whole chat from `'0'` (up to `MAX_TOTAL_PAGES`, 1000 pages).
- Also: the withheld filter (`:189`) then hides the receipt with no placeholder, whereas a dropped plain line gets review I2's "no longer on the server" line. The buyer never saw the package, so nothing shown is lost, but the device knows a package existed and was dropped and says nothing.
- Fix: after a secured cold read that reached the end (`reached === 'all'`) without showing a held receipt, treat it as judged: show the I2 placeholder for it and stop re-reading cold for it (e.g. clear `heldPay` on the receipt, or record the chat as "held packages judged" in the session).

**M4. Plaintext rows linger in a module-level map after the chat panel closes.**
- `apps/web/src/chat/payDetailsFeed.ts:262`: `publishPaySnapshot` writes `latest.set(key, rows)` whether or not anyone is subscribed for that trade; `latest` is only cleared when the last subscriber leaves (`:303-306`). A ChatPanel on the seller's side, or in DisputeRoom (`DisputeRoom.tsx:195`), publishes with no feed subscriber, so the rows stay in the page's memory for the page's life. Memory only, never storage: hygiene, not a leak.
- Fix: only set `latest` when `listeners.has(key)`, or delete the key in ChatPanel's unmount.

**M5. Two pollers per open trade room, four requests every 15 s.**
- payDetailsFeed polls `chatClient().sync(chat)` every `PAY_FEED_POLL_MS` (15 s, `payDetailsFeed.ts:236,292`) while the buyer's "Send exactly" card is mounted (BuyerPay's `usePaymentDetails`, `BuyerPay.tsx:328`; TradeGlance's `PayFacts`, `TradeGlance.tsx:218`, buyer only through `glanceStep`). ChatPanel polls the same chat every 15 s too (`ChatPanel.tsx:65,171`) when the pane or sheet is open, and both fire on the chat's live event. Each sync is `GET /v1/chats/:chat` plus at least one `GET …/envelopes` (`engine.ts:382,307`). The engine serialises them per chat but does not merge them.
- Cost, not a hole; the feed already follows the panel's snapshots at once through `publishPaySnapshot` (`ChatPanel.tsx:137`). Fix: pause the feed's timer while a panel for the same trade is publishing (a "panel open" flag in the feed), or lengthen the feed's poll when the chat is `ready`.

**M6. Tabs and the allowed zero-width joiners pass inside one-line account boxes; line and paragraph separators pass inside any box.**
- `checkPayDetails` refuses only `\r` and `\n` in a one-line box (`payFields.ts:165`) and `checkChatText` allows tab, ZWNJ, ZWJ, LRM, RLM and ALM (`chatCrypto.ts:103`); U+2028/U+2029 are category Zl/Zp, not Cf, so neither check sees them. So an IBAN can carry a tab, a ZWJ or a U+2028 (which `white-space: pre-wrap`, `chat.css:201`, renders as a line break). Every other format and control character, the bidi overrides and isolates included, is refused (`:99-103`), and the card is React text (`ChatPanel.tsx:341-342`: `{label}` and `{f.value}` in `dt`/`dd`), so there is no XSS and no bidi reordering of a number.
- Who is hurt: only the seller, who typed their own details and receives the money; a copied value with a hidden joiner fails at the buyer's bank, and the payment does not go elsewhere. Low.
- Fix: for kinds `email`, `phone`, `iban`, `account` refuse any whitespace other than a plain space and any character outside `\p{L}\p{N}\p{P}\p{S}` and space (no joiners, no Zl/Zp); keep the current rule for `text` and `postal`.

**M7. The table deviates from the research pack in four rows, and one row's source is not the pack (the header says it is a row-by-row copy).**
- Checked row by row against research-pack Part 2 (13 rows). Exact: Zelle, Interac, SEPA, SEPA Instant, Cash App, Venmo, UK Faster Payments, UPI (QR code omitted, which no text box can carry), Cash by mail. Deviations:
  1. **Wise** (`payFields.ts:76-78`): the pack says "IBAN for EUR and several others; sort code plus account number for GBP; account holder name" and "the form shows the exact fields". The table adds "Email registered with the account" as a third way to reach the account, sourced from data/payment-method-profiles.json, not the pack (the comment says so). It also has no way to enter other currencies' fields (USD routing and account, and the rest of the pack's list).
  2. **Revolut** (`:81`): the pack lists Revtag, phone or email for another Revolut user AND "IBAN or sort code plus account number and name" for bank transfers. The table has only the first three; a seller receiving by bank transfer to Revolut has no IBAN box.
  3. **PayPal** and **Venmo** (`:86,90`): the pack's "Recipient's name, PayPal username, email or mobile number" is read as "name optional, one of the identifiers required". A fair reading, but a reading; the pack's confidence is READ for both.
  4. **PIX** (`:94`): the pack lists a Pix key OR a QR code OR Pix Copia e Cola OR manual bank details; the table requires a Pix key. Copia e Cola is text and could be a box.
  - **ACH_TRANSFER** (`:100`) is from the profiles file (`fields`: name, routing, account), marked "not researched". Matches that file.
- Every id in the table exists in data/payment-methods.json (checked: ZELLE, INTERAC_E_TRANSFER, SEPA, SEPA_INSTANT, TRANSFERWISE, REVOLUT, CASH_APP, PAYPAL, VENMO, FASTER_PAYMENTS, PIX, UPI, PAY_BY_MAIL, ACH_TRANSFER, CUSTOM).
- Not a defect in the code; what is required vs optional is the owner's call (the module header says so). Listed for the owner under Q2.

**M8. Tests: `tradeSecuredAt` is asserted only as null; no test shows a secured trade's chat carries its `secured_at`, nor that it is the trade's own.**
- `apps/api/test/chat.test.ts:207` asserts `tradeSecuredAt: null` on a pre-trade chat. The non-null case (take, secure, `GET /v1/chats/:chat` → the trade's `secured_at` ISO string) and the stranger's 404 on the same chat (the stranger check at `:210` covers the route, not the new field, but the field cannot leak past a 404) are not pinned. Cheap to add.

## Confirmed safe (with evidence)

1. **Plaintext never reaches the API.** The only bodies the web sends on this path: `POST /v1/chats/:chat/envelopes` with the sealed envelope (`http.ts:381`), `POST /v1/trades/:code/chat` with `{}` (`client.ts:177`), and GETs. The boxes cross only the page-to-worker postMessage (`chat-send-pay`, `serve.ts:13,83`; `client.ts:152`), same origin, never the network; the worker answers with a snapshot, never a key or ciphertext (`serve.ts:4`). The API stores the envelope as given (`routes.ts:399-401`), never decrypts, has no log call in `apps/api/src/chat/` and request logging is off (`app.ts:173`). Tests: `chatPay.test.ts:73-83` and `chatEngine.test.ts:566-580` probe the wire for every name, value, label, key and the `"pay"`/`"text"` keys. Error messages never carry a value (`payFields.ts:113-123`; `ChatSendFailed('bad-details', e)` carries a PayDetailsError whose message is `code: key`).
2. **Signed by the sender, unforgeable by the mod.** The protocol's `open` verifies the signature against `participants[from]` (`packages/protocol/src/envelope.ts:399-412`), so a mod-key signature claiming `from: 'seller'` is `bad-signature` and skipped; a mod-signed package is refused `bad-message` (`chatCrypto.ts:292`, test `chatPay.test.ts:142`). Participants come only from the verified attestation (`engine.ts:250-260`). The server's `sender_role` must also agree with the signer (`engine.ts:344`).
3. **Malformed and lying packages are refused without a trace.** `openChatMessage` builds a fresh `ReplayGuard.from(state.guard)` per call and returns a new state only on success (`chatCrypto.ts:262-303`); the exact-shape check (`parsePayDetails`, `payFields.ts:180-197`: exactly `{v, method, fields}`, each field exactly `{key, value}`, no repeats, canonical order and trimming) and `renderPayDetailsText(pay) === text` (`:300`) run after decryption. Tests `chatPay.test.ts:105-129` show six malformed shapes refused and the same seq then accepted.
4. **The held path cannot desync or replay.** A well-formed early package moves the guard and gets a `heldPay` receipt with the envelope's signature (`engine.ts:336-356`); the seller's later lines (higher seq) flow (test `chatEngine.test.ts`, "held while the trade is not secured ... shown once it is"). Once secured the chat is read cold and the receipt is shown only for the same signed envelope (`reopen`, `:268`). A replay under a new id is a replay to the guard and skipped (`:365`). A seq is never reused by the sender's own device (`chatCrypto.ts:208-209`, state saved before posting `engine.ts:436`). The API enforces monotone seq per sender at post time (`routes.ts:393-398`), so served order is seq order. Nothing of the package is on the device while held (`chatEngine.test.ts`: the store never contains the name, email or method).
5. **`tradeSecuredAt` is party-only and derived only from `trades.secured_at`.** `GET /v1/chats/:chat` goes through `roleInChat` (`routes.ts:316,120-141`): a non-party, an unknown chat and a malformed code are the same 404 before any fact is read. The value is `(select t.secured_at from trades t where t.code = $2)` with `$2 = row.trade_code` (`:324`), ISO or null (`:334`). The same field is already in the parties' trade view (`apps/api/src/trades/view.ts:140`), so no new information reaches a party.
6. **The gate.** The seller's button and submit are closed until `snapshot.paySecured` (`ChatPanel.tsx:408,459`), which is `view.tradeSecuredAt !== null` (`engine.ts:197`). A package from an old or tampered client posted early is held on every reader (`chatCrypto.ts:292`, `engine.ts:336-342`), including the seller's own device. The buyer's "Send exactly" card fills only from lines with `pay` (`payDetailsFeed.ts:246`), which exist only once secured. Accepted residual, inherent to an end-to-end chat: free text saying "send to IBAN …" can be typed at any time, as it always could; the gate is about the structured card and the buyer's "Pay now" screen (Q12), which stay closed.
7. **The feed fills only from this trade's seller.** `chatPaymentDetailsSource` resolves the chat with `POST /v1/trades/:code/chat` (`payDetailsFeed.ts:287`), which the API answers only for the trade's buyer or seller and only with the chat linked to that trade (`routes.ts:201-245`); rows come from lines with `from === 'seller'`, `pay` set and not `missing`, newest by envelope id (`:243-252`). `publishPaySnapshot` is keyed by the trade code the panel was opened with (`ChatPanel.tsx:137,155`), and every caller passes the same code it resolved the chat from (`TradeChatPanel`, `ChatPanel.tsx:538-541`; `DisputeRoom.tsx:195`). Test `payDetailsFeed.test.tsx:91-99`: another trade's package does not reach this card. A buyer's own package never counts (`:51-53`).
8. **Stored data.** Receipts hold id, sender, seq, signature, time, gap and `heldPay` (`store.ts:414-436`), never text or boxes; the record is AES-GCM wrapped in IndexedDB `x2f-chat`. The opened text and boxes live in the worker's `sessions` map (`engine.ts:178`) and the page's React state and the feed's `latest` map (M4), memory only. No `localStorage`/`sessionStorage` use in `apps/web/src/chat/` or the pay screens (grep).
9. **Limits.** One-line boxes 120 chars, address 400 chars and 8 lines (`payFields.ts:49-51,161-167`); the whole text ≤ 2000 UTF-8 bytes and the envelope ≤ 16 KiB (`chatCrypto.ts:147,222`); unknown keys, non-strings and a method id outside `^[A-Z0-9_]{1,64}$` refused (`payFields.ts:148,153,185`). Hidden characters: every Cf and Cc, the tag block, CGJ and the Hangul fillers refused but tab, newline, ZWNJ/ZWJ and LRM/RLM/ALM (`chatCrypto.ts:99-103`); see M6 for the gap. The card is React-escaped text (`ChatPanel.tsx:341-342`); `data-pay-card` carries only the regex-checked method id.

## Owner questions (with recommendations)

- **Q1. Should the reader refuse a package whose `method` is not the trade's payment method?** Today a seller with a tampered client can send Zelle boxes in an Interac trade; the buyer's card shows them as rows with no method named (`payDetailsFeed.ts:250`, `ChatPanel.tsx:334`; neither the engine nor the feed knows the trade's `methodId`). The seller only hurts their own payment, so this is integrity, not safety. Recommendation: yes, refuse on the reading side (pass the trade's `methodId` into the feed's source and the panel's card; a mismatch shows "Ask in the chat"), cheap and removes a confusion.
- **Q2. The table's deviations from the research pack (M7): Wise's email way and missing other-currency fields, Revolut's missing bank-transfer fields, PIX's Copia e Cola, PayPal/Venmo's optional name.** Recommendation: keep Interac as built (your example); add an optional "IBAN" box to Revolut and an optional "Pix Copia e Cola" box to PIX; for Wise keep the three ways and add a free-text "Other account details" optional box until the per-currency form is designed. These are data rows only (`payFields.ts`), no code change.
- **Q3. Free text before the escrow is secured.** The gate closes the structured card and the "Send exactly" rows until secured (Q12), but a seller can still type their details as a plain line at any time, as before. Recommendation: accept (an end-to-end chat cannot police words), and let the buyer's screen keep saying "Pay now" only when secured, as it does.
