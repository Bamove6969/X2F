## Verdict: CHANGES REQUIRED (2 Critical, 7 Important, 9 Minor)

Task 16 on its own is solid: the approval is bound to the device cookie and a hashed 32-byte approval cookie (`approval.ts:305-314`, `timingSafeEqual`), decisions and the device limit are serialised per account by an advisory lock plus `for update`, collection is a single conditional `update … returning` (one session per approval), the live event and push carry no detail, the label shown to the approver is from fixed lists (no digits, no free text, no IP), numbers come from `crypto.randomInt` through a seam, staff are unaffected, and no column holds an IP, user agent or login name. ## Critical

**C1. A weak session can add a method that "predates" the hold, then use it to skip approval and end the hold.** `apps/api/src/auth/strength.ts:160-189` (the `onSend` hook), `strength.ts:106-131` (`provenBeforeCooling`), `apps/api/src/auth/approval.ts:214,263`.
- The hold is started in `onSend`, *after* the handler has committed the new credential. The credential's `created_at` is the handler's `now` (`webauthn.ts:199`, `totp.ts:284`, `pgp.ts:144`). `coolIfWeak` calls `deps.clock()` again later, so in production `cooling_from` is strictly after `created_at` and the new method counts as "held before the hold".
- Scenario (real clock): a thief gets a weak session without a hold. The easy paths are a trusted device (`approval.ts:218`: trusted and under the limit means no approval and no hold), or an approval the owner tapped by mistake (1-in-3 odds). The thief adds a passkey with `POST /v1/account/webauthn/finish` (confirm-it's-you with the password they have). The hook starts the hold.
- The thief then logs in with that passkey on any new device. `traderLogin` sees strong plus `provenBeforeCooling` true, so line 214 returns `null`: **no approval prompt reaches the owner's devices**, and line 263 **ends the hold**. Result: a strong session, no wait, no prompt, starting from a password alone. The same works with TOTP: a weak session enrols TOTP, then logs in with password+TOTP through the `password-totp` branch at `strength.ts:123-129`.
- Why tests pass: the fake clock makes `created_at == cooling_from`, so `<` is false. `coolingOff.test.ts:269-279` "a passkey added during the cooling never ends it" fakes the case by rewriting `created_at` in SQL instead of driving the real route.
- Fix:
  - Start the hold *inside the handler's transaction, before the insert*, with the same `now` (a `requireWeakChange`-style preHandler or a helper each security route calls). Store the method ids held at that moment (the plan's `started_methods`) instead of comparing timestamps.
  - `provenBeforeCooling` then checks membership in that snapshot.
  - Add a test that drives the real `webauthn/finish` (or `totp/finish`) from a weak session with the clock advanced between handler and hook (or with a real clock), then logs in with the new method on a new browser. Expect `approve-on-device` and the hold still on.

**C2. During the hold a weak session can still change the password and add or delete login methods, and the change applies at once.** `strength.ts:138-157`; `COOLING_BLOCKED_ROUTES` holds no security route.
- Plan 2 Task 17 (29c, merged): the triggering change is stored in `pending_change` and applied only when the hold ends by time; a strong pre-hold login cancels it. *Lead defaults:* login-method changes are refused during the hold. R42 says "the triggering change waits out the 24 hours". The branch applies every change immediately and only starts or extends the hold afterwards.
- Scenario: a thief with the password logs in on a new phone while nothing is logged in. The hold starts (correctly). Inside the 24 hours the thief:
  - deletes the owner's passkey and PGP key (`DELETE /v1/account/methods/:type/:id`; confirm-it's-you is the password, which the thief has);
  - adds their own passkey;
  - changes the password.
  
  The owner now has no pre-hold method left to end the hold, cannot log in, and after 24 hours the thief has the account with no restrictions. The "push on every new login" warning is useless if the owner cannot get back in.
- Fix:
  - Add every `SECURITY_CHANGE_ROUTES` entry (and `PUT /v1/account/security/logout-timer`, see M2) to the hold check for weak sessions: refuse during the hold (`recovery-hold`/`cooling-off`, 403).
  - For the first, hold-starting change, either refuse it and start the hold (simplest), or implement `pending_change` as Plan 2 Task 17 (29c) specifies.
  - Deletions of a pre-hold method must never apply before the hold ends.
  - Tests: during the hold, a weak session's `DELETE /v1/account/methods/passkey/:id`, `PUT /v1/account/password` and `webauthn/finish` → refused, nothing changed; the owner's pre-hold passkey still ends the hold.

## Important

**I1. PGP alone counts as strong, against the owner's ruling of 14:12.** `strength.ts:38`; `sessions.ts` `startSession` default (`method` `pgp` → `'strong'`); `strength.ts:110-116` (a PGP-alone login ends the hold); `approval.ts:214` (a PGP-alone login skips approval during a hold); copy `apps/web/src/screens/auth/refusals.ts` `coolingSentence` ("Log in with a passkey, security key or PGP key to end the wait").
- The owner, 14:12: the qualifying no-wait combos are password + authenticator, password + passkey/security key, PGP + passkey/security key, and a passkey or security key alone. "Everything else (incl. PGP alone, any single weak factor) → 24 h." The main line's plan 29c even has PGP alone as `pgp-single` with no hold (*lead reading*), so the plan text must be updated too.
- Scenario: someone with the owner's PGP private key (a stolen laptop keyring) logs in on a new device with nothing else logged in: no hold. During a running hold, the same login skips the approval and ends the hold.
- Fix:
  - PGP alone → `weak-single`.
  - Replace `kinds.size >= 2 → 'two-factor'` (`strength.ts:36`) with an explicit allow-list of the owner's combos, so a future "TOTP + recovery code" or "PGP + password" path is not silently strong. The 29b plan's lead default "TOTP + recovery code" backup combo is *not* in the owner's list.
  - Update the copy and `loginStrength`'s test (`coolingOff.test.ts:105`).
  - Tell the lead the plan text (29c "PGP alone: no hold") needs the 14:12 correction.

**I2. Starting and ending the hold is not atomic with what triggers it, and fails open.** `approval.ts:258-264`; `strength.ts:164-173`.
- `noApprover`: the session is committed by `startSession`, then `startCooling` runs in a separate statement. If it fails (pool exhaustion, a deadlock, a crash), the weak new-device session exists with no hold.
- The security hook runs in `onSend` after the change committed. If `coolIfWeak` throws, the client gets a 500 but the password or method change stays, with no hold.
- `provenBeforeCooling` is checked inside the account-locked transaction (line 214), but `endCoolingIfOwner` runs after commit (line 263) and checks again without the lock.
- Fix:
  - Do the hold write in the same transaction as the session insert (give `startSession` an `inTx` callback, or have `traderLogin` insert the session inside `withTx`).
  - Do it in the same transaction as the security change (ties in with C1's fix).
  - Test with an injected failure: no session or change without its hold.

**I3. A held backup session still cannot finish open trades.** `sessions.ts:242-245` (unchanged); trade routes (`trades/routes.ts`, `disputes/routes.ts`) take no `allowRecovery`/`allowHeld`.
- Plan 2 Task 17 and R42: during the hold, `requireSession({ allowHeld: true })` lets the routes that finish trades already open through: GET trade and chat, `mark-paid`, `release-started`, `open-dispute`, chat send, and the buyer's cancel before "I've paid".
- The branch opens them only to *full* sessions of a cooling account (`coolingOff.test.ts:223`). A TOTP-alone or recovery-code backup login is still a `level='recovery'` session, which gets 403 `recovery-session` on every trade route.
- Scenario: a buyer loses their phone mid-trade, logs in with a recovery code to mark paid before the window closes, and is refused. The trade lapses.
- Fix: the trade-finishing routes take `requireSession({ allowRecovery: true, allowHeld: true, kinds: ['trader'] })`, and the rest stays as is. Add the plan's test: during the hold, `mark-paid` and `release-started` from a held recovery session succeed, and `take` / wallet add → refused.

## Minor

**M1. A cancelled backup session leaves its hold on the owner.** `recovery.ts:179-192`. `DELETE /v1/account/recovery-sessions/:id` from a full session ends the thief's held recovery session, but the account hold started by `weak-backup-login` runs on for 24 hours, and the owner cannot trade until they log in again with a pre-hold strong method. Fix: when a full *strong* session cancels the recovery session that started the hold, end the hold too (alert `hold-ended`).

**M2. `PUT /v1/account/security/logout-timer` is a Settings → Security change but not in `SECURITY_CHANGE_ROUTES`** (`strength.ts:138`). A weak session can stretch the idle timer to the maximum with no hold. Add it, or record why not.

**M3. Offers posted before the hold can still be taken, so the account gets new trades during the hold.** `trades/take.ts` checks only the *taker's* hold. A thief's hold doesn't stop takers starting trades on the owner's live offers, and the thief then sets the poster wallet (`POST /v1/trades/:code/wallet`, existing wallets only, so the coins still go to the owner's wallets). Low risk, but "no new trades" isn't fully true. Lead call: pause the account's offers from the market while the hold runs, or record it as accepted.

**M4. Approval lifetime is 2 minutes; the plan's lead default is 5** (`approval.ts:49`; plan Task 16 "expires after 5 minutes"). No lead decision is recorded. Either record it in the plan or use 5. Two minutes is tight for someone who has to find their other phone.

**M5. The new device is told how many devices the owner is logged in on** (`approval.ts:252-254`, `devices: { loggedIn, max, oneDevice }`; shown at `ApproveOnDevice.tsx:29`). Anyone with the password learns the number of live sessions and the "One device at a time" setting before anyone approves them. Fix: send `devices` only with `ok` (after approval), or drop `loggedIn`.

**M6. A strong pre-hold login skips the device limit too** (`approval.ts:214` returns before `maxDevices`), so a 4th or 5th session can open during a hold. Fix: still apply the limit, and on reaching it return the session list to choose from.

**M7. Not atomic: one-device and limit logouts run after the new session starts** (`approval.ts:346-349`). If `endForNewDevice` fails, the new session exists and the old ones that should have ended don't. Put the logouts in the same transaction as the session.

**M8. Sessions from before migration 014 count as weak** (`014_cooling_off.sql:60`, `strength.ts:186`). After deploy, any existing session that changes its methods starts a 24-hour hold on its own account. That's fine before launch, but it should be in the deploy notes. Also note that, per the owner's 14:12 answer, every account will need two factors (sign-up requires the second). That is not this task, but the copy "Change how you log in now" (`LoginApprove.tsx:88`) will hold a password-only owner for 24 hours if they follow it.

**M9. Test gaps** (in addition to C1, C2, I3 and I2's failure injection):
- no test that a weak session's security change *during* a running hold is refused or kept pending;
- no test of a trusted-device weak login followed by a method add;
- no test that the `new-login` push skips the device that just logged in;
- no test that a strong pre-hold login still respects the device limit;
- `coolingOff.test.ts:105` asserts PGP alone is strong (must flip, I1).

## Hold-evasion checklist (what I checked)

| Path | Result |
|---|---|
| New device, weak login, owner logged in | Approval needed; the owner can block; a wrong number blocks; 10 an hour per account. OK. |
| New device, weak login, nothing logged in | Hold starts (but not atomically, I2). |
| Trusted device, weak login | No approval while under the limit, and no hold. Matches the plan, but it is the easiest entry for C1. |
| Weak session → add a method → strong login | **Approval skipped and hold ended (C1).** |
| Weak session during the hold → delete or replace methods | **Allowed (C2).** |
| PGP alone | **No hold (I1).** |
| Backup login (TOTP or recovery code alone) | Held recovery session plus account hold. OK, but it cannot finish open trades (I3). |
| Approving during the hold | Refused; blocking still works. OK. |
| Approval spam / number guessing | 3 open, 10 an hour, 1-in-3 with one try, superseded per browser. OK. |
| Poll from another browser or without the cookie | 404, the same as an unknown id. OK. |
| Staff | Unaffected; the gate test (`deviceApproval.test.ts:532`) checks no other file starts a later full session. OK. |
| Privacy | No IP, user agent or login name stored or shown; push texts are fixed. OK (M5 aside). |
