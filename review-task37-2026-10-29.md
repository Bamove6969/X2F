## Verdict: CHANGES REQUIRED (1 Important, 7 Minor)

The core build is right. The list and the detail both filter with `blockedEitherWaySql`. The detail's 404 for a block runs the same single query and goes down the same throw path as an unknown or paused offer, with the same body, so there is no status, body or timing oracle I could find. Presence stays one-way through `lastSeenSql`. DELETE touches only the caller's own rows. Open trades finish (tested through mark-paid, release-started and settled after a mutual block). The SQL is parameterised: the helpers interpolate only constant expressions. Every lookup is a primary-key `(account_id, blocked_id)` lookup, and the OR of two PK probes BitmapOrs. The tripwires read the local tree only. The one Important finding is cheap to fix now.

## Important

**I1. `/v1/methods` still shows a blocker's offers to the identified, blocked person: the count and the best price.** `apps/api/src/offers/routes.ts:306-313` (`liveOfferStats`) and `apps/api/src/methods/routes.ts:76` (`source({ side, currency })`, no viewer).
Scenario: A blocks B. B, signed in, opens the method picker for sell/EUR and sees "SEPA: 3 offers, best €X". B taps SEPA and gets 2 cards, none at €X. B now knows A's price, and that someone with the €X offer is hiding from them. This is more than the builder's "N vs N-1" residue. `bestRate` can be the blocker's own price, which is literally "seeing your offers" (owner's words). Unlike the logged-out residue, the viewer here is identified: the session cookie is on the request.
Cheap fix (about 15 lines and 1 test):
- Export `viewer()` from offers/routes.ts, or move it into traders/.
- In `/v1/methods`, call it and pass `viewerId` through `LiveOfferQuery`.
- Add `and not ${blockedEitherWaySql('o.account_id', '$4::uuid')}` to `liveOfferStats`.

The route is not cached per viewer (it is computed per request), so nothing breaks. Test: after a block, B's `/v1/methods` count and `bestRate` match the B-visible list.

## Minor

**M1. Unblock resolves the name through `checkDisplayName`, so a later change to the reserved list strands a block.** `apps/api/src/nudge/routes.ts:230` (and `apps/web/src/screens/settings/Blocked.tsx:41`).
Scenario: A blocked `helpdesk1`. Later `help` becomes a reserved token (or the look-alike rules widen). `findByPublicName` returns null, so DELETE answers 404. Blocked.tsx takes 404 as "account closed" and removes the row. The block is still in the database and the row comes back on reload, and A can never unblock that person.
Fix: delete within the caller's own blocks by key, without the shape or reserved check:
`delete from account_blocks b using accounts a where b.account_id = $1 and b.blocked_id = a.id and a.display_key = lower($2)`.
404 only when no such account exists. Account deletion already cascades (107_nudge.sql FKs `on delete cascade`).

**M2. Focus is lost at every step of the block and unblock flows; unblocking is not announced.** `apps/web/src/screens/settings/BlockAction.tsx:69` (open), `:56` (Cancel), and the confirm-to-done step; `Blocked.tsx` Unblock removes the focused row.
Scenario: a keyboard or screen-reader user activates "Block X". The button unmounts, focus drops to `<body>`, and the confirm group (no live region) is not announced. The same happens on Cancel and after Unblock.
Fix:
- Move focus to the confirm button (or the group's heading, with `tabIndex=-1`) on open.
- Return focus to "Block X" on Cancel.
- After an unblock, show a `role="status"` line ("Unblocked X") and focus the list or heading.

**M3. Nothing links to `/settings/blocked` except the one-time "You blocked X" note.** Scenario: a trader who blocked someone last week cannot find the list to unblock them without typing the URL. The NEEDS_DESIGN_BLOCK tripwire defers the link to Plan 5's Profile tab. Until then, a link from `/settings/security` (or wherever settings live today) would close the gap. A lead call.

**M4. Other "treated as logged out" cases beyond logged-out and second accounts.** `apps/api/src/offers/routes.ts:292` / `viewer()`. Every 401 and 403 from `viewerCheck` becomes a null viewer, which includes a recovery session (`recovery-session` / `recovery-hold`). Scenario: B, signed in through account recovery, browses and sees A's offers like a stranger. This belongs to the same accepted residue. Add it to the coordination.md "What still leaks" line so the lead's decision covers it explicitly.

**M5. NEEDS_PROFILE_BLOCK matches only a single-quoted `'/v1/traders/`.** `apps/api/test/block-tripwires.test.ts:46`.
Scenario: Plan 5 registers ``app.get(`/v1/traders/:name`…)`` or `"/v1/traders/:name"` without `hasBlocked`. The tripwire stays green and the profile leaks to the blocked person.
Fix: match `/['"`]\/v1\/traders\//`.

**M6. Nudges check the block one way only.** `apps/api/src/nudge/routes.ts:130` drops only blocked-person-to-blocker nudges. Today a nudge needs an open trade, which is allowed to continue, so this is fine. Once Task 20 makes an offer chat a shared context, the blocker could still nudge the blocked person from an old offer chat after the block, and the blocked person receives "<name> wants to trade" from someone they cannot trade with.

**M7. The copy promises more than the build delivers.** `apps/web/src/screens/settings/blockCopy.ts:8,17`: "They won't … see when you're online." A blocked person who logs out still sees coarse presence and the offers (the accepted residue). The copy is `COPY-UNSIGNED`. Flag this to the owner at sign-off, so either the copy softens or the owner rules on hiding presence from every logged-out viewer.

## Checked, no finding

- **List and detail, both directions; online sort.** The block filter runs before `LIMIT 500`, so hidden offers cannot crowd out visible ones.
- **Detail 404.** The body is identical to an unknown offer, and the test compares bodies. Headers match too: `viewer()` uses `touch: false`, so there is no cookie or expiry difference. Moving `viewer()` ahead of the query changes nothing visible.
- **Trade view counterparty** (`trades/routes.ts:79`): goes through `traderSummary(…, me)`. The blocked person sees `online:false, lastSeenAt:null`.
- **SSE, push and the events route:** no offer or presence data.
- **DELETE /v1/account/blocks/:displayName.**
  - It deletes only `account_id = req.auth.accountId`, so no one can remove another person's block.
  - Name enumeration (404 vs 204) is the same as Task 26's existing POST, and display names are public.
  - Display names are ASCII `[A-Za-z0-9._-]{5,20}`, case-folded through `display_key`, and cannot be renamed. NFC and case handling and path encoding are therefore safe; `encodeURIComponent` is in `blockApi.ts`.
  - Unblocking yourself gives 204 (POST gives 400). That is harmless.
- **GET /v1/account/blocks:** returns only `{displayName, blockedAt}` for the caller's own blocks (the public name, never the login name). Who blocked me is never answered.
- **Web confirm and disable.**
  - BlockAction asks once, with Cancel. After a block, Trade is disabled on the quote (`canTrade` gate; e2e asserts `[data-primary]` disabled).
  - It is shown only to a signed-in non-poster (`myName !== poster`; `/v1/me` carries `displayName`).
  - Refusals show inline.
- **No migration, no new CSS.**
