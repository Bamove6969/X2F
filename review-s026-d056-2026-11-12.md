## The checks

### No login-name leak: holds
- `listFeedbackForm` left-joins `accounts` and sends `a.display_name`, the public name column (`PUBLIC_NAME_COLUMN` is `display_name`). It never sends `login_name` or `login_key`. `accountName` is null whenever `accountId` is null.
- A deleted account gives a null id, so the row reads as anonymous.
- content.test seeds a display name that differs from the login name. It asserts that the name shown is the display name and that the whole JSON body never contains the login name.
- A team member's named send stores the team account's id (`feedback/form.ts`: `req.auth.accountId`). The list therefore shows the team's public name, never the member's login account.
- Legacy accounts (`legacy_login_name`) have a display name equal to the login name by construction. That name is already public on offers and chats, so this exposes nothing new.

### The log: no detail leak; a small spam surface (m2)
- Each list page (`GET /staff/v1/feedback/form`, any cursor) appends `feedback.form-opened { namedRows: <count> }`.
  - The detail holds only a count. It holds no row ids, cursor, account ids or names, so the log cannot be used to tell who sent what.
  - The schema in `log/actions.ts` pins the field as a number.
- The actor and time are the reader's own. That is the point: the owner can see who looked.
- The append runs after the read, in its own transaction. If logging fails the request fails and no data goes out, so it fails closed.
- Only staff holding `feedback.read` can trigger it. Each entry names its actor, so spam is attributable.
- **m2:** there is no rate limit and no merging. Every request, empty pages included, takes the hash-chained log's advisory lock, the same lock the money paths wait on (staff pay's `appendLog`). A script with the grant could grow the log and contend that lock.
  - Suggest at most one entry per staff session per few minutes, or logging only the first page, or a per-staff limit like `keyTap`'s.
  - This is low risk: it is a trusted, attributable actor.

### Grant scoping: the code matches the stated decision (Q1)
- The route is still `requireStaff('feedback.read')`. That means the owner and seniors by role, and moderators or helpers only when the owner ticks the grant (owner Q60).
  - This is unchanged, and members.test still pins the grant path. Its grant-set log entry is still asserted.
- What changed is deliberate (lead, 12 Nov, replacing lead review 7 Nov M5): grant holders now get `accountId` *and* `accountName` on named rows, the same as the owner and seniors.
  - The old M5 assertions were removed and replaced by assertions for the new rule. That is a behaviour change, not a weakened test.
- **m1 (least privilege):** staff-web never shows `accountId`. It is used only for the Anonymous/named check, and `accountName` is enough to follow up. Suggest either:
  - dropping `accountId` from the response (or keeping it for the owner and seniors only); or
  - deriving "named" from `accountName !== null`.
  This would keep raw account ids out of grant holders' hands without changing what anyone sees.
