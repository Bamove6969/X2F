## Verdict: CHANGES REQUIRED

There are 2 Important and 9 Minor findings, and no Critical one. I found no way for a member to reach owner powers, and no way for coins to get stuck. The two Important findings are both about trades: with members on the team, trades fail quietly, because the escrow can only run on the account owner's device, while the live stream and push code treat any stream of the account as reaching the account.

## What holds (checked)

- **The fail-closed gate is sound.**
  - `requireSession` (`auth/sessions.ts:290-296`) answers 403 `owner-only` whenever `member` is left out. It answers 401 the moment the `team_members` row is removed, not joined, or moved to another account. It answers 403 when the member's login account is disabled.
  - I listed every `requireSession(` call. 34 name no member role, so they are owner-only. These name one: offers (`offers`), take, trade wallet, trades, confirmations, disputes, attestation read, `/v1/events` and `GET /v1/wallets` (`trades`), and `/v1/account/me`, the browse viewer and the feedback form (`any`).
  - No route reads the session cookie outside `requireSession`. `/v1/logout` only revokes, which is correct for a member too.
  - Confirm-it's-you (`/v1/confirm/*`) is owner-only, so a member can never get a confirm token. Login methods, sessions, logout timer, login name, wallets add/remove, blocks, nudges, push, alerts and the team routes are all owner-only.
  - A member cannot change their own roles (owner-only, tested). Staff routes need kind `staff`, and a member session's kind is always the team's `trader`.
  - The relay and moderation services do not use API sessions.
- **Member login.**
  - `allowedMethods`, `pairAllowed`, `needsAfter` and `leavesLogin` treat `member` exactly as `staff`.
  - `completeLogin` runs `assertNotDisabled` on the member's login account.
  - `startSession` sends a member's login to the team account under `for share` of the team_members row, so a removal running at the same time waits and then revokes this session too. It refuses a session that is not `full`. It gives no onboarding window, and it alerts the owner (`team-member-login`).
  - A password, TOTP or backup-code login is impossible: members hold none of these.
  - A member who has only proved the first factor (status "joining") can never start a session: `joined_at` is still null.
- **Invites.**
  - The code is 256 bits, only `sha256('team-invite/'+code)` is stored, the answer is one 404 for wrong, used and expired codes, and it lives 24 h.
  - The code travels in the `#fragment`, so it is never in a request URL. The API sends `referrer-policy: no-referrer`. `MemberInvite` reads the hash and `replaceState`s it away at once.
  - Single use holds under a race: `startMember` re-runs `openInvite(..., lock=true)` with `for update of tm` inside the join transaction. Under READ COMMITTED, the second finisher re-checks the updated row (`invite_hash is not null`, `member_account_id is null`) and gets 404 before `createAccount`.
  - Every step after `join/start` is bound to the device (challenge `device_hash`, and the setup challenge `team-setup` is per device and single use through `useSetup`).

  - The owner's own actions write nothing. Refused actions write nothing (tested).
  - The trigger refuses UPDATE except clearing `trade_code` with every other column unchanged. It refuses DELETE except in the cascade after the team account row is gone.
- **Signing is refused.** `release-started` (`MEMBER_SIGNING_EVENTS`) and `POST /v1/trades/:code/identity` answer 403 `member-cannot-sign`. `open-dispute` cannot be sent through `/events` (`clientEvent`), so it is audited once, by the dispute route.

## Important

**I1. A Trades member's open stream stops pushes to the account owner, the only device that can run the escrow, and the "accepted your offer" sheet then opens on the member's device.**

Where:
- `apps/api/src/events/tradePublisher.ts:28-29` (`streamed = publish(id) > 0; if (!streamed ...) push`)
- `apps/api/src/trades/take.ts:316` (`if (app.events.publish(posterId, ev) === 0) push`)
- `apps/api/src/nudge/routes.ts:54` (`delivered(accountId) ? false : push`)
- `apps/api/src/events/routes.ts:41` (members with `trades` attach to the account's bus slot)
- `apps/api/src/events/bus.ts:56-58` (5 streams per account, members included)
- `apps/web/src/App.tsx:132-148` (`isTrader` now true for a Trades member, so `LiveAccepted` runs on the member's device)

A member's stream is attached under the team account id. Every "is the account reachable?" check therefore counts it as the owner being reachable.

Scenario: the owner posted a sell offer and is offline, and a Trades member has the app open.
1. A buyer takes the offer. `publish(posterId)` returns 1 (the member's tab), so no push goes to the owner.
2. The member's `LiveAccepted` shows the AcceptedSheet. If the member confirms it, the `ConfirmedTrade` is stored in the member's sessionStorage.
3. The room starts the escrow on the member's device, and `registerIdentity` answers 403 `member-cannot-sign`.
4. The owner is never told. Even if they open the trade, their device has no `ConfirmedTrade`, so `escrow/runtime.ts:469` fails with `not-confirmed`.
5. The trade can never be secured and ends at the funding timeout.

The same suppression applies to every later step that needs the owner's device. For example, the buyer's `mark-paid` reaches only the member's tab, so the seller-side owner gets no push to release, and the trade drifts into a dispute.

Three member tabs plus two of the member's own can also fill the 5 per-account slots. The owner's own `/v1/events` then gets 429 `busy`, and every push is still suppressed.

No coins are lost: funding needs both identities. But with a member online, any of the owner's own trades can fail without a word.

Fix:
- (a) Pass `memberId` to `bus.attach`, and have `publish`/`delivered` report owner streams apart from member streams. Push to the owner whenever no stream of the owner's own is open, for every event that needs the owner's device (all trade events and `accepted`), whatever the member streams are doing.
- (b) Give member streams their own cap, or at least keep one slot per account for the owner.
- (c) On a member's device, `LiveAccepted` must not offer the confirm sheet (it would store a `ConfirmedTrade` on a device that can never use it). Show "<buyer> took your offer. The account owner's device sets up the escrow." until Task 42.
- Add API tests: a member stream is open and the owner has none, then a trade event and a take of the owner's offer each still send the owner's push; a member stream never makes the owner's attach answer 429.

**I2. Every trade a Trades member takes cannot proceed: the owner's device can never confirm it, and the member's device is refused.**

Where:
- `apps/api/src/trades/take.ts:223` (`requireTrader` = `member: 'trades'`)
- `apps/web/src/escrow/runtime.ts:461-470` (`not-confirmed` without the device's own `ConfirmedTrade`)
- `apps/api/src/trades/identity.ts:15-20` (member refused)

The take stores the `ConfirmedTrade` on the member's device (useTake, `x2f.confirmed:<code>` in that tab's sessionStorage). The only device allowed to register the account's trade identity is the owner's, and it has no `ConfirmedTrade` for this code. By design (Plan 3 Task 18/22: "never set by the API alone"), the room refuses to build one from the API's view.

Result: the take succeeds and counts toward the account's caps. The counterparty registers and waits. The trade never gets an escrow and times out in `funding`, which is a cancelled trade on the account and wasted time for the counterparty. No coins are at risk (funding needs every identity), which is why this is Important and not Critical.

The tests (`team.test.ts:229`, "a Trades-only member takes and marks paid") only drive the trade with `driveTo` on the server, so they never meet this.

Fix, either:
- (a) **Recommended until Task 42:** refuse a member's take with 403 `member-cannot-sign`. Add `take` to the NEEDS_PLAN3_TASK42_MEMBER_KEY tripwire. The web shows it through CantDoThat ("Only the account owner's device can start a trade for now"). Members keep mark paid, cancel, dispute and appeal on trades the owner's device set up.
- (b) Build an owner-side "Confirm this trade on this device" sheet, like the AcceptedSheet, that shows the deal the member took and stores the owner's own `ConfirmedTrade` after the owner explicitly confirms. Pair it with I1's push, so the owner learns a member took a trade.

Either way, add a test: a member take, then the owner device's room either starts from the owner's explicit confirmation or the take was refused.

Spec 6.7 and R44 say members "accept trades". (a) narrows that until Task 42, so the lead must decide; (b) keeps it.

## Minor

**M1. A removed or role-reduced member's request already past the gate still commits, and is logged as the removed member.**
Where: `apps/api/src/team/audit.ts:44-56`, `auth/sessions.ts:290-296`, `team/members.ts:158-198`.
`requireSession` checks the member once, before the handler. `DELETE /v1/team/members/:id` or a `PATCH` dropping a role can commit in between: the post, take or mark-paid commits afterwards, and its audit row names a removed member or a role they no longer hold. "Removal ends sessions at once" therefore holds for new requests only.
Fix: in `auditMember`, run `select roles from team_members where id = $1 and removed_at is null for share` and throw 401 or 403 when the member is gone or no longer holds the route's role. Pass the needed role in. This serialises with `removeMember` and `setRoles`, whose updates take the row lock, so a removal or role change either waits for the action or the action rolls back. Test: remove the member between the preHandler and the handler (a test hook, as `events/routes.ts` has `afterAttach`).

**M2. Dropping a member's Trades role leaves their live stream running.**
Where: `team/members.ts:158-168` (`setRoles` closes nothing), `events/routes.ts` (only `maxStreamMs`, 10 min, ends it).
A member downgraded from Trades to Offers keeps receiving the account's trade codes and states, and `accepted` events, for up to 10 minutes.
Fix: when `setRoles` removes `trades`, call `events.closeSession(accountId, id)` after the commit for each live session of that member, as `removeMember` does. Test: a member stream ends when the owner drops Trades.

**M3. Nothing structural keeps the audit complete.**
Every new member-allowed effectful route must remember `auditMember` by hand. The feedback form (`feedback/form.ts:117`, `member: 'any'`) is effectful and writes no row. That is probably right, because feedback is anonymous by design, but nothing records that it was decided.
Fix: add a test that scans `apps/api/src` for `requireSession({... member:` and fails for any non-GET route that is neither in the audited list nor in a documented exemption list (feedback form: anonymous, not an account action). Also widen the audit test, which today covers only offer-posted/paused/relisted and mark-paid: add trade-taken, trade-wallet-set, final-alert-seen, dispute-opened and appeal-filed, one row each.

**M4. Append-only is weaker than it looks.**
Where: `migrations/015_team_members.sql:54-88`.
- Row triggers do not fire on `TRUNCATE`, and the app's DB role owns the table, so it can also `alter table ... disable trigger`. The rule therefore protects against code bugs, not against a compromised API role.
- `member_account_id ... on delete cascade` → `team_members` → `team_audit` (member_id cascade) means deleting a member's login account raises "append-only" while the team exists. That is safe today, but it blocks Plan 7 account deletion and any later deletion of a removed member's login (see M6).

Fix:
- Add `create trigger ... before truncate on team_audit for each statement` raising unless a session setting the test reset sets is on, or revoke TRUNCATE from the app role if roles are separated (as `PURGE_ROLE` is).
- Change `team_members.member_account_id` to `on delete set null`, so a member's login can be deleted while the audit rows keep the member's name.
- Add both to the NEEDS_PLAN7_PURGE_AUDIT tripwire text.

**M5. The R36 guard depends on how the purge happens to be written.**
Where: `apps/api/test/team.test.ts:389-394` (regex `delete\s+from\s+trades\b`).
A purge written as `DELETE FROM public.trades`, through a CTE, or through a query builder passes the tripwire and leaves trade codes in `team_audit`.
Fix: when trades get deleted (Plan 7), add an `after delete on trades for each row` trigger in that migration: `update team_audit set trade_code = null where trade_code = old.code`. Then the database does it and no call site can forget it. Until then, widen the regex to `/delete\s+from\s+(\w+\.)?"?trades"?\b/i`.

**M6. A removed member's login account stays forever.**
Where: `team/members.ts:186-191`.
It is disabled, not deleted, so their login name, stripped PGP public key(s) and WebAuthn credentials stay with no end date. Their login name also stays taken for good. A "joining" member whose setup expires (`createInvite` closes the row) keeps an enabled login account with one PGP key. It cannot log in (no `joined_at`), but nothing ever deletes it.
This is against privacy-first data minimisation; not urgent.
Fix (with M4's `set null`): delete the member's login methods, or the whole login account, at removal and when a setup expires. Or add it to Plan 7's purge with a retention rule, and add a NEEDS_PLAN7 line.

**M7. Trades members read every payout wallet's full address.**
Where: `wallets/routes.ts:362` (`GET /v1/wallets`, `toJson` = full `address`).
A member needs only `id`, `label`, `app`, `usableFrom` and the address end to pick a wallet. The take and `/trades/:code/wallet` take a `walletId`, and the member's device never runs the escrow, so it needs no `ownAddress`. This lead default exposes more than the role needs.
Fix: for `req.auth.memberId !== null`, return `address: addressEnd(address)`, or omit `address` and add `addressEnd`. If I2(b) is chosen later, the owner's device builds `ownAddress` itself.

**M8. Login.tsx's new passkey branch cannot be reached, and its comment is wrong.**
Where: `apps/web/src/screens/auth/Login.tsx:266-275`.
The comment says "A staff or team-member login". But discoverable passkey login refuses every non-trader (`webauthn.ts:628`), and members are told to start with PGP (`teamCopy.ts:89`). Showing `SecondStep` is harmless (the server still decides the pair), but it is untested, and if the server ever returns `second-factor` here it is a silent change to the main login flow.
Fix:
- Either keep the old message, or keep the branch with the comment corrected ("unreachable today: discoverable login is trader-only").
- Add an API test that a member's passkey used as the first factor through discoverable login is refused.
- Add a web test (or an assertion in login.spec) that a trader's passkey still lands on returnTo with no second step.

**M9. Small items.**
- (a) The `team-invite` confirm binds only the roles (`routes/team.ts:149`), not the display name, so one token could invite "Alice" or "Mallory" with the same roles in the same session. Bind `displayName` (or its key) in the action, and show it in `describeAction`.
- (b) A Trades member's `final-alert-seen` (`trades/routes.ts:109`) sets `final_alert_delivered` for the account. That fits the role, since the member can answer the alert, but the owner gets no sign of it beyond the audit row. Say this in the plan and the copy.
- (c) `requireSession` could also refuse `row.kind === 'member'` outright. No path inserts such a session today, but the check would keep it that way.
- (d) Members never accept the Terms themselves: the team account's acceptance covers them. Ask the lead or owner, alongside lawyer item 2.
- (e) `webauthn/finish` (`routes/team.ts:258-286`) stores the credential before `useSetup` and `finishMember`. A lost race or a member removed meanwhile leaves a credential on a disabled login. This is harmless, and M6 cleans it up.
