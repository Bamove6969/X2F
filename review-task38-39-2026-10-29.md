## Verdict: CHANGES REQUIRED (3 Important, 8 Minor)

The state machine work is careful: no cancel event gets through in `paid` (checked on both `state` and `paidAt`), `mark-paid` clears any open proposal, `fund-started` is seller-only and can be posted once, in `funding` only, `walk-away` is refused once coins are seen, `confirm-cancel` ignores the request body (`clientEvent` sets 0 and the route fills in X2F's own node count), `return-confirmed` is a system event recorded once (the watcher/route race ends in a rule refusal, which is swallowed), and the 48 h timer is anchored on `cancelConfirmableAt`, frozen and shifted by pause/resume and cannot close twice. The owner's buyer wording (`PAY_WARNING_LEAD`/`WHY`) matches word for word. Both warnings actually gate the action: the hold stays `disabled` while `!acked`, and I've paid goes through the warning first. Reloads and second tabs only ever show the warning again; they never skip it. The three Important findings: a new dispute refusal that leaves a buyer who paid with no way to dispute, the device runtime that still lets a buyer cancel in `paid`, and a red web suite on the main line.

## Important

**I1. The new "a cancel can't be disputed" refusal also hits buyers who HAD paid.** `packages/trade/src/machine.ts:425` (also `apps/web/src/screens/dispute/rules.ts:79,131`, and `DisputeSlot.tsx:85`'s "You cancelled…" text)
The refusal looks only at `settling` and `dispute`, not at `paidAt`. A cancel refund can still land after "I've paid": the settle window lapses (`onTick` settling → back to `settleFrom`), the buyer marks paid, and only then does the already-signed refund reach the chain (`settled` is accepted from `paid`, `SETTLED_FROM`). I confirmed this with a scratch machine probe for both kinds: refunded, `paidAt` set, `open-dispute` → `wrong-state`.
Failure scenario (a seller scam): the seller proposes a cancel and the buyer accepts. For `mutual-cancel` the buyer builds and the SELLER co-signs last (`policy.ts` ROUTE), so the seller ends up holding the fully signed refund. The seller holds it back until `settleBy` passes, and the trade returns to `secured`. The seller then tells the buyer "glitch, just pay". The buyer pays the fiat and marks paid, and the seller broadcasts the refund. The seller now has the fiat and the XMR. Before this branch the buyer had the 90-day dispute. Now the API answers 409 and the screen tells the buyer "You cancelled". The buyer-cancel version is the same, with the buyer's device as the one sending the refund (see I2).
Fix: refuse only when `paidAt === null` (machine, `isCancelRefund`, and the RefundedSlot "Cancelling" copy). `awaitingCancelConfirm` should probably exclude `paidAt !== null` as well, so the seller isn't told "<buyer> cancelled before paying". Add a machine test and an API test for the late refund.

**I2. The device escrow keeps a buyer's cancel alive in `paid`.** `apps/web/src/escrow/runtime.ts:209-210` (`CANCEL_STATES`/`BUYER_CANCEL_STATES` include `paid`), used by `viewSupports` at `runtime.ts:219-229` and by the tap-holds logic at `runtime.ts:946-949`. Also `apps/web/src/escrow/policy.ts:96`.
The builder left these for Task 12's owner. Here is the risk: a buyer taps Cancel in `secured`, so the device records a user intent `buyer-cancel`. The mod is slow or offline, the settle window lapses, the trade returns to `secured`, and the buyer marks paid (`markPaid` doesn't reset the intent). `viewSupports('buyer-cancel', paid)` is true, so the tap still holds: the buyer's device keeps building and signing the cancel refund in `paid` and asks the mod to co-sign it. Today's moderation service signs it, because the guard on claude2's `wip/second-p3-task10` is not on the main line. Combined with I1, the buyer then also loses the dispute.
Fix (cheap): drop `paid` from both runtime lists and from policy `BUYER_CANCEL_STATES`, and rework the buyer-cancel-in-paid cases in attestation-flow.test.ts. Otherwise, make the Task 10 mod guard an explicit landing condition for this branch. Fixing I1 alone is not enough; the device also has to agree with "no cancel after I've paid".

**I3. Landing blocker: the full web vitest goes red after merging the main line.** Main's Task 21 copy-lint `refusal` rule flags three lines:
- `apps/web/src/screens/trade/PaidConfirmSheet.tsx:76` "After this you can't cancel the trade. If something goes wrong, open a dispute."
- `apps/web/src/screens/trade/ReleaseWarning.tsx:41` and `:46` "…and can't be taken back."

These are explanations, not refusals, so `// not-a-refusal: <why>` is the right marker. But `apps/web/test/cantDoThat-lint.test.ts` caps `notARefusal` at `<= 40`, and the main line already has exactly 40. The lead has to raise the cap to 43 with a reason, or the copy has to be reworded. `test/copy-lint.test.ts > passes on apps/web/src as committed` failed in the trial merge.

## Minor

- **M1** `apps/api/src/trades/routes.ts:137-148` + `machine.ts:568`: `confirm-cancel` asks the node again even after the server has recorded `cancelConfirmableAt`. If the node is briefly down when the seller taps, the count is null → 0 → `too-early`, and the screen (whose `ready` counts `cancelConfirmableAt`) shows the button enabled but says "doesn't have all its confirmations yet". Accept when `cancelConfirmableAt !== null` (the server's own earlier count).
- **M2** No node, no Task 9: `apps/api/src/main.ts:81` sets `txConfirmations` only when monerod is configured. Without it there is no watch, `confirm-cancel` is always `too-early`, and no 48 h clock starts, so the trade says "Cancelling" forever. Separately, no API timer loop exists (`timerEvents`/`startTimers` are not wired anywhere in apps/api), so the owner's 48 h auto-close never fires on this branch. It is documented as owed by Task 9. Track it as a landing dependency rather than calling it done.
- **M3** `apps/api/src/trades/cancelReturn.ts:39-41`: the select has no bound, no index and no age limit. A refund tx the node never finds (dropped or reorged, null count) is polled every 60 s forever, and its trade stays "Cancelling" with no 48 h. Also, refunded `buyer-cancel` rows written before migration 116 have `cancel_confirmed_at` null, so they become "awaiting" and get the push. Backfill in 116 (`update trades set cancel_confirmed_at = closed_at where state='refunded' and settling='buyer-cancel'`), or limit the watch to recent rows. Push spam is otherwise fine: one `return-confirmed` per trade.
- **M4** `machine.ts:548-554`: `fund-started` is controlled by the seller. A modified client, or a seller who only scans the QR code, never records it, so "the seller can't cancel after Fund escrow" holds only through chain facts. A walk-away that races a just-broadcast funding tx (before the watcher sees it) closes the trade with coins in escrow. `escalate` from a closed state is the only way back, and only the seller is harmed (the buyer can't pay before `secured`). The buyer cannot spoof the event (wrong-party), so it cannot block a legitimate walk-away. Accept and document.
- **M5** `apps/web/src/ui/Sheet.tsx:66`: the `alertdialog` has no `aria-describedby`, so screen readers announce only the title and not the owner's warning text. Initial focus goes to the panel, not the safe action ("I'll wait" / "I'll check again"). Escape and the backdrop correctly map to the safe action.
- **M6** `apps/web/src/screens/trade/SellerConfirm.tsx:204`: when the box is ticked but the warning has not been acknowledged, the caption still says "Tick the box above to unlock this release button." It should name the warning, or reopen it from the caption.
- **M7** `apps/web/src/screens/trade/SellerCancelConfirm.tsx:109`: the auto-close time is a raw `toISOString()` slice in UTC, not in the user's locale (COPY-UNSIGNED). The owner asked for a notification ("Your input is needed to cancel this trade."), but only the generic trade push is sent, and the line only shows once the button is ready.
- **M8** (open, flagged by the builder; the lead needs to decide): the owner's "a refund CAN be disputed if the amount refunded was wrong" is not built. The machine refuses any seller dispute on `refunded`, and the cancel refusal also blocks the buyer. Decide who can open it, the window, and the test.

## Checked and OK
- No path to any cancel in `paid` through the API (all four events, `paidAt` guard). `withdraw-cancel` has no `paidAt` check but can't fire, because `mark-paid` nulls the proposal.
- `walk-away` is seller-only: in `setup`; in `funding` only with no `fund-started`, `receivedAtomic` 0 and no `fundingSeenAt`; refused during maintenance. `fund-started` is accepted during maintenance (by design).
- 48 h: anchored at `cancelConfirmableAt` (`base` = pause during maintenance), `opens(...)` shift on resume, `onTick` guarded by `pausedAt`, and no double close (`cancelAutoCloseAt` → null once confirmed; `confirm-cancel` then `wrong-state`). `timerEvents` pauses awaiting trades. Restart safety is all in DB columns (but see M2: there is no loop).
- The watch: one pass at a time (`inFlight`), unref'd, stopped on `onClose`, 15 s node timeout per lookup, failures skip the row.
- The warnings: PayWarning sits in front of PaidConfirmSheet. The FinalAlert path (`refund_requested`, escrow secured) skips it by design. The release hold is disabled until acked, also on the `foreign` path. "Once per trade" is localStorage keyed by the room code, with a memory fallback. Another tab or another device shows it again (safe).
- Copy: the owner's buyer sentences are verbatim. The seller warning covers "really in your account / own bank or app, not a screenshot / can't be taken back". PaidConfirmSheet follows the board (the owner's question was left to Claude Design, as the plan says).
