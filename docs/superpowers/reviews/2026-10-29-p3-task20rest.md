## What I checked and found sound

- **No plaintext reaching the server or logs.** The page sends text to the escrow worker (serve.ts) and gets back verified plain lines. Keys, ciphertext and ChatState never cross postMessage. The API stores the envelope JSON only, and envelopes are padded to buckets (protocol envelope.ts), so the length of a line does not show. The chat routes log nothing. chat.test "never logs" checks the code and the ciphertext against the captured logs.
- **The server cannot forge a line or change who sent it.** routes.ts:322-347 stores `sender_role` from the session (`checkChatEnvelope(body, channel, role)` refuses a body `from` that differs: wrong-sender). engine.ts:197-200 shows a line only when the verified signer equals the server's `senderRole`. Participants come only from the attestation checked against the pinned key (engine.ts:169-179, `verifyAttestation(..., context: 'chat')`: exact channel set `{chat}`, no terms, own keys in own slot, trade = chat code).
- **The moderator badge outside a dispute.** A mod line needs (a) the attested mod identity's signature (minted in the moderation service, attest.ts `attestChat`, stored sealed with the chat code as AAD, keystore.ts), (b) server `senderRole = 'mod'`, which no API route writes (POST envelopes takes buyer/seller roles only), and (c) `disputeOpen`. A compromised API can lie about (c) but cannot forge (a). This matches spec 6.6 ("a rule enforced by the system plus the log").
- **Replays and duplicates.** Server side: unique (chat, sender_role, seq) plus the `stale-seq` check under the chat row lock (routes.ts:335-345). Client side: a ReplayGuard per sender, strictly increasing, saved after every envelope. seq is saved after sealing and BEFORE posting (engine.ts:272-273). A `stale-seq` reply re-syncs and re-seals once. The test "after losing the device state…" covers seq reuse.
- **Cross-trade and cross-chat leaks, 404 vs 409.** Every `/v1/chats/:chat*` route runs `roleInChat` first: a malformed code, an unknown chat and someone else's chat all give the same 404. Only then do `chat-not-ready`, `identity-*`, `attestation-refused`, `stale-seq` and `chat-unavailable` follow. `POST /v1/trades/:code/chat` gives 404 to anyone who is not the trade's buyer or seller before it can give 409 `chat-unavailable`. `POST /v1/chats` gives 404 for an unlisted offer or a malformed id. The live event carries the chat code only and goes only to the two traders.
- **Moderation (key separation).** The chat identity proof uses its own domain (`x2f/chat-identity/v1`). The moderation service re-checks both proofs and refuses a trade-domain proof (moderation chat.test). It mints the mod identity itself, so the API never chooses who reads. The attestation and the sealed identity are committed in one transaction before posting, and a restart re-posts the same attestation. The internal route accepts it only when signed by MOD_SIGNING_PUBLIC, with channels exactly `{chat}`, no terms, and exactly the two registered trader keys. The chat engine shares the escrow worker, but generateIdentity is reached only through worker.ts (separation check).
- **Fixtures out of the production bundle.** worker.ts names `import.meta.env.VITE_MOD_SIGNING_PUBLIC` only, never the env object, and no chat module imports fixtures (grep). bundle.test is in the web run.
- **Device binding.** ensureIdentity saves the identity before registering it, re-reads after an `identity-exists` race, and makes another device read-only. The IndexedDB store `x2f-chat` is separate from the escrow store, AES-GCM wrapped under a non-extractable key, with the chat code as AAD.

## Important

### I1. The quote's Chat button opens a pre-trade chat that can never become usable

`apps/web/src/screens/quote/Quote.tsx:246-253` + `:366-368`; `apps/api/src/chat/routes.ts:210-245`; `apps/api/src/internal/routes.ts` chat-work (needs both identities).

The taker taps Chat. `POST /v1/chats` creates the chat and the taker's device registers its identity. The moderation service attests only once BOTH traders have registered. The poster registers only by opening this chat in a ChatPanel, but nothing in the web app lists or opens a pre-trade chat for the poster. `GET /v1/chats` has no caller. No live event or push tells the poster, because the taker cannot post (409 `chat-not-ready`) until the attestation exists. Nothing in Plans 3-7 or the spec adds a chats inbox (grep).

Failure scenario: a buyer taps Chat on a seller's offer to ask "is Zelle OK?". They get "Securing this chat…" forever, re-polled every 3 s while the sheet is open (CHAT_POLL_MS.waiting), and the seller never knows. Spec 2 ("A user may open free pre-trade chats…") is not met. The button used to be honestly disabled; now it looks broken. The chat row is purged after 7 idle days.

Fix (pick one, lead's call): (a) keep the quote's Chat button disabled ("Chat opens once the trade starts") until a chats entry point exists, and record the inbox as owed (Plan 3 follow-up or Plan 5). (b) Build the minimal entry point now: a `{type:'chat'}`-style live event plus push to the poster when a chat is opened on their offer, and a chats list (GET /v1/chats is already there) that opens OfferChatPanel by chat code. The trade chat is not affected: both parties reach it from the room, once Task 23's seam installs it, or today through `/trade/<code>#chat`.

## Minor

- **M1. Gap detection misses a sender's first message(s).** `engine.ts:209`: `gapBefore` needs a previous seq (`prev !== undefined`). A server that drops a counterparty's seq 0..k-1 serves seq k with no "A message is missing here." line. Senders start at 0 (`newChatState` nextSeq 0), so treat "first seen seq > 0" as a gap: `prev ?? -1`. (The seq-from-guard rule can start a re-installed sender above 0, but that device is read-only, so it never seals.)
- **M2. The server sets the order of lines from different senders.** `engine.ts:127` sorts by the server's envelope id, and nothing inside a sealed message ties it to the other side's lines (no "last seen seq" of the peer). A compromised API can show the two traders different interleavings, for example moving the buyer's "No" from after one seller question to after another, and it can choose the `at` time shown. Within one sender, seq order holds: a swap drops the older line as a replay and shows the gap. Record this as a known limit of the moderator's evidence, or carry the sender's last-seen peer seq in the payload in a later protocol version.
- **M3. ChatPanel accessibility.**
  (a) `ChatPanel.tsx:168-178`: while sending, the focused textarea (or the Send button) becomes `disabled`, so the browser drops focus to `<body>` and nothing puts it back. A keyboard or screen-reader user loses their place after every message. Keep the textarea enabled (use `aria-disabled` / readOnly while sending) and refocus it after a send.
  (b) `:123`: `aria-live="polite"` on the whole `<ol>`. The first render after "Opening the chat…" announces the whole history, and every line the user sends is read back to them. Announce only new lines from others (a separate visually-hidden live region with the last incoming line).
  (c) `:135-138`: the speaker and the text are adjacent spans with no separator, so a screen reader reads "Samhello". Add a visually-hidden ": " or structure each line as "Sam said: …".
  (d) `chat.css` `.x2f-chat__lines`: the scrolling region has no `tabindex="0"`/role/label, so older browsers give keyboard users no way to scroll it, and nothing scrolls to the newest line.
  (e) `.x2f-chat__hidden` lacks `clip`/`white-space: nowrap`/`margin:-1px` (the full visually-hidden pattern); "Opening the chat…" and "Securing this chat…" are not in a status region.
- **M4. Retention (owner decision 2026-10-29), where chat storage must follow.** Not required in this task; flagged so the retention change covers chat:
  (a) `packages/trade/src/chat.ts:22` `CHAT_AFTER_CLOSE_DAYS = 90` after close, and `chatPurgeDue` never deletes while disputed. The new rule is 30 days for undisputed trades and 90 days from the dispute button for disputed ones. That needs a `disputedAt` fact (from the disputes table, migration 110 reserved) in `ChatRetentionFacts` and `purgeChats`' query (`chat/retention.ts:33-37`). `ChatPurgeRule` is already pluggable, which is good.
  (b) `106_chat.sql:17`: `chats.trade_code references trades (code)` with no ON DELETE. If the new rule deletes trade rows, the delete fails while a chat points at the trade. Purge the chat first in the same job, or use `on delete cascade`.
  (c) The device copy: `chat/store.ts` keeps every opened line as plaintext (inside the AES-GCM record) in IndexedDB `x2f-chat` forever. `ChatStore.delete` has no caller. A purged chat answers 404 and the panel says "no longer available", but the device keeps the text. Self-destruct needs the engine to delete the record on 404 (and on logout, see M6).
  (d) Pre-trade chats (7 idle days) are untouched by the owner's decision, as far as I know.
- **M5. Landing with Task 4's minors.** `chat/routes.ts:254,269` call `traderSummaries(deps.db, ids, now)`. Task 4's ed27ad3 makes `viewerId` required, so presence honours blocks via `lastSeenSql`, and tsc will flag both calls. Pass `req.auth.accountId`. Note that ChatView's `counterparty` carries `online`/`lastSeenAt`, and Task 4's M3 note says presence must go through the viewer-aware summary.
- **M6. Chat records survive logout and account switches.** IndexedDB `x2f-chat` is per origin, not per account. After logout, the secret chat identities and the plaintext lines of every chat stay on the device. The escrow store has the same property, so this may be a deliberate choice (the identity must survive a re-login, since there is no recovery). If so, write it down. If not, wipe on logout with a warning.
- **M7. No rate limit on chat writes.** `POST /v1/chats` and `POST /v1/chats/:chat/envelopes` (routes.ts:210,322) have no budget. With 16 KiB per envelope, a party can grow the database without bound and slow every reader's sync (M8, M10). A per-account bucket (for example 30 envelopes/min, 20 new chats/hour) belongs here or in Plan 6. Record which one.
- **M8. A sync reads at most 2000 envelopes and does not say so.** `engine.ts:108` (MAX_PAGES 20 × the API's page of 100). The loop stops silently with `more` still true. The next sync goes on from the saved cursor, so this only delays, except in M10's case. Consider a `more` flag in the snapshot ("loading earlier messages").
- **M9. Opening any chat boots the escrow runtime.** `escrow/worker.ts`'s `serveEscrow` calls `makeRuntime` at worker start, so the quote's Chat sheet (no trade at all) loads monero-ts in the worker. The author flagged this. It costs memory on phones. Make the runtime lazy (on the first escrow message) when convenient.

- **M10. A held moderator line pins the read cursor (matters once moderator posting lands).** `engine.ts:213-220`: an envelope refused with `mod-not-allowed` (or `bad-message`) leaves `cursor` before it. Every later sync re-reads from that point, up to 2000 envelopes, and `store.save` re-encrypts the whole record for every envelope, skipped ones included (`:221-222`). A trader's `bad-message` unpins on its own: the sender's next accepted line makes the held one a replay, which is skipped (I checked this with a local test, below). A mod line held after a dispute has ENDED never unpins. Scenario for the plan that adds moderator posting: the moderator writes the ruling's explanation during the dispute, and the buyer first opens the chat after the trade is released (`disputeOpen` false). That line is never shown on the buyer's device, every sync re-reads from it, and after 2000 more envelopes nothing new loads. Fix there: keep held ids in a retry list instead of pinning the cursor, and decide whether a mod line signed during a dispute shows after it ends (it probably should: carry the dispute window, or let the server mark mod envelopes posted while disputed). Save once per page.
  Local check (my worktree, not committed): one authentic seller envelope with an extra payload key (`bad-message`), then 45 lines. The first sync keeps cursor '0'. The next sync skips the held one as a replay and moves the cursor to 40. So there is no permanent stall from a trader.
