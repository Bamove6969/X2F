Passes: name rules are ASCII-only (`username.ts:42`, 5–20 code points, raw input over 64 units refused first), so there is no Unicode, confusable or whitespace normalisation to collide on; keys are `toLowerCase()` of ASCII (locale-free); display and login keys are each unique at DB level (`accounts_display_key_key`, `accounts_login_key_key`), the pair constraint and the per-row names-differ check are in 009, and a taken login name is reported only by the credential-bound create as the generic `names-unavailable` (`accounts.ts:93`). Password login (focus 2): every failure is 401 `credentials-invalid` `{ misses }`, exactly one Argon2 verify on every path (real hash, DUMMY_HASH for unknown, staff, no-password and quiet-locked), the try is claimed atomically before checking (`claimPasswordTry`, at most 10 checks per streak, consistent with R28's "a parallel burst gets exactly N"), the lock alert runs the same `update` + `insert … where $5` for no account, and the only 429/503 on the route is the name-independent global budget or Argon2 slot. ## Important
1. `migrations/009_login_names.sql:12-17`, `accounts.ts:42-45`: a login name can equal another account's public display name, in both directions, so a private login name ends up printed on the site. Uniqueness is per column only and names-differ is per row. Trigger A: Alice has display name `mira.k`; Bob signs up with display `bob.trades`, login `mira.k`: `checkNames` passes (it only compares Bob's own two names), `assertDisplayNameFree` only reads `display_key`, and the insert hits no constraint. Every one of Alice's offers now shows Bob's login name, and a sprayer working through scraped display names gets 10 password tries per 15 minutes on Bob's account (residual (d)). Trigger B: Bob already has login `night.owl`; Carol picks display name `night.owl`, which is accepted. That defeats spec 6.1 ("so nobody can target an account they see on the site"). Fix: (a) refuse a new login name whose key equals any existing `display_key`. Display names are public, so this check leaks nothing and can be a cheap 400 (`login-name-invalid`, or a new `login-name-public`). (b) Refuse a new display name whose key equals an existing `login_key`, but only in the credential-bound create, answered with the generic `names-unavailable`. That is the same cost as the accepted residual (b). (c) Make it race-proof at DB level with one `account_names(key text primary key, account_id, kind)` table holding both keys (or a trigger). (d) Record that FU-D must keep this check when it moves login names to tags, for example by also tagging display keys under the login-name ring for the comparison. Tests: both triggers.
2. `auth/webauthn.ts:488-496` (security-key login by name): the options still reveal whether a login name exists. A real account's `allowCredentials` lists all of its security keys, at whatever length each authenticator chose. An unknown name always gets 1 or 2 decoys of exactly 64 bytes. Trigger: an account with 3 security keys (spec 6.2: "Several keys can be registered"). `POST /v1/login/webauthn/start { loginName: 'guess' }` returns 3 entries, which no unknown name ever produces, so the guess is confirmed. The same happens for any authenticator whose credential ID is not 64 bytes. The `M3` test (`webauthn.test.ts:706-722`) only checks the decoy length and the query count. This was the accepted P2-I7/M3 shape when the name was public. Now the name is the secret, and FU-A's security note (`plan-2-review.md:176-185`) neither fixes it nor lists it as a residual. Fix: cap security keys per account at N (say 4). Always return exactly N entries, padding real accounts with per-name HMAC decoys. Draw each decoy's length deterministically from the lengths actually stored (or a fixed set such as 16/32/48/64/80). Add a test comparing the entry count and length multiset for a 3-key account and an unknown name. If the owner prefers to accept it, add it to the "Accepted residuals" list explicitly.
3. `docs/coordination.md:63` and `migrations/009_login_names.sql:4-6` (focus 6): the pre-009 gap is a silent permanent lockout, not just "no backup-code recovery", and the planned route cannot help those accounts. ## Lead decisions (2026-10-27, applied on `wip/lead-p2-fua`)
