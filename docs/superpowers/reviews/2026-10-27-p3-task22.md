## Important

1. **TradeFund.tsx:231-234 and 275-279, FundFallback.tsx:48 and 56: after a short payment the QR code, "Copy amount" and "Send exactly this amount" still give the full `sellerFundsAtomic`, right under "Received X of Y XMR, send the rest".**
   - Trigger: the seller's wallet rounds 1.2625 down to 1.26, or the seller types 1.0. The API reports `receivedAtomic` 1.0 of 1.25. The hold is locked (opened mark), so the seller scans the QR, which still carries `tx_amount=1.25`. The escrow ends up with 2.25 XMR. By spec 11.1 and `amountForFunds` the trade grows to the funded amount (or, above the offer maximum, the extra returns at the end). The seller has now sold about twice what they meant to, and the buyer is asked to pay roughly double or cancel.
   - Fix: while `0 < received < funds`, build the link, QR and copy amount for the remainder. Take that remainder from the device's own escrow reading: add the balance Task 12 already reads via `funds()` to `TradeEscrow`, next to `escrowAddress`. Until the device has that reading, do not show a full-amount QR or copy. Show the address and "Send the rest: X XMR", with X computed only for display.
   - Test: short funding shows no `tx_amount=<full>` anywhere, and "Copy amount" copies the remainder.
2. **TradeFund.tsx:170-176 with HoldButton.tsx:71-76: on a phone, the wallet link is "clicked" from a `setTimeout` 1.5 s into a touch hold, where the browser has no user activation.**
   - In the HTML activation rules, `pointerdown` grants activation only for a mouse. For touch, activation comes on `pointerup`/`touchend`, and those have not happened while the finger is still down.
   - Browsers require user activation to open an external app. Chrome reports "Not allowed to launch '…' because a user gesture is required". Android Chrome blocks intent navigations without a gesture.
   - The e2e `hold()` uses `page.mouse` (fund.spec.ts:158-165), where `pointerdown` does count, so the tests cannot see this. The wallet link exists only on Android and iOS, which are exactly the touch platforms affected.
   - Trigger: on an Android or iPhone, hold "Open in Cake Wallet". The opened mark is set and the button locks to "Waiting for your payment…", but the wallet may never open. The seller has to fall back to the QR code.
   - Fix: make the user's release perform the navigation. When the hold time is reached, show "Release to open" and call `link.click()` synchronously inside the `pointerup` handler. Or make the real `<a href>` the hold target and `preventDefault()` its native click unless the hold time was reached (with `-webkit-touch-callout: none` and the context menu suppressed).
   - Also add the hold path on Android to the manual check (see focus 6 below).
3. **SetupStatus.tsx:41-67: a non-retryable, non-integrity escrow error is shown as endless "Setting up escrow" and "Keep this page open until the escrow is ready".**
   - The affected errors are `unsupported-browser`, `not-confirmed`, and `escrow-failed` with `retryable: false`. They never show the retry block (`retryable` is false) and never show the danger screen (seams.ts:72). The unit test pins this behaviour (tradeFund.test.tsx:304, "an unsupported browser … only setup progress").
   - Trigger: a seller on a browser without Web Locks waits on "Setting up escrow" for the whole 30-minute funding window, and the trade lapses. Task 12 says errors and refusals are shown, never silent.
   - Fix: give each error code its own sentence. `unsupported-browser`: "This browser can't run the escrow. Open the trade in an up-to-date browser." `not-confirmed`: "Open this trade from the device you started it on." Non-retryable `escrow-failed`: the cancel path. Drop the keep-open bar whenever `error !== null`, and update the test.
4. **TradeRoom.tsx:177-179 and seams.ts:24-29: the room's trade start depends on `location.state.confirmed`. Nothing provides it, and no tripwire watches for it.**
   - Task 12 fails with `not-confirmed` on the first start without it (wip/lead-p3-task12-fixes runtime.ts:405-406).
   - Neither built caller passes it: Task 18 (`wip/lead-p3-task18` useTake.tsx:50) and Task 19 (`wip/lead-p3-task19` App.tsx:76) both navigate to `/trade/${code}` with no state.
   - Trigger: Tasks 12, 18, 19 and 22 are merged as they stand. Every new trade stops at `not-confirmed`, which item 3 shows as endless setup. No escrow is created and nothing can be funded.
   - Fix:
     - Type `ConfirmedTrade` as Task 12's interface (`{ role, ownAddress, deal }`) in the seam, not `unknown`.
     - Add a tripwire that fails while useTake.tsx or the accepted sheet navigates to `/trade/` without `state: { confirmed }`.
     - Add a coordination note for Tasks 18 and 19.
     - Note that history state does not survive the user opening the trade from a push notification before the first start. Tasks 18 and 19 should start the escrow themselves (or persist `confirmed`) before navigating.
