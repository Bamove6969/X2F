## Important

1. **A system-escalated dispute has no `disputes` row, so the trader sees the wrong screen and can never appeal.** `escalate` (machine.ts:414-418, emitted by Task 9's timerLoop.ts:71, already on the main line) moves a trade to `disputed` with `dispute.by = 'system'`, but nothing inserts a `disputes` row. The schema cannot hold one either: `opened_by` is checked against `('buyer','seller')` (108_disputes.sql:11).
   - **Trigger:** late funds after `released`/`refunded`/`cancelled`, or a lapse nobody refunded.
     - `GET /v1/trades/:code/dispute` returns 404 (routes.ts:190).
     - `fetchDispute` maps that to `null` (api.ts:171-177).
     - DisputeScreen renders DisputeOpen (DisputeScreen.tsx:32-48) for a trade that is already in dispute. `disputeEntry` returns `opened` (rules.ts:52), so `allowed` is false (DisputeOpen.tsx:46-47) and the trader gets a dead, disabled "Open a dispute" form with no explanation.
     - There is no room, no moderator banner, and no ruling screen. `appeal` always refuses `wrong-state` because no row exists (routes.ts:235-237).
   - The same gap applies to a trade disputed and settled earlier that later escalates on late funds: the old row (status `closed`) is shown as if it were current.
   - **Fix (API):** let `opened_by` be `'system'` (reason `other` or a new `escalated`). Either have the escalate path insert the row through `applyEvent(..., within)` (Task 9's timer loop), or have GET synthesise an `open` view from `trade.dispute` when the state is `disputed` and no row exists.
   - **Fix (client):** in DisputeScreen, treat `trade.state === 'disputed' && dispute === null` as DisputeRoom ("In dispute", waiting for a moderator), never as DisputeOpen.
   - **Test:** apply `escalate` to a released trade with late funds, then GET → 200 with `openedBy: 'system'`, and the screen shows the room.

   - No test exists.
   - `disputes.code references trades (code)`, `dispute_rulings`→`disputes` and `dispute_appeals`→`disputes` (108:10, 29, 44) have no `on delete` clause. Any future trade deletion (the owner's 2026-10-27 self-delete and 90-day auto-delete) will fail on a disputed trade unless the purge deletes the dispute rows first, in order.
   - The ruling footer tells traders "This ruling and its evidence are kept with the trade." (rules.ts:207), which suggests permanence.
   - Plan 3 never writes `closed`, so today nothing is due for deletion. The cost of leaving it is the missing column and job, which is cheap now.
