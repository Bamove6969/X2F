# Plan 4: Disputes and staff tools — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner claims a fresh server with a one-time setup code and two hardware keys, invites staff with roles and login hours, and runs the site from a separate staff address. Moderators settle disputes through a queue, a case view and rulings, with two-person approval at or above the large-trade limit, an appeal window and an append-only, hash-chained activity log. Traders open disputes, see a moderator join, and receive and appeal rulings. Throughout, the moderator key signs only what an approved ruling, or the guarded auto-refund, allows.

**Architecture:**
- **`packages/staff` (`@x2f/staff`)** holds the pure rules that the API, the moderation process and the staff web app share: roles and permissions, login hours, key-tap intents, the dispute state machine, the anonymizer and the performance maths.
- **`apps/api`** gains a second Fastify instance, `buildStaffApi`. It listens on its own port and origin, with its own cookie. Plan 4 also adds the trader-side dispute routes to the existing trader API.
- **`apps/moderation`** is the only process that holds moderator keys. It has no public HTTP. Its **ruling gate** signs a ruling only after it has verified security-key approvals itself. It trusts those approvals through a chain rooted in the owner's two keys, which are pinned outside the database. Payouts go only to the addresses it recorded at escrow setup.
- **`apps/staff-web`** is the staff app, built in React and Vite from the canvas boards. The trader screens DisputeOpen, DisputeRoom and DisputeRuling are added to `apps/web`.

**Tech Stack:** Node 24.22.1, npm 11.21.0 (`npx -y npm@11.21.0`), TypeScript 7.0.2 strict, vitest 5.0.3, fastify 5.12.5, pg 8.23.1, @simplewebauthn/server 14.0.3, @simplewebauthn/browser 14.0.0, monero-ts 0.11.16, React 19.3.0, Vite 8.3.2, @playwright/test 1.63.0, Semgrep 1.178.0. **No new dependencies.** Every version above is already pinned by Plans 1–3 and was re-checked on 2026-10-15 with `npm view <pkg> time --json`; each was published on or before 2026-09-30. Charts are hand-written SVG. Time zones use `Intl`.

**Spec:** `docs/superpowers/specs/2026-10-14-x2f-design.md`: 2.3 (cancel, no-show auto-refund, dispute after refund, trading hold), 3.1, 3.3 (moderator key custody, two-moderator approval, auto-refund conditions), 6.5, 6.6 (all), 9. **Boards** (the source of truth for UI) are in Claude Design **X2F App**, mirrored in `design/x2f-app/`. ## Global Constraints

- **Non-custodial.** X2F holds at most one key per trade, the moderator's. The server never holds, relays for completion, or can obtain a second signature. On a ruling, the moderator builds the transaction and the *winning trader's app* completes and broadcasts it. Nothing in this plan adds a key.
- **The moderator key signs in only two ways:**
  - **(a)** A published ruling whose approvals the ruling gate has verified. Payouts go only to the addresses the moderation process recorded at escrow setup.
  - **(b)** Plan 1's `autoRefundDecision`, paying only the seller refund address recorded at setup.

  No route, setting or database row can add a third way.
- **Two-person rule.** A ruling on a trade whose USD value is **at or above** the large-trade limit needs two different people:
  - a proposer, who is the assigned moderator, senior moderator or owner;
  - an approver, who must be a senior moderator or the owner.

  Both prove themselves with a security-key tap bound to the ruling.
- **Activity log.** It is append-only and hash-chained. Database triggers refuse `UPDATE`, `DELETE` and `TRUNCATE`. Entries never contain chat text, ruling reasons, addresses or IP addresses.
- **Owner account.**
  - It cannot be switched off, demoted, given login hours or recovered by any message, code or password.
  - It always keeps two or more attested hardware keys and a PGP key, and every owner login needs an attested security key and the PGP key (owner, 2026-10-17; Plan 2 Task 10).
  - Anonymous login failures never block a security-key or PGP login (Plan 2 P2-C1 fix).
- **Staff sessions.**
  - Staff log in only with an attested security key or PGP. Anyone who rules or approves must have a security key.
  - Sessions last 30 min idle and 12 h absolute (Plan 2 `sessionPolicy`).
  - Outside their login hours, staff cannot log in, and an open session ends when the window closes.
- **Least privilege.** Every staff route declares one `Perm`. The privilege-matrix test (Task 4) calls every route with every role, and a route without a declared `Perm` fails the build.
- **No client-sent system events.** Traders may send only `appeal` and `open-dispute` (plus Plan 3's whitelist). Moderator-joined, rulings, holds and execution events are written only by staff routes or the moderation process.
- Every dependency is pinned exactly and was published at least 14 days before 2026-10-15. `npm audit` reports 0 vulnerabilities, using the same scope as Plans 2 and 3.
- `npm run check` (typecheck, tests, audit, Semgrep 1.178.0, copy lint) passes at the end of every task.
- Migrations are numbered `2xx`, and each task adds its own.
- Server clock only: every module takes `clock: () => Date`.
- Logs never contain trade codes, invite tokens, setup codes or request bodies. Request logging stays off.
- **UI.** Copy comes verbatim from the boards. Where no board exists, the wording comes from the spec.
  - Violet `#b69cff` appears only on the X2F Moderator badge and on staff role chips.
  - Exactly one `data-primary` per screen.
  - `expectParity` at the board's size; trader screens at 390×844.
  - Never run Playwright with `--update-snapshots`.
- Code from agy-delegated agents is merged only after Semgrep, the Security Guidance hook and a code-review plugin have checked it.

## Review Focus

1. **Login windows that cross midnight or a daylight-saving change.**
   - Windows: `Fri 22:00–02:00 America/New_York` and `Mon–Fri 09:00–17:00 Europe/Berlin` across both 2027 changes.
   - Expected: login is allowed and the session ends at the local wall-clock end; a Saturday 01:30 login under the Friday window is allowed.
   - Test owned by Task 1.
2. **A trade worth exactly the limit, or a EUR trade whose USD value moves after setup.**
   - Rule: the limit is applied to the USD snapshot recorded at escrow setup, and exactly 1,000.00 USD needs two approvals.
   - The gate uses its own snapshot even if the database says 999.99.
   - Tests owned by Tasks 12 and 13.
3. **Appeals at the edge.**
   - Both traders appeal at the same moment: exactly one appeal is stored.
   - An appeal at `appealEndsAt` exactly is refused.
   - The payout never fires while an appeal exists, even if the API hides it from the gate for less than the window.
   - Tests owned by Tasks 2, 12 and 14.
4. **The winning trader is offline when the window closes.**
   - The moderator's half-signed release waits; the dispute shows "Waiting for <name> to open X2F"; the winner's app completes it on next open.
   - Exactly one transaction is broadcast.
   - Test owned by Task 21.
5. **Anonymizer misses.**
   - Cases: a username in another case or split by zero-width characters; an address broken across a line; a payer's real name in free text.
   - Expected: automatic masks catch the first two, and the owner reviews and adds masks before saving. Nothing is saved without that review.
   - Tests owned by Task 19.

  - `applyDispute(d: Dispute, e: DisputeEvent, by: Actor, now: Date, s: { appealWindowH: number }): Dispute`. It is pure and throws `DisputeRuleError` with code `'wrong-state' | 'wrong-party' | 'too-late' | 'same-person' | 'not-eligible'`.

Rules the tests pin (one test each):
- **Assign.** `assign` is done by staff with `disputes.handle`. It is allowed only when unassigned; a senior or the owner may also take over an assigned case. A trader or system actor gets `wrong-party`.
- **Reply.** `reply` sets `firstReplyAt` the first time only.
- **Propose.** `propose` is done by the assignee only, in `open` (round 1) or `appealed` (round 2).
  - In round 2 the proposer must be in `appealReviewers(...).ids`; otherwise `not-eligible`.
  - When `needsSecond`, the status becomes `awaiting-approval`.
  - Otherwise round 1 becomes `published` with `appealEndsAt = now + appealWindowH`, and round 2 becomes `final`.
- **Approve.**
  - Allowed only in `awaiting-approval`, by a senior or the owner.
  - Approving your own proposal gives `same-person`.
  - In round 2, anyone who proposed or approved round 1 gives `not-eligible`, unless A4's fallback applies.
- **Send back.** `send-back` (the approver declines) returns the case to `open` or `appealed` and clears `ruling`.
- **Appeal.**
  - Allowed only from a trader, only in `published`, and only while `now < appealEndsAt`. At `appealEndsAt` exactly: `too-late`.
  - A second `appeal` gives `wrong-state`.
- **Window closed.** `window-closed` comes from the system only, and only when `now ≥ appealEndsAt` and the status is `published`. It moves to `final`.
- **Final, escrow case.** `final` + `executed` (system) → `closed`.
- **Final, after-refund case.**
  - `seller-sends-xmr` moves to `complying`, with `complyBy = now + COMPLY_H`, and `complied` (system) → `closed`.
  - The other outcomes go → `closed`.
