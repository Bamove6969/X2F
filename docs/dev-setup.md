# Dev setup

- **Node 24.22.1** (Active LTS) via nvm (`nvm install` reads `.nvmrc`; on this machine it lives at `~/.nvm/versions/node/v24.22.1`). `tools/check.sh` uses the PATH node if it is v24.x, else the nvm path, and fails clearly otherwise. Node 22 is in maintenance only and Node 20 is end of life.
- **Install dependencies** with `npx -y npm@11.21.0 install --save-exact` (older npm crashes on the vitest 5 peer set). `package-lock.json` is generated by this npm.
- **Semgrep 1.178.0** in `~/.local/semgrep-venv`. On a system with `python3-venv` installed: `python3 -m venv ~/.local/semgrep-venv && ~/.local/semgrep-venv/bin/pip install semgrep==1.178.0`. Without it (fresh Linux Mint 22.3), either run `sudo apt install python3-venv` first (preferred) or create the venv with `--without-pip` and bootstrap pip. Semgrep scans only git-tracked files: `git add` new files before `npm run check`.
- Run everything with `npm run check` (typecheck, tests, `npm audit --omit=dev`, Semgrep).
- Keep `apps/.gitkeep` until `apps/relay` exists (Semgrep errors on empty scan roots).
- **Docker** for the API tests (`npm test -- --project @x2f/api`). The vitest global setup starts one throwaway PostgreSQL 17.11 container per run (data on tmpfs, port bound to 127.0.0.1 only, random password), migrates a `x2f_template` database and gives each test file its own copy; the container is stopped afterwards. Each container is labelled `x2f-api-test=<pid of the test run>`; the next run stops any labelled container whose run is no longer alive (left behind by a killed run), and `docker ps --filter label=x2f-api-test` lists them. Image, pinned by digest: `postgres:17.11-alpine3.24@sha256:b0f9560a2de083e2cc7382e75f808c7381a32852a7ec49117deedb300e552b24`. Without a running Docker daemon the API tests fail with "api tests need Docker"; they never skip. If `docker info` says the daemon is not running, start it (`sudo systemctl start docker`, or `dockerd` in a container).
- **Regtest monerod** (`tools/regtest`, used by the regtest and escrow tests): the vitest global setup runs `tools/regtest/fetch-monerod.sh`, which installs monerod v0.18.5.3 into `.regtest/bin/` (needs `curl`, `gpg`, `bzip2`). It picks the official build by `uname -m`: `x86_64` gets `monero-linux-x64-v0.18.5.3.tar.bz2` (in `.regtest/bin/monero-x86_64-linux-gnu-v0.18.5.3/`), `aarch64` (arm64 Linux, e.g. the Debian-on-Android machine) gets `monero-linux-armv8-v0.18.5.3.tar.bz2` (in `.regtest/bin/monero-aarch64-linux-gnu-v0.18.5.3/`); anything else fails. Both go through the same checks: binaryFate's key must have fingerprint `81AC591FE9C4B65C5806AFC3F0AF4D462A0BDF92`, the `hashes.txt` pinned at monero-site commit `141bec8` must carry his good signature, the tarball must match both its pinned SHA-256 and the line in that signed file, and the extracted monerod must match its pinned SHA-256. `tools/regtest/regtest.ts` picks the same directory by `process.arch` (`x64` or `arm64`). Moving to a new Monero version means re-pinning all four hashes for both CPUs from one signed `hashes.txt`.
- **Migrations**: `DATABASE_URL=postgres://... npm run migrate -w @x2f/api` applies `apps/api/migrations/NNN_*.sql` in order (one transaction each, recorded in `schema_migrations`). It needs only `DATABASE_URL`.
- **API settings** (`apps/api/src/config.ts`): `X2F_ORIGINS`, `X2F_RP_ID`, `DATABASE_URL`, `X2F_LEAKED_LIST_PATH`, `X2F_SERVER_KEY` (base64 of 32 random bytes), `X2F_MONERO_NETWORK`, `X2F_TERMS_VERSION` (≤ 32 characters; must equal the web app's `TERMS_TEXT_VERSION` in `apps/web/src/screens/setup/termsText.ts`, else sign-up shows "Reload the page" forever), `X2F_PGP_SIGNING_KEY_PATH` (the official X2F PGP key, unencrypted armored private key, `chmod 600`, owned by the API's user; the API refuses to start otherwise), `X2F_PGP_SIGNING_FINGERPRINT` (lower-case hex, 40 or 64 characters), `X2F_PASSWORD_PEPPERS`, `X2F_RECOVERY_CODE_KEYS`, `X2F_TOTP_KEYS` and `X2F_LOGIN_NAME_KEYS` (key rings, see below); optional `X2F_SITE_NAME` (default `X2F`), `X2F_ATTESTATION_DIR` (default `apps/api/data/fido-mds`), `X2F_HOST` (default `127.0.0.1`), `X2F_PORT` (default `8080`). Start with `npm start -w @x2f/api`.
- **Stored-secret key rings** (FU-C, owner decision 2026-10-23; ASVS 2.4.5, 2.6.2, 2.8.2; FU-D, owner 2026-10-25). Four secrets, each separate from `X2F_SERVER_KEY` and from each other (the API refuses to start if any key is shared): `X2F_PASSWORD_PEPPERS` (the pepper: passwords are stored as Argon2id of HMAC-SHA-256(pepper, NFC password)), `X2F_RECOVERY_CODE_KEYS` (recovery codes are stored as HMAC-SHA-256 under this key, bound to the account), `X2F_TOTP_KEYS` (the file/env key store that seals TOTP secrets with AES-256-GCM; an HSM or KMS replaces it in Plan 6) and `X2F_LOGIN_NAME_KEYS` (the private login name is stored only as `accounts.login_tag` = HMAC-SHA-256 under this key of `x2f/login-name\0` + the lower-cased NFC name, so a stolen database holds no login names once Migration 012 step 1 below, including its `ANALYZE accounts, name_keys; VACUUM FULL accounts, name_keys, pg_statistic; CHECKPOINT;` as a database superuser, has run and every older backup is gone; a sign-up waiting in its challenge keeps the login name sealed under a key derived from `X2F_SERVER_KEY`). Each is `<id>:<base64 of 32 random bytes>[,<id>:<base64>...]`, ids 1–32767, **newest first**: the first entry is used for everything new, the others only to check or open older stored values. Instead of the variable, `<NAME>_FILE` may name a file holding the same text (a regular file, `chmod 600`, owned by the API's user), never both. Make a key with `node -e "console.log('1:' + require('crypto').randomBytes(32).toString('base64'))"`. They are secrets: never log them, never commit them; config errors name the variable only.
  - **Migration 009 (login names, FU-A).** Stop the API, run the migration, start it again: it renames `accounts.username` to `display_name` (and `username_key` to `display_key`) and adds `login_name`, `login_key` and `legacy_login_name`, so an API from before FU-A fails every sign-up, login, `me`, nudge and trade view on the new schema and one with FU-A fails the same way on the old one. There is no rolling path. Existing accounts keep logging in by their old name (`login_name = display_name`, `legacy_login_name = true`) until each sets a private login name (`POST /v1/account/login-name`; `GET /v1/account/me` says `needsLoginName: true` until then).
  - **Migration 011 (from Plan 2 data).** Stop the API before running migration 011 and start it again afterwards (no rolling deploy: an API without FU-C cannot read the marked TOTP secrets, and one with FU-C needs the new columns). Old password hashes have `passwords.pepper_id` null: still accepted, and rehashed under the current pepper at the next successful password login or confirm (`updated_at` unchanged). Old recovery codes have `recovery_codes.key_id` null: they are plain SHA-256 and cannot be converted (only the hash is kept), so they keep working, one use per code, until used up or until the person regenerates the set. Old TOTP secrets are marked format 0 (sealed under `X2F_SERVER_KEY`): they still open; run `npm run rewrap-totp -w @x2f/api` once after migrating (full API settings needed; prints `{"rewrapped":n,"failed":n}`) to move them to `X2F_TOTP_KEYS`. TOTP enrolments open at migration time are ended (they last 5 minutes). Progress: `select count(*) from passwords where pepper_id is null`, `select count(distinct account_id) from recovery_codes where key_id is null`, `select count(*) from totp where get_byte(secret_enc, 0) = 0`.
  - **Migration 012 (FU-D, login names as tags), step 1.** SQL has no key, so the app tags the existing rows. Stop the API, run the migrations, run `npm run tag-login-names -w @x2f/api` once (full API settings needed; it tags every row that still holds `login_key` under the current `X2F_LOGIN_NAME_KEYS` key and nulls `login_name` / `login_key` in the same update, which also drops the plaintext `login` entries from `name_keys`; prints `{"tagged":n}`, a re-run prints `{"tagged":0}`), then run `ANALYZE accounts, name_keys; VACUUM FULL accounts, name_keys, pg_statistic; CHECKPOINT;` as a database superuser (`pg_statistic` belongs to the bootstrap superuser; FU-D review I2 and round-2 N1: the update leaves the old plaintext values in dead tuples and in the pages of `accounts_login_key_key` and `name_keys_pkey`, which plain or auto VACUUM does not zero, and once the tables have been analysed `pg_statistic` (`pg_stats`) holds up to 100 sampled login names per column; `ANALYZE` replaces those samples, leaving the old ones as dead tuples, and `VACUUM FULL` rewrites both tables, all their indexes and `pg_statistic`), then start the API. Every `pg_dump`, base backup and WAL archive taken before that point still holds the login names in clear: destroy it, or keep it as sealed as the key ring. The same goes for the data volume of a deployment that held real rows (and its snapshots, and each standby's): its `pg_wal` holds the names until those segments are overwritten, and the disk blocks of the old table files are freed, not wiped, so treat it like the older backups: encrypted at rest, or retired. A pre-009 account (`legacy_login_name`) is tagged under its display name and keeps logging in by it until it sets a private login name. The API refuses to start while any row still holds a plaintext login name (`select count(*) from accounts where login_key is not null`). The migration also ends sign-ups waiting in a challenge (their payload held the login name in plaintext). Before launch there should be no rows to tag. **Step 2** (a later migration, once that count is 0 on every deployment): drop `accounts.login_name` and `accounts.login_key` with their constraints, and `name_keys` with its trigger.
  - **`X2F_LEGACY_SECRETS`** (`on` by default, or `off`): with `off` the API refuses every pre-FU-C value: a password hash with `pepper_id` null fails like a wrong password (still one Argon2 verify), a recovery code with `key_id` null never matches, and a format-0 TOTP secret fails closed (and is no longer rewrapped). Set it to `off` once all three counts above are 0. Before launch there should be none.
  - **Rotation.** Put the new key first with a new id and keep the old one after it. `X2F_TOTP_KEYS`: restart, run `npm run rewrap-totp -w @x2f/api`, and run it again: drop the old key only after a re-run reports `{"rewrapped":0,"failed":0}` and `select count(*) from totp where substring(secret_enc from 1 for 3) <> '\x01'::bytea || int2send(<current id>::smallint)` (blobs not under the current key) is 0. A `failed` count above 0 means a secret that does not open (investigate it; the person can enrol TOTP again) and is not fixed by waiting. `X2F_PASSWORD_PEPPERS`: each password moves to the new pepper at its owner's next login; a password still under a pepper that has been removed can no longer log in (check `select pepper_id, count(*) from passwords group by 1` before removing one). `X2F_RECOVERY_CODE_KEYS`: new sets use the new key; removing an old key invalidates the unused codes made under it (check `select key_id, count(*) from recovery_codes where used_at is null group by 1`). `X2F_LOGIN_NAME_KEYS`: logins look a name up under every key in the ring; each account moves to the new key at its owner's next successful login by name (password, security key by name, backup code), and new accounts and newly set login names use it at once. There is no rewrap tool (only the tag is stored, never the name), so an account still under a removed key can no longer log in by name (PGP and discoverable passkeys still work); check `select login_tag_key_id, count(*) from accounts where login_tag is not null group by 1` before removing one. Removing a key also frees every name still tagged only under it, in both namespaces (FU-D review M3): sign-ups check names only under the keys still in the ring, so a stranded account's private login name can then be taken by someone else as a login name, or shown on the site as someone's display name. Before removing a key, contact or close the accounts still under it (or set `legacy_login_name` for them so they choose a new login name). Every API process must hold the same keys during a change (new key second, then first after all have restarted): sign-ups check the name under every key in their ring.
- **`X2F_TRADE_PURGE`** (`off` by default, or `on`; Plan 7 Task 2): whether the whole-trade self-destruct deletes anything. The `purgeTrades` retention job is always registered; with `off` it deletes nothing and reports 0 rows. Keep it `off` in production until the revenue ledger (Plan 4 Task 32), the daily statistics (Plan 7 Task 14) and Plan 5's reviews, proofs and running totals record a trade before it is deleted (tripwires in `apps/api/test/tradePurge-tripwires.test.ts`); the default changes to `on` only then. Any other value stops the API at start-up with an error naming the variable. Outside tests, `on` also stops the API at start-up until `TRADE_PURGE_READY` in `apps/api/src/config.ts` is true (review R2-m1); it stays false until every item below has landed. Tests run with it on (`testConfig`). While it is `off` the trade view's `deleteAt` is null (no self-destruct date in the room) and Settings → Privacy (`GET /v1/privacy`) says trades are kept. The flag is process-global (`setTradePurge` in main.ts) and only the `purgeTrades` job reads it: a CLI or tool calling `purgeTrades` directly would bypass it (nothing does; add none before `on` is allowed). No purge pass runs during site maintenance, and the trade view's `deleteAt` is null then. **MUST LAND BEFORE `on`** (docs/coordination.md, Plan 7 section; tripwires in `apps/api/test/tradePurge-tripwires.test.ts`): the revenue ledger and daily stats; Plan 5's running totals and lost-dispute record, reviews and proofs; the moderation watch's drop of a closed escrow (or `WATCH_CLOSED_DAYS` plus a margin) with a loud staff error for late funds on an unknown trade; **never purging unless the escrow is shown empty (unknown = may hold coins, so the trade is kept)**, which the owner's surplus rule depends on; liens and trading holds naming a trade; and deleting x2f_moderation's per-trade rows `mod_party_state`, `mod_wallet_secrets`, `signed_terms`, `mod_escrow_state`, `mod_watch` and `mod_sweeps` with the trade (the escrow key material only once the escrow is shown empty, and `mod_sweeps` only after the watch has dropped the trade).
- **Web Push keys** (`X2F_VAPID_PUBLIC`, `X2F_VAPID_PRIVATE`; required, Plan 3 Task 19): a VAPID key pair, both base64url (the P-256 public key, 87 characters, and its private key, 43 characters). The API refuses to start if either is missing or malformed, or if the public key is not the private key's own half. Make one pair per deployment, once, with the web-push package the API already depends on (nothing new to install): `npx web-push generate-vapid-keys --json` in the repo, or `node -e "console.log(require('web-push').generateVAPIDKeys())"` from `apps/api`. Keep the private key as secret as `X2F_SERVER_KEY`. Changing the pair later makes every browser's existing push subscription stop working until it subscribes again. The VAPID subject sent to push services is the first `https://` entry of `X2F_ORIGINS` (X2F has no contact email). The browser subscription endpoints the API accepts are limited to the major push services (`PUSH_SERVICE_DOMAINS` in `apps/api/src/push/routes.ts`), because the API sends requests to them.
- **Leaked-password list** (`X2F_LEAKED_LIST_PATH`): the API refuses new passwords found in Have I Been Pwned's Pwned Passwords, checked against a file on X2F's own server (no outside lookup). Subset: SHA-1 entries seen at least 10 times. Build it as the operator, never on the server: download the SHA-1 list with the official `haveibeenpwned-downloader`, then `npx tsx tools/leaked/build-leaked-list.ts <pwnedpasswords.txt> <leaked.bin> [--min-count 10]` (the input must be sorted by hash, as the downloader writes it; the tool prints the record count and byte size). The file is sorted 20-byte SHA-1 records with no header; the API refuses to start if it is missing, empty, or its size is not a multiple of 20. Measured size: not yet recorded (record the size the tool prints here when the production list is first built).
- **Node proxy settings** (`apps/node-proxy`, the browser wallet's only way to a Monero node): `NODE_PROXY_UPSTREAM` (the node's RPC URL, e.g. `http://127.0.0.1:18081`; monerod must run with `--restricted-rpc`: at startup the proxy calls `get_info` and refuses to start, printing only `{"reason":"node-not-restricted"}` or `{"reason":"node-unavailable"}`, unless the node reports `restricted: true`), `NODE_PROXY_WEB_ORIGIN` (the web app's exact origin, the only one given CORS headers or allowed to call); optional `NODE_PROXY_HOST` (default `127.0.0.1`), `NODE_PROXY_PORT` (default `8789`; the relay's admin listener has `8788`), `NODE_PROXY_TIMEOUT_MS` (default `20000`), `NODE_PROXY_MAX_BODY_BYTES` (default `1048576`), `NODE_PROXY_MAX_IN_FLIGHT` (calls held at once, waiting or at the node; default `256`, 503 `busy` beyond), `NODE_PROXY_MAX_UPSTREAM` (calls open at the node at once; default `20`; the rest wait in a queue for up to the timeout, then get 503 `busy`). Start with `npm start -w @x2f/node-proxy`. It serves Monero's own paths at its root and refuses everything off its allowlist (`apps/node-proxy/src/server.ts`); it logs only that it is listening.
- **Released-screen confirmations** (`X2F_MONEROD_URL`, optional, Plan 3 Task 24; read in `apps/api/src/main.ts`): X2F's own monerod RPC base URL, a bare http(s) origin such as `http://127.0.0.1:18081` (no credentials, path, query or fragment; the API refuses to start otherwise). `GET /v1/trades/:code/confirmations` asks it for the trade's own settlement tx (`/get_transactions`, pruned, and `/get_height`), at most 4 lookups at once, each answer reused for 10 s. A `--restricted-rpc` node is fine (the same node the proxy uses works). Unset (the default): no count is shown, the route answers `confirmations: null`, and the released screen says "Checking…" and backs off. The node must be reachable from the API's host (Plan 6: a firewall rule when monerod runs on another host).
- **Relay settings** (`apps/relay/src/main.ts`): `RELAY_MOD_SIGNING_PUBLIC` (required — the moderation service's signing public key, hex; the relay refuses to start without it, since only moderator-signed admin calls register or close trades); optional `RELAY_HOST` (default `127.0.0.1`), `RELAY_PORT` (default `8787`), `RELAY_ADMIN_HOST` (default `127.0.0.1`) and `RELAY_ADMIN_PORT` (default `8788`) for the separate admin listener that serves trade register/close, plus the tuning knobs `RELAY_MAX_ENVELOPE_BYTES`, `RELAY_MEMORY_BUDGET_BYTES`, `RELAY_MAX_UNAUTHENTICATED` and `RELAY_RATE_REFILL_PER_SEC`. Start with `npm start -w @x2f/relay`. The admin listener carries the trade-management API and must stay on a private interface (loopback or an internal network reachable only by the moderation service); it is never published.
- **Monero node behind the proxy**: every wallet reaches monerod from the proxy's one address, and monerod limits RPC connections per address. Its defaults are `--rpc-max-connections-per-private-ip 25`, `--rpc-max-connections-per-public-ip 3` and `--rpc-max-connections 100`; past them it refuses calls (502s, measured at 200 wallets at once). The proxy opens at most `NODE_PROXY_MAX_UPSTREAM` connections (one per call, no keep-alive), so run monerod with `--restricted-rpc` and raise the limit for the proxy's address above that cap with some room, e.g. for the default of 20: `--restricted-rpc --rpc-max-connections-per-private-ip 30 --rpc-max-connections-per-public-ip 30 --rpc-max-connections 100` (the public-IP flag matters when the proxy reaches the node over a public address, where the default is 3). Raising `NODE_PROXY_MAX_UPSTREAM` means raising these flags with it.
