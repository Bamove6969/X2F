- **Serving the web app** (`X2F_WEB_ROOT`, with `X2F_RELAY_ORIGIN` and `X2F_NODE_PROXY_ORIGIN`; `apps/api/src/static/serve.ts`). `X2F_ORIGINS` is needed here too (an `http:` site origin only on 127.0.0.1, [::1], localhost or a `.onion` host, unless `X2F_ALLOW_INSECURE_ORIGINS=1`, as for the relay and node proxy): the OCR worker's CSP (on every `/ocr/*` response) lets it load scripts and fetch only under `<origin>/ocr/` of each listed origin, and start no worker (Plan 5 Task 16 review, M-1). Every origin setting must be a plain exact origin: lower-case host-name characters or a bracketed IPv6 address, and an optional port, with no path, `;`, `,`, quote or `*`. **A reverse proxy in front of the API must pass `/ocr/` paths with the raw request URI:** it must not decode `%2F` (or `%2E`, `%5C`) or resolve `..` under `/ocr/`, or else it must refuse such paths. The CSP allows `/ocr/..%2Fv1%2Fx`, because the browser does not normalise `%2F`, and a proxy that decodes it would hand the API `/v1/x`. The API itself answers 400 to any `/ocr/` path (its first segment decoded once, so `/%6Fcr/` counts; one that does not decode is refused) containing `%2F`, `%2E`, `%5C`, `%25`, `..` or a backslash, read from the raw request line (review m-2). With nginx: `proxy_pass http://upstream;` with no URI part (nginx then passes the request URI unchanged), and no `rewrite` on `/ocr/`.
- **Stored-secret key rings** (FU-C, owner decision 2026-10-23; ASVS 2.4.5, 2.6.2, 2.8.2; FU-D, owner 2026-10-25). Four secrets, each separate from `X2F_SERVER_KEY` and from each other (the API refuses to start if any key is shared): `X2F_PASSWORD_PEPPERS` (the pepper: passwords are stored as Argon2id of HMAC-SHA-256(pepper, NFC password)), `X2F_RECOVERY_CODE_KEYS` (recovery codes are stored as HMAC-SHA-256 under this key, bound to the account), `X2F_TOTP_KEYS` (the file/env key store that seals TOTP secrets with AES-256-GCM; an HSM or KMS replaces it in Plan 6) and `X2F_LOGIN_NAME_KEYS` (the private login name is stored only as `accounts.login_tag` = HMAC-SHA-256 under this key of `x2f/login-name\0` + the lower-cased NFC name, so a stolen database holds no login names once Migration 012 step 1 below, including its `ANALYZE accounts, name_keys; VACUUM FULL accounts, name_keys, pg_statistic; CHECKPOINT;` as a database superuser, has run and every older backup is gone; a sign-up waiting in its challenge keeps the login name sealed under a key derived from `X2F_SERVER_KEY`). Each is `<id>:<base64 of 32 random bytes>[,<id>:<base64>...]`, ids 1–32767, **newest first**: the first entry is used for everything new, the others only to check or open older stored values. Instead of the variable, `<NAME>_FILE` may name a file holding the same text (a regular file, `chmod 600`, owned by the API's user), never both. Make a key with `node -e "console.log('1:' + require('crypto').randomBytes(32).toString('base64'))"`. They are secrets: never log them, never commit them; config errors name the variable only.

Old recovery codes have `recovery_codes.key_id` null: they are plain SHA-256 and cannot be converted (only the hash is kept), so they keep working, one use per code, until used up or until the person regenerates the set. - **Secure Jabber account-change alerts** (owner rule p5-7; optional, off by default). `X2F_JABBER_KEYS` (or `X2F_JABBER_KEYS_FILE`): a key ring like the ones above, separate from every other secret, that seals each user's Jabber address at rest (`jabber_contacts`, AES-256-GCM via the key store, bound to the account). `X2F_XMPP_JID` (X2F's own sending address, lower-case bare, e.g. `x2f-alerts@xmpp.example.org`) turns sending on and then needs `X2F_XMPP_PASSWORD` (or `X2F_XMPP_PASSWORD_FILE`, `chmod 600`), `X2F_JABBER_KEYS` and `X2F_XMPP_SOCKS`; optional `X2F_XMPP_HOST` (default: the address's domain; a `.onion` name is fine) and `X2F_XMPP_PORT` (default 5223). **Tor is mandatory** (owner ruling p11-31): `X2F_XMPP_SOCKS` is the Tor SOCKS5 proxy as an IP address and port (`127.0.0.1:9050` or `socks5h://127.0.0.1:9050`; never a host name), and the API refuses to start with `X2F_XMPP_JID` set and no proxy. Every connection goes through it, with the server's name handed to the proxy unresolved, so nothing is looked up in DNS. Inside the tunnel the connection is direct TLS only (XEP-0368): the server must offer TLS on that port with a certificate valid for the address's domain, and SASL inside it (SCRAM-SHA-256, else SCRAM-SHA-1, else PLAIN); there is no plaintext or STARTTLS fallback. **OMEMO is mandatory** (owner ruling p11-31; `docs/jabber/omemo-plan.md`): a message goes only to a recipient who publishes an OMEMO 0.3 device bundle (`eu.siacs.conversations.axolotl`: Conversations, Dino, Gajim, Monal; not Kaidan, which is OMEMO 2 only), and only encrypted, never plaintext. Every notice is a fresh session and a PreKeySignalMessage per device (`@x2f/omemo`, `apps/api/src/jabber/omemo.ts`); no session state is kept. X2F's OMEMO identity key and bundle (signed prekey, 100 prekeys) are created on first use in `jabber_omemo_identity`, sealed under `X2F_JABBER_KEYS`, and published to the sending account's PEP nodes on every connection, so the account's server must offer PEP (XEP-0163) with publish-options. Trust is blind trust before verification: every device in the recipient's device list whose bundle verifies gets the message. **GAP:** not yet tested against a real client; the plan lists interop tests as the next step. Without these the set-up answers `jabber-unavailable` and the Alerts section is hidden. **GAP:** X2F's production Jabber account and server are not set up yet. Rotation of `X2F_JABBER_KEYS`: put the new key first and restart, run `npm run rewrap-jabber -w @x2f/api` (reseals every address, pending address, queued notice, the OMEMO identity key, the OMEMO bundle and the record of OMEMO prekeys used per address, which it re-tags; resealing sends no notice), and run it again: drop the old key only after a re-run reports `"rewrapped":0,"failed":0` and `"prekeysNotCurrent":0` (OMEMO prekey records still under an old key: the rewrap moves those of every address it opens, in `jabber_contacts` and `jabber_outbox`; one it cannot match is lost with the key, and its device may then get a prekey it already used). A `failed` count above 0 is a blob that does not open (its user sees "Needs setting up again" and sets Jabber up again). A typed address that was never proven is purged 24 hours after its test message (`purgeJabberPending`). Every change to an account queues a notice in `jabber_outbox` from database triggers (migration 331; the reviewed list is `apps/api/src/jabber/changePaths.ts`), sent every 5 s after commit; logs carry counts only.

- **Relay settings** (`apps/relay/src/main.ts`): `RELAY_MOD_SIGNING_PUBLIC` (required — the moderation service's signing public key, hex; the relay refuses to start without it, since only moderator-signed admin calls register or close trades); optional `RELAY_HOST` (default `127.0.0.1`), `RELAY_PORT` (default `8787`), `RELAY_ADMIN_HOST` (default `127.0.0.1`) and `RELAY_ADMIN_PORT` (default `8788`) for the separate admin listener that serves trade register/close, plus the tuning knobs `RELAY_MAX_ENVELOPE_BYTES`, `RELAY_MEMORY_BUDGET_BYTES`, `RELAY_MAX_UNAUTHENTICATED` and `RELAY_RATE_REFILL_PER_SEC`. Start with `npm start -w @x2f/relay`. The admin listener carries the trade-management API and must stay on a private interface (loopback or an internal network reachable only by the moderation service); it is never published.
- **Moderation service** (`apps/moderation/src/main.ts`, Plan 3 Tasks 8-9; a separate process with no listening socket): `MOD_DATABASE_URL` (its own database `x2f_moderation`, which the API's role cannot read; migrations in `apps/moderation/migrations/` run at start), `MOD_KEYSTORE_KEY` (base64 of 32 bytes; seals `mod_party_state`, `mod_escrow_state` and, under a subkey, `mod_wallet_secrets`), `MOD_SIGNING_SECRET` (base64 of the 64-byte Ed25519 secret key; its public half is the API's `X2F_MOD_SIGNING_PUBLIC` and the relay's `RELAY_MOD_SIGNING_PUBLIC`), `X2F_API_INTERNAL_URL` (the API's private internal listener, `X2F_INTERNAL_HOST`/`X2F_INTERNAL_PORT`, default port 8081), `RELAY_ADMIN_URL` (the relay's private admin listener), `RELAY_URL` (the relay's public WebSocket URL, `ws://` or `wss://`, which each moderator party joins), `MONERO_DAEMON_URI`, `MONERO_NETWORK` (`regtest`, `stagenet` or `mainnet`) and `X2F_FEE_WALLET`. All are required. Start with `npm start -w @x2f/moderation`. It pulls work every 5 s and runs the chain watcher every 15 s. Deploy the API before moderation, because moderation needs the API's `/internal/v1/watch` and its Task 9 report kinds.
- **Moderation ruling gate** (Plan 4 Task 13; on when `MOD_STATE_DIR` is set, with `MOD_STAFF_ORIGIN`, `MOD_STAFF_RP_ID`, `MOD_FIDO_MDS_DIR` and `MOD_API_READER_DATABASE_URL`). If `gate.bin` ever goes missing, find out why before running init-gate again: a new gate trusts nobody until the owner is pinned again.
- **`MOD_LIEN_RECOVERY`** (moderation, optional; lien recovery, docs/lien-recovery.md; re-review N1): the moderation service's own switch for lien recovery. Unset, empty or `off` (the default): it refuses every trade whose terms carry a lien recovery (logged `lien-refused-off`; the trade waits unsigned) and never signs a lien statement. `on`: recoveries are checked and signed as the doc describes (it also needs the ruling gate, `MOD_STATE_DIR`). - **The staff site must be served from a build the API host cannot change** (re-verify X1, lead call 2026-11-12). A security key shows nothing of what it signs, so the staff site's `KeyTapDialog` shows the whole intent and rebuilds the tap's challenge itself (`tapChallenge` from the nonce and `issuedAt` that `taps/start` answers), refusing a challenge for anything else or an `issuedAt` more than 2 minutes from the device's clock. That check is only worth anything while the browser runs the code it was built from: serve `apps/staff-web`'s build from its own origin and host, deployed by the owner, not by the API's host or process (or behind a shell whose scripts are pinned with Subresource Integrity), so a compromised API host cannot swap the checking code. The staff origin's CSP stays `script-src 'self'`.
- **Monero node behind the proxy**: every wallet reaches monerod from the proxy's one address, and monerod limits RPC connections per address. Its defaults are `--rpc-max-connections-per-private-ip 25`, `--rpc-max-connections-per-public-ip 3` and `--rpc-max-connections 100`; past them it refuses calls (502s, measured at 200 wallets at once). The proxy opens at most `NODE_PROXY_MAX_UPSTREAM` connections (one per call, no keep-alive), so run monerod with `--restricted-rpc` and raise the limit for the proxy's address above that cap with some room, e.g. for the default of 20: `--restricted-rpc --rpc-max-connections-per-private-ip 30 --rpc-max-connections-per-public-ip 30 --rpc-max-connections 100` (the public-IP flag matters when the proxy reaches the node over a public address, where the default is 3). Raising `NODE_PROXY_MAX_UPSTREAM` means raising these flags with it.
