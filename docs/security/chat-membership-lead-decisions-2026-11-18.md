# Chat membership keys: lead decisions 18 Nov (addendum)

This is an addendum to `design-chat-membership-keys-2026-11-08.md` (comms folder). It records the lead's engineering calls of 18 Nov 2026 for design tasks 8 and 9, which the design left open, so a security reviewer can check them against the design.

It lives on `wip/lead-mod-chat` and not in the comms file, because helpers may not push comms. The lead may append this section to the design file as is.

## Lead decisions 18 Nov

- **Device key id.** SHA-256 of the staff device's Ed25519 signing public key, as hex, first 32 characters (128 bits). Built: `deviceKeyIdOf` in `apps/moderation/src/internal/grant.ts`. The grant route refuses any other form.
- **Certification lifetime.** A certification lasts 365 days. After that the device needs a fresh `certify-device` tap.
- **Replay of the certification.** The `certify-device` tap is a normal key tap bound to its intent, so the gate's existing nonce and single-use rules apply. The gate also refuses a second certification of a key id while one is still live.
- **Devices per person.** At most 3 live certified devices per staff member. This matches the trader device limit.
- **Revoking one device.** A `revoke-device` tap names the key id. Revoking a person (switch-off or removal) revokes all their devices.
- **Countersign.** The domain is `x2f/mod-countersign/v1`. The staff signature covers chatId, seq, the SHA-256 of the ciphertext, requestId and issuedAt. A countersign is single use because seq is unique per chat in envelope v2. Moderation refuses an issuedAt older than 5 minutes, and any requestId it has already seen.
- **`chat.read`.** It goes in the existing `activity_log` until the per-trade audit log (design task 12) exists. Moderation's own `mod_chat_access` record is the authoritative one.
- **No v1 stopgap.** No new wrap scheme is built on chat envelope v1. Order: groundwork (C), then design tasks 3, 4, 5, 6, then 8, then 9.
- **Owner questions.** p12-1, p12-4 and p12-11 are built to the design's recommendations. Each sits behind a named constant marked `// OWNER: p12-x`, until the owner answers page 12.

## Builder's calls in the groundwork (C), for the reviewer

These were made on `wip/lead-mod-chat` while building `POST /internal/chat/grant`. None of them is crypto.

1. **Who someone is comes from the ruling gate, not the API.** The gate's state (`GateState`, owner-rooted) supplies:
   - the owner;
   - live, joined staff who are not switched off and not removed;
   - their role.

   The gate registry is synced before each check, as `gateCheck` does, so a switch-off already shown by the API counts at once. Only the assignee comes from the API (migration 710 grants the read-only role `disputes.assignee` and nothing else). A compromised API can therefore only point a case at a real moderator, and the access is recorded in `mod_chat_access`.
2. **"Disputed" means two things must both hold.** The API's current dispute is not closed, and this process itself saw the trade disputed within `CHAT_AFTER_DISPUTE_DAYS` (`mod_dispute_seen`, which comes from the watch list and its own escalations). This narrows what the API alone can claim. It is not independent of the API, because the watch list is the API's word too (design section 3, table, API row).
3. **The log entry is bound to the person.** The `chat.read` entry must have actor kind `staff` and the actor must be exactly the staff account named in the request. It must also:
   - be of this trade;
   - be at most 60 seconds old, with up to 30 seconds of clock skew;
   - never have been used before.
4. **Order of checks.** Each check refuses at the first failure:
   1. HMAC, then parse.
   2. Gate present (503 `gate-unavailable`).
   3. Log entry (403 `log-entry-invalid`).
   4. Disputed (403 `not-disputed`).
   5. On the case (403 `not-on-case`). That means the assignee; or a senior or the owner (OWNER p12-4). A helper is never on a case, even if assigned.
   6. Device certified and live, at this process's clock (403 `device-not-certified`).
   7. Chat attested (404 `no-chat`).
5. **Use and record happen together.** Only after every check passes does one SQL statement both mark the entry used and write the `mod_chat_access` row. A replay finds the entry used and gets 403 `log-entry-invalid`. Refused requests use nothing and record nothing.
6. **(Superseded by task 9.) Nothing is granted yet.** A request that passes every check is answered 503 `grant-unavailable`, because no moderator copy of the chat key exists until tasks 3–6 (NEEDS_P4_CHAT_MEMBERSHIP). In production `devices` is `NO_CERTIFIED_DEVICES` until task 8, so in practice every request stops at `device-not-certified`.
7. **(Superseded by task 9: the send route is a countersign, in production, and `X2F_DEV_MOD_CHAT` is gone.) The grant route is not dev-only.** `/internal/chat/send` stays behind `X2F_DEV_MOD_CHAT` (NEEDS_P4_MOD_COUNTERSIGN) until the countersign is built.
8. **Shredding.** The shred pass deletes `mod_chat_access` with the chat's keys (design section 5).
9. **Migration numbers.** API 710 and 711 (lead 18 Nov: after retention's 701, so an existing database applies them in order) and moderation 016 (the next free number).

## Builder's calls in tasks 5 and 6, for the reviewer

Tasks 5 and 6 are on `wip/lead-mod-chat`. None of these is a new primitive; the formats follow the design's own pattern (Ed25519 over a domain string and canonical JSON).

**Task 5, the trader engine**
1. **Getting the key.** The engine gets the chat key right after the attestation checks out, before it reads or seals any envelope. With no record on the server, it makes the key and posts the record. On 409 it reads the record that won.
2. **Checking the record.** The engine checks the record against the attested participants, never the API's word. The record must be signed by the trader it names, for this chat's channel. This device's copy must hash to the record's tkh. If any check fails, the chat shows the `security` failure and nothing is read or sent.
3. **The key is never stored on the device.** It is held in the worker's memory and erased with the chat. Each worker start opens the device's copy again.
4. **The engine is v2 only.** A v1 envelope is never shown: it gets a refused receipt, and the lines after it still show. Envelope v1 stays in chatCrypto for its own tests. Consequence: a chat that already holds v1 lines from before its key record shows none of them. The design assumes there are no production chats yet. The lead should confirm.
5. **No "unreadable" line.** Design section 9 wants a message that does not open shown as "unreadable". Today it is dropped, as before, because a visible line needs copy (an owner/design item).

**Task 6, the dispute grant (T1)**

6. **Grant-accepted statement.** Domain `x2f/chat-grant-accepted/v1\0`, body `{v, chat, tkh, grantBy, grantSig}`. It names exactly one grant, by that grant's signature, and is signed with the chat's moderator identity.
7. **What the API checks before filing a grant.** The grant must:
   - be signed by the registered identity of the side sending it, for this chat's channel;
   - carry the key record's tkh;
   - have a `disputeAt` within 10 minutes of the server's clock.

   The grant is required once the chat has a key (400 `grant-required`) and refused when it has none. The API stores the signed grant exactly as posted, in `chat_members.statement`.
8. **What moderation checks before accepting a grant.** All of these come from its own records:
   - the chat is one it attested;
   - the key record and the grant are each signed by the attested trader they name;
   - the grant's tkh equals the record's tkh;
   - the wrap opens with the chat's sealed moderator identity to a key with that tkh.

   The key is wiped from memory at once. Moderation keeps only a `mod_chat_grants` record (no key; deleted by the shred pass). It does not check its own view of the dispute, because a grant is the trader's own act.
9. **Fallback grant (T1 by proxy).** The counterparty's device grants too only when all of these hold:
   - the trade is disputed;
   - the other side's grant, signed by its attested identity for this chat, has no acceptance that verifies against the attested moderator identity;
   - `GRANT_FALLBACK_MS` = 2 minutes have passed since that grant's `disputeAt`;
   - this side has not granted.

   The API files a fallback grant only under the same conditions, once per side.
10. **The grant passes through the page.** It crosses postMessage from the worker to the page, which sends it with the dispute request. Its only secret part is a wrap that only the moderator's key opens.

## Builder's calls in task 7 (T2, the dispute notice), for the reviewer

No new primitive: the notice format (`x2f/chat-dispute-notice/v1\0 {chat, disputeSeq, openedAt, openedBy}`) is task 3's.

1. **When moderation signs a notice.** Only when all of these hold, on its own records: it attested the chat; its own `mod_chat_trade` links the chat to the trade the API names; its own `mod_dispute_seen` shows the trade disputed within `CHAT_AFTER_DISPUTE_DAYS`; it accepted no grant for the chat (`mod_chat_grants`); it signed no notice for that dispute seq (`mod_chat_notices`, migration 018, shredded with the chat). The seq, opening time and opener are the API's word, listed by `GET /internal/v1/chat-notices`.
2. **A trader-opened dispute waits.** `NOTICE_AFTER_TRADER_MS` = 2 minutes after its opening, by moderation's clock, so the disputer's own grant (T1) goes first. A system dispute gets its notice at once. This also covers the disputer whose device holds no key.
3. **What the API files.** The notice is stored (`chat_dispute_notices`, migration 712, cascades with the chat) only when it verifies against the chat's attested moderator identity for this chat's channel and names the linked trade's current open dispute exactly (seq, opening time, opener). The chat view shows the notice for the current open dispute only.
4. **What the device does.** With the API's `disputeOpen` true AND a notice that verifies against the attested moderator identity, and no grant of this side and no verified acceptance, the device grants once at once (`POST /v1/chats/:chat/grant`, trigger `notice`). The API takes such a grant only while disputed, with a stored notice for the current dispute and no accepted grant, once per side.
5. **The banner.** A verified notice with `openedBy: 'system'` shows "A moderator has been called by the system." (COPY-UNSIGNED, the design's own words). A trader-opened dispute's notice grants without the banner: the trader already sees the dispute.

## Fixes from the review of tasks 3-6 (review-lead-mod-chat-t3-6-2026-11-18.md)

- **F1.** Lead call (a): tasks 6 and 7 land together, never 6 alone. Task 7 is on the branch.
- **F2.** `chat_members.refused_at` and `refused_reason` (migration 713). Moderation reports `chat-grant-refused {chat, grantBy, grantSig, reason}` for a grant that fails for good (`bad`, `wrong-key`, `unattested`, `other-key`). The API marks only that exact row, only while it is neither accepted nor refused. `pendingGrants` skips refused rows. The fallback still treats a refused grant as unaccepted.
- **F3.** The trader device pins the chat key's tkh in its ChatRecord on the first record it accepted or posted, before anything is sealed. After that, a record of another tkh, or a 404, is the `security` failure, and the device never makes a second key.
- **F4.** The engine counts the other side's grant as accepted only when both the grant's and the acceptance's tkh equal `chatKeyHash(tk)` of this device's key. Moderation's grant pass refuses (`other-key`) a grant whose tkh differs from one it already accepted for the chat.
- **F5.** The key route inserts under the chat row's lock (`for update`). The dispute route, inside the dispute's transaction, takes that row `for share` and re-checks `chat_keys`; a record that appeared needs the grant (400 `grant-required`).
- **F6.** The API takes a grant's `disputeAt` at most 10 minutes in the past and at most 1 minute in the future. The engine waits `GRANT_FALLBACK_MS` from the earlier of `disputeAt` and when this worker first saw the grant.
- **F7.** The engine fills the chat key with zeros before dropping it (on erase, on a refused record, on a lost race). In JavaScript, libsodium's `memzero` is the same fill; the web app does not import libsodium itself.
- **F9.** **A grant relies on one trade per chat and one dispute per trade.** It names its chat (the channel), not a trade or a dispute seq. That is safe only while a chat links to at most one trade (`linkChatToTrade … where trade_code is null`) and a trade has at most one dispute. If re-disputes or chat reuse ever come, the grant needs `trade` and `disputeSeq` under `x2f/chat-grant/v2\0`. Noted in `chatV2.ts` too.
- **F11.** Tests: two identical `/internal/chat/grant` requests at once give exactly one access row (one passes, one 403 `log-entry-invalid`); one person's `chat.read` entry cannot be used for another person.
- **F8** (the gate wired into the internal server) and **p12-11** are in task 9.

## Builder's calls in task 8 (staff device certification), for the reviewer

The lead's decisions above are built as stated. No new primitive: the certification is a key tap (`tapChallenge`), verified by the gate as every tap is.

1. **The intents.** `certify-device {accountId, deviceKeyId, signPublic, boxPublic, issuedAt}` and `revoke-device {accountId, deviceKeyId, issuedAt}` (`@x2f/staff`). `issuedAt` is the API's own start time of the tap, signed (as the owner registry kinds), and the 365 days run from it. The id is `staffDeviceKeyId(signPublic)`, one function for staff-web, the API and the gate.
2. **Who may tap.** A certification only for oneself (`accountId` is the tap's account), by any live staff member or the owner. A helper may certify a device too; a helper is never on a case, so it opens nothing. A revocation by the device's own person or by the owner. The API has a route for one's own revocation only; the owner's revocation of someone else's device works in the gate, but there is no API route or screen for it yet (switching the person off revokes all their devices anyway).
3. **What the gate refuses** (each tap spent, logged `gate.refused.device-*`): a tap that does not verify against its registry (unknown key, revoked person, bad signature), a reused nonce, a key counter at or below its mark, a tap for someone else, an id that is not the signing key's, keys that are not 64 lower-case hex, an `issuedAt` more than 2 minutes ahead or more than 24 hours old (`MAX_TAP_AGE_MS`), a certification issued before the person's last switch-off this gate saw (less 2 minutes), a live id, a revoked id certified by a tap issued before its revocation, and a fourth live device.
4. **Revoking a person.** At every sync, every device of a person who no longer stands (switched off, removed, gone from the API, not the owner) is revoked for good: a later switch-on brings none back. A tapped security reset (D-032) revokes the person's devices too (builder's call: the devices were certified with the old keys). `deviceLive` also checks the person still stands at the moment of a grant.
5. **The device step leaves other taps alone.** It reads only `certify-device` and `revoke-device` taps and never spends a nonce of any other kind.
6. **The API keeps no device table.** `POST /staff/v1/devices` uses the tap (bound to the session, as every tap) and logs `staff.device-certified {deviceKeyId}`; it refuses a live id (409 `device-exists`) and a fourth device (409 `device-limit`) from its own view of the used taps. The gate re-verifies the stored tap itself and is the only judge.
7. **Staff-web keeps the key.** An Ed25519 key and its X25519 box key (`generateIdentity`), the secrets sealed with AES-256-GCM (AAD `x2f-staff-device/v1`) under a non-extractable WebCrypto key in the same IndexedDB database (`x2f-staff-device`), as the trader chat store does. `identity()` opens the secrets for one use and checks they belong to the stored public key. Staff-web now depends on `@x2f/protocol` (lock file updated by hand: one line).
8. **The screen.** `DeviceCard` ("Confirm this device", COPY-UNSIGNED, DESIGNER-REVIEW, no board) opens the key tap with every signed field labelled. It is added to the webauthn tripwire's reviewed callers.

## Builder's calls in task 9 (the grant to staff and the countersign), for the reviewer

No new primitive. The re-wrap is `crypto_box_seal` (`wrapChatKey`); the countersign is the lead's `x2f/mod-countersign/v1`; `encryptChat` and `signChatEnvelope` are `sealChat` split in two, unchanged.

1. **The gate is wired (F8).** The process entry passes `gateInternalDeps(store, source, ctx)` to the internal server: `gateStaffDirectory` and `gateDevices` on the same gate store, each question syncing the registry under the gate's lock and saving it. Without `MOD_STATE_DIR` the server gets neither and refuses every call (503 `gate-unavailable`). Startup test: `gateDeps.test.ts`.
2. **One check order for both routes.** HMAC, shape, gate present, log entry (this route's action, this trade, fresh, unused, a staff actor who is exactly the named person), disputed (API status not closed AND `mod_dispute_seen`), on the case, device certified and live (the gate's record), chat attested. Nothing is used or recorded before every check passed.
3. **The re-wrap.** Moderation takes the trader grant it accepted itself (`mod_chat_grants`: side, signature, tkh), reads that grant's signed statement back from the API (migration 714: the reader may select `chat, member_kind, granted_by, sig, statement, removed_at` of `chat_members`, never `wrap` or `member_ref`), verifies it again against the traders it attested and its own recorded signature and tkh (else 409 `no-grant`), opens its wrap with the sealed moderator identity to a key of that tkh, seals the key to the device's **certified** box key, and wipes it. Only then one statement uses the entry and writes `mod_chat_access` (`grant`, migration 019). The answer is `{wrap, tkh, boxPublic, nextSeq}`.
4. **What staff-web checks before it shows a line.** The attestation by the pinned moderation key (`VITE_MOD_SIGNING_PUBLIC`, new `verifyAttestationSignature` in `@x2f/trade`: the signature part of `verifyAttestation`, for a reader who is not a participant), naming this chat and channel; the key record signed by the attested trader it names, whose tkh is the re-wrapped one (so the API cannot hand the device a key of its own); the wrap opens with this device's box key; every envelope verifies by an attested participant and opens under the key. An envelope that does not is counted ("n message(s) did not open"), never shown. COPY-UNSIGNED.
5. **The countersign on the wire.** The API forwards `{seq, nonce, ct, ctSha256, requestId, issuedAt, sig}` from staff-web. `chat` in the signed body is the chat's channel (the envelope's `trade`); `ctSha256` is SHA-256 of the ciphertext bytes (WebCrypto: the libsodium build has no SHA-256); `requestId` 16 random bytes as hex. Moderation verifies with the device's certified signing key over its own recomputed hash, refuses an `issuedAt` older than 5 minutes (lead) or more than 1 minute ahead (builder's call; staff-web stamps it by the server's clock), a used `requestId` (`mod_countersign_requests`, migration 019, shredded with the chat) and a `seq` that is not the chat's next moderator seq (409 `stale-seq` with `nextSeq`; staff-web re-seals once at that seq). Then one transaction uses the entry, takes the request id and the seq and records `send`; then it signs the v2 envelope as `from: 'mod'`. It never decrypts. The API stores the envelope only if it carries exactly the seq, nonce and ciphertext the device sealed.
6. **Text checks moved to staff-web.** The API can no longer check a moderator message's text (it is ciphertext). Staff-web refuses a blank one, control characters and more than `CHAT_TEXT_MAX_BYTES` before sealing; the trader app's own checks are unchanged.
7. **`chat.read`.** The API commits one `chat.read` (the staff member as actor) per read, before it asks moderation; with the log failing nothing is asked. It files the staff copy in `chat_members` (`staff`, `<staffId>/<deviceKeyId>`, trigger `assigned`, the log entry id; one live row per device, replaced on each read). `sig` is empty: no new signature is made over the re-wrap.
8. **OWNER p12-11** (`CHAT_READ_VISIBILITY` in `apps/api/src/log/query.ts`). The owner sees every `chat.read` entry (scope `all`). A senior sees those on "their cases", read here as a trade whose current dispute is assigned to them or that they have any other entry on. A moderator or helper sees only their own. With no role given, the narrowest view. No staff route calls `queryLog` yet, so this is where it will apply.
9. **Where the key is held in staff-web.** Superseded by design task 10 (below): in the chat key worker only.
10. **The unblurred proof** is still not readable: no proof is uploaded yet. The re-wrap of its key is left under the existing `NEEDS_P5_PROOF_ENVELOPE` (the proof parts of the old `NEEDS_P4_CHAT_MEMBERSHIP` markers were renamed to it).
11. **Residuals for the reviewer.** The staff site's CSP has no `'wasm-unsafe-eval'`; libsodium in staff-web is expected to fall back to its JavaScript build, which no test here checks in a browser (no Playwright in this job). The applied migration 208 keeps its historical `NEEDS_P4_CHAT_MEMBERSHIP` comment (an applied migration is never edited). A compromised API can still withhold envelopes or the grant (denial of service), as the design says.

## Fixes from the review of tasks 7-9 (review-lead-mod-chat-t7-9-2026-11-18, comms), and design task 10

Builder's calls, for the re-review:

1. **N1.** ModCase wipes the chat key on unmount only (a ref to the current chat; every chat state after a message shares the key).
2. **N2.** Gaps are counted over verified envelopes only, per sender (`buyer`, `seller`, `mod`); a gap found on a verified envelope that is not a line is carried to the next line shown. "n message(s) missing here" is COPY-UNSIGNED.
3. **N3.** Moderation migration 020: `mod_chat_notices.notice` and `posted_at`. The notice is recorded before it is posted (unchanged); the same signed notice is posted again on every pass while the API lists the dispute and `posted_at` is null, whatever the API answered (a 4xx included); never a second one. A row from before 020 (no notice) is never signed again.
4. **N4.** `liveDevices` drops every certification not issued **strictly** after the latest of: the last switch-off (API migration 715, `last_switched_off_at`, never cleared), the removal, a used `reset-staff-security` tap. No 2-minute skew here, unlike the gate's `before-off` for a new tap: the gate revokes existing devices at its own sync, later than these times, so a skew would let this API list a device the gate revoked. ModCase routes 403 `device-not-certified` back to DeviceCard's confirm step. At the same `used_at`, a certification sorts before a revocation (the existing test was flaky on the random tap id).
5. **N5.** An applied owner switch-on revokes all the person's devices, as of the switch-on's **signed issuedAt** (never later than the gate's clock), not "now" as the review wrote: with "now", a device certified after the switch-on but before the sync would be refused `before-revoke` while this API lists it live, which is the N4 dead end again. Anything certified before the switch-on is revoked either way.
6. **N6.** A countersign's `requestId` is taken in its own committed statement as soon as it verifies, before the freshness and seq checks; a verified countersign refused for any later reason is spent. **Re-review m3 (accepted residual, lead call):** a compromised API can still hold a countersign, fake a 409 `stale-seq`, and forward both it and staff-web's re-seal at the next seq, so both traders see the moderator's message twice, in seq order, within 5 minutes. It can duplicate a moderator message, never forge or alter one.
7. **N7.** `x2f/mod-countersign/v1` now signs `{chat, seq, nonce, ctSha256, requestId, issuedAt}` (changed in place: v1 never landed).
8. **N8.** The registry sync snapshots every key's counter mark before it starts and records the counters it takes; the device step sorts its verified taps by counter and judges each against the pre-sync mark (raised by each device tap it applies) and refuses a counter the registry already took this sync.
9. **N11 (a)** API migration 716: `chat_members` statement only on a `mod` row. **(b)** `attestationKeys()`. **(c)** the tkh is compared before every seal. **(d)** `identityKeysMatch` (protocol): the Ed25519 seed and public half, and the X25519 secret times the base point. **(e)** `retireStaffCopies`: staff `chat_members` rows get `removed_at` with a revoke-device tap (that device), a switch-off, a removal or a security reset (all the person's devices). The API does not yet refuse a read for a person with removed rows: moderation's own device check does. **(f)** The read returns the newest 5000 envelopes and `olderNotShown`; staff-web believes it only with exactly 5000 envelopes, then counts no gap before a sender's first line. A lying API can therefore hide the start of a chat only behind 5000 real envelopes. "Older messages not shown." is COPY-UNSIGNED.
10. **Design task 10 (N10): the chat key worker.** `src/keys/` (`chatWorker.ts`, `keeper.ts`, `reader.ts`, `deviceKey.ts`) runs only in a dedicated module Worker that the page starts from `chat/client.ts`; the page's own import graph never reaches `src/keys/`, `@x2f/protocol` or libsodium (`test/workerBoundary.test.ts`). The device key is a pair of non-extractable WebCrypto keys (see 13, re-review B1). The worker holds each opened chat's key as a `Uint8Array` zeroed on `forget` (the screen's unmount) and on `pagehide`. The page gets the device's public halves, the lines under an opaque handle, and the sealed message to post; the pinned moderation keys are the worker's own build value, never the page's. The worker refuses a seal dated more than 10 minutes from its own clock (`SEAL_CLOCK_SKEW_MS`), so a page script cannot mint countersigns for use long after it is gone.
11. **Residual (task 10), corrected by the re-review (m4).** What B1's fix now guarantees: no secret byte of the device key exists anywhere this origin's script can read. The keys are non-extractable WebCrypto CryptoKeys in IndexedDB, so page script (an XSS, an extension) cannot export them or decrypt them out of a record (the e2e probe checks it in a real browser). It cannot carry the real device key away, so once it is gone it cannot open later re-wraps to that key. What it still can do, while it runs on the staff origin: use the stored keys itself (sign a countersign, derive the X25519 secret for a re-wrap it is handed) and ask the worker to open a chat or seal a text, as the moderator could. **And it can plant a key pair it knows** (re-review 2 m3): it can store a v3 record holding keys it generated and kept the bytes of, so the case page shows "Confirm this device" again; one routine-looking tap by the moderator then certifies the attacker's key for 365 days, usable from anywhere with a staff session or a compromised API. This is inherent (the confirm dialog is the page's); B1's storage cannot prevent it. The countermeasure is the alert: every certification alerts the owner (in-app and pushed, `staff-device-certified`) and the person (their own alerts, and their Jabber when set up, through the account-change path), so a certification nobody expected is seen and the device revoked. Limits that stand:
    - A countersign stays usable about 15 minutes after the page closes: the worker accepts an issuedAt up to 10 minutes from its own clock, and moderation accepts one from 5 minutes back to 1 minute ahead.
    - Chat keys (TK) and plaintext pass through libsodium's WebAssembly heap in the worker, which `fill(0)` does not reach; nothing there is zeroed. The worker's memory is also not zeroed if the browser kills it (only on `forget`, `pagehide` and unmount).

12. **Lead calls after the e2e run (18 Nov).** libsodium-wrappers 0.8.4 has no JavaScript fallback, so STAFF_CSP's script-src is now `'self' 'wasm-unsafe-eval'`, as the trader app's: WebAssembly compilation only, never `'unsafe-eval'` or `'unsafe-inline'` (a test pins both out). Where the crypto library still cannot load, the worker answers `crypto-unavailable` and DeviceCard shows its own fault (COPY-UNSIGNED, DESIGNER-REVIEW). "Confirm this device" is a secondary button, so ModCase keeps one primary action; the e2e checks ModCase parity on an unconfirmed device too.
13. **Re-review B1 (lead call): the device key is WebCrypto, non-extractable.** Made in the worker with `generateKey({ name: 'Ed25519' }, false, ['sign', 'verify'])` and `generateKey({ name: 'X25519' }, false, ['deriveBits'])`, stored as those CryptoKey objects in IndexedDB (record v3: the public halves and the two private keys; no AES wrap key, no bytes). The countersign is `subtle.sign('Ed25519')` (protocol `Signer`; `makeModCountersign` checks the signature by signPublic before sending). A re-wrap is opened from `subtle.deriveBits('X25519')`, then libsodium's remaining crypto_box_seal_open steps: nonce = blake2b-24(epk || pk), k = HSalsa20(shared, 0^16) (protocol `hsalsa20`, as the standard wrappers build lacks it; checked against `crypto_box_beforenm`), `crypto_secretbox_open_easy` (protocol `openSealedWith`, checked against libsodium's own `crypto_box_seal_open` on the same inputs). An all-zero shared secret opens nothing. On load the keys are checked to be the stored public keys' by use (`deviceKeysMatch`: a signature, and an X25519 against a fresh ephemeral key). A browser without Ed25519 or X25519 in WebCrypto gets `crypto-unavailable`, never a raw-key fallback. An older record (v1, v2) is deleted with its AES wrap key and a new key made, which the person certifies again (nothing had landed); a v3 record that does not check out stays `bad-record`.
14. **Re-review M1, M2, and re-review 2 m2.** A security reset revokes the person's devices as of min(the reset tap's signed issuedAt, now), as N5. The gate keeps `devicesRevokedAt` per person, set only from times the API's clock signed (an applied switch-on's or reset's issuedAt), since certifications carry the API's clock; a certification issued at or before it never counts (`device-before-revoke-person`), a pending tap from before a switch-off included. A switch-off or removal the gate sees revokes by its own clock and is covered by `before-off` with its 2-minute allowance, never by the watermark (re-review 2 m2: a gate clock a few seconds ahead had made a fresh confirmation after a switch-on a dead end). Likewise a device's own `revokedAt`: a revoke-device tap revokes as of its signed issuedAt (never later than now) and is compared strictly; a revocation by the gate's clock (`revokedOnGateClock`) is compared with the same 2 minutes.
15. **Re-review m5, m6, and re-review 2 m1.** A notice the API refuses with a 4xx other than 401, 408, 409 or 429 is not posted again (401 is the API's transport check: `stale` clocks, `replay`, `bad-signature` during a key rotation; 408 a timeout; all transient) (moderation migration 021: `refused_status`, `alerted_at`); moderation reports `chat-notice-stopped` and the API raises one owner alert (`chat-notice-refused`, in-app; its message COPY-UNSIGNED), re-sent each pass until the API takes it. A 5xx, 401, 408, 409, 429 or network error keeps retrying. Re-review 2 m4: the all-zero shared-secret check in `openSealedWith` is constant time (an OR over every byte).
