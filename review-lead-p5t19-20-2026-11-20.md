## Blocking

**B1. schema.test.ts fails (3 tests), and 317 must be renumbered.** `apps/api/test/schema.test.ts:44-46`, `:194`, `:272` (the three exact `migrate()` lists) do not include `317_review_disputes.sql`. The failures: "applies every migration once on an empty database, then nothing", "009: an existing username…" and "010 carries existing rows over…". Each one shows `+ "317_review_disputes.sql"` in the diff. The builder never ran this file.

How the migrator handles 317 (`apps/api/src/db/migrate.ts:17-38`): it sorts file names and applies each one whose name is not yet in `schema_migrations`. It does **not** compare against the highest number applied. So a database that has already run up to 750 does **not skip** 317. It applies 317 last, after 750. A fresh database applies it between 316 and 324. The two orders differ. Today that is harmless: no migration from 324 to 750 touches `reviews`, `reviews_final` or `review_disputes` (I grepped them; only comments mention reviews). But the two orders can drift apart later. They also give `schema_migrations` a different order on staging than on a fresh test database, and the exact-order lists in schema.test assume that order.
Fix: rename the file to the next free number above every branch's numbers, not just main's. 751 is taken by `wip/lead-p5t11-past-rep` (751_pastrep_revoked_by) and 760 by `wip/lead-p4t26-limits` (760_account_limits), so 752 works if no other branch claims it first. Then append the new name at the end of all three lists in schema.test.ts. Also update the "317's reviews_final" mentions in `apps/api/src/reviews/disputes.ts:7,134` and the migration's own header.

## Major

**M1. Any role but x2f_purge can remove or trim a review with no real decision, by inserting an already-decided dispute.** `317_review_disputes.sql:28-41` and `:58-60`. `review_disputes_decide_once` guards only UPDATE. INSERT has no guard, so a row can be born `status = 'removed'` (or `'comments-removed'`) with any `decided_by`, the subject's own id included (it is only an FK to accounts). The reviews_final exceptions at `:96` and `:110` check only that such a row exists. So the trigger's "only as a decided dispute says" holds for the API's code path, not for the database.
I proved it with direct SQL as the app role: `insert into review_disputes (… status 'removed', decided_by = <subject id>, …)` followed by `update reviews set removed = true` → both succeed (probe P1). The same works for comments-removed (P5).
The app role owns the tables and could disable triggers anyway, so this is defence in depth, not a remote hole. But 301 and this migration make the database the guard for a permanent record, and the claim should be true.
Fix (engineering): add a BEFORE INSERT trigger that requires `status = 'open'` and null `decided_*`. Optionally have the reviews_final exceptions also require `d.decided_by` to be a staff account.

**M2. A decided dispute can be deleted, which erases the audit and lets the subject dispute again.** Same file, `:28-60`: nothing refuses DELETE on `review_disputes` (and TRUNCATE). Probe P2: after a moderator decided `stands`, `delete from review_disputes where id = …` as the app role succeeds, and `POST /v1/reviews/:id/dispute` then answers **201** again. That defeats the one-dispute-per-review rule and the "kept so the decision can be checked" promise. For a `removed` or `comments-removed` decision, the review keeps its mark but loses the reason and who decided it.
Fix: a BEFORE DELETE / TRUNCATE trigger that refuses, except for the cascade from a review delete. The R-011 erase runs as x2f_purge, so allow `pg_trigger_depth() > 1`, or allow it when the parent review row is already gone.

## Minor

**m1. No test pins "the stars stay" inside the comments-removed exception.** I removed `'stars'` from the protected rest (`317_review_disputes.sql:99-100`: `… - 'comments_removed' - 'stars'`) and reviewDisputes plus reviews stayed green (40/40). The existing `update reviews set stars = 5` assertion (`reviewDisputes.test.ts:263`) runs only **after** the trim, where `not old.comments_removed` already refuses it. The real trigger does refuse a trim that also changes the stars (probe P5). Add that case: after a decided `comments-removed`, one UPDATE that drops the note and sets stars, and one that sets neutral/stars null, must both be refused.

**m2. The trigger cannot tell which comments the moderator chose.** `:103-108`. Once a `comments-removed` decision exists, the trigger accepts any non-empty subset trim: the note can go even if the moderator removed only a phrase. The API writes exactly the moderator's choice (`disputes.ts:151-175`), so this is a known limit, not a bug. Note it in the migration comment, or store the removal on the dispute row and have the trigger compare against it.

**m3. Only the newest 20 reviews can be disputed** (`apps/api/src/reputation/profile.ts:31,154`). The id and `disputable` arrive only through the subject's own profile, which lists `PROFILE_REVIEWS = 20`. An older bad review has no Dispute button and no other way to get its id. Owner/lead question below; recommend a paged "my reviews" list later.

**m4. `review.disputed` logs the subject's side** (`apps/api/src/reviews/routes.ts:133`, actor `{ kind: 'trader', side }`). It carries no account and no trade code, so it is fine. Listing for completeness: the log keeps "the person a review is about was the seller" forever, beside a dispute id that points to the review. That is harmless, since the review itself stores reviewer_role.

## Checked and fine

- **Who can dispute / 404 vs 409:** `openReviewDispute` (`disputes.ts:51-63`) locks `where r.id = $1 and r.subject_id = $2`. The reviewer, a stranger, an unknown uuid and a non-uuid all get the same `404 not-found`. `409 not-disputable` and `409 review-disputed` are reachable only by the subject, so nothing leaks. One dispute ever per review: the unique index plus `on conflict do nothing` (except M2).
- **Staff view:** `listOpenReviewDisputes` (`disputes.ts:93-121`) returns the review (stars, phrases, badges, note, method, month, the writer's side), the reason, and `trade_code` while it exists (null after purge, tested). It never returns an account id or name. The staff-web screen shows the same. Perm `reputation.review`; a helper gets `forbidden` (tested, and in matrix).
- **Public view:** a removed review is gone from the profile, the trade-review view (the writer's own too, `routes.ts:158`), `% positive`, the count and the signed record. An under-review review is listed with "Under review" and counts in no figure. Comments-removed keeps its stars and counts.
- **Ids:** a review id appears only on the subject's own profile (`profile.ts:154`); not in `toPublicReview`, the trade view, staff output or logs (the logs carry only the dispute id).
- **Logs:** `review.disputed {disputeId}` and `review.dispute-decided {disputeId, outcome}`, with trade code null. No reason, decision text or note (tested against the log table and the process logs).
- **Won/lost fix:** `wonDisputesLiveSql` now has `rulingCountsSql` (`summary.ts:122`), mirroring lost (`:103`). A pending appeal counts for neither side (tested). The purge never deletes a trade with an open dispute or appeal (`tradeDeleteDue`), so `purged_won`/`purged_lost` are only ever added once a ruling is final.
- **Purge idempotence:** reputationTotals pins summary, profile and tradeCap as identical before purge, after it, and after a second pass. My probe P4 adds an under-review review and a removed review, and compares the summary, `tradeCap`, the public and own profile JSON and the signed record before, after and after a re-run: all identical.
- **tradeCap:** reads completed trades only, never reviews. Unchanged by this branch, and pinned equal across the purge.
- **reviews_final otherwise:** stars never change on any path. `removed` never reverts. A removed review cannot be trimmed, and a trimmed one cannot be removed or trimmed again. DELETE is still refused except for x2f_purge, and x2f_purge cannot write the marks (column grants plus the trigger). A decided dispute row is frozen, `decision_reason` included.
