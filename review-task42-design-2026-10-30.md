## Verdict: CHANGES REQUIRED (4 Important, 6 Minor)

The direction is right. Option A + B-above-cap is the best of the three options, and the rejections in 2.4 are correct (Monero has no threshold inside one party; a server signer breaks 3.1). Caps, revocation, the takeover flow, the counterparty's unchanged view and the audit list all hold up. But the security argument needs fixing in four places before the owner is asked q14. In two of them the owner question promises something the design does not deliver.

## Important

**I1. The hole in section 1 is already open for owner trades, so the delegation alone does not close it.** (`:34`, `:37`, `:159`, `:267-270`)
The design says the only defence against an API key in the account's slot is "the real party's device is in the trade and notices" (`:34`). Then it says a member scheme must not open "API registers its own key as a member" (`:37`). But on main, the moderation service binds a slot to nothing about the account. `checkWork` (`apps/moderation/src/attest.ts:47-51`) checks only each key's proof of possession for its code and role (`identityProofValid`, `attestation.ts:92-110`).
*Failure scenario, today and after 42a as written:* a compromised API makes a take "by account X" (a reputable account) against a real counterparty. It registers its own per-trade identity in X's slot without marking the slot as a member's. The moderation service attests it, since both proofs are valid and the slot is not "a member's" (`:91`, "For a trade slot the API marks as a member's"). The counterparty sees a normal attested trade with X's reputation. No owner device or member device is in the trade, so nobody checks `not-me`. The delegation never comes into play, because the API simply doesn't mark the slot as a member's.
*Fix:* either (a) bind EVERY account slot. The pinned key (call it the account key, not the team key) signs a binding for each owner trade too, or the owner registers an account-device key the same way. The moderation service then refuses any account-slot identity without a valid binding under the account's pinned key, owner or member. Or (b) narrow the claim honestly: the design closes "API adds a member" but not "API trades as the account", which stays a known limit of spec 3.3. In that case `:159` "Cannot add a member key" must not read as the 3.1 guarantee. Lead decision: I recommend (a), since it is the same crypto and turns the delegation into a real guarantee. Either way, the "Compromised API" row and recommendation point 2 must state what is and isn't covered.

**I2. The team-key pin is trust-on-first-use through the API.** (`:51`, `:61`, `:160`, `:164-170`)
"The first registration sticks", and the API forwards it to the moderation service. The owner's receipt check (`:61`) protects only an owner who registers. *Failure scenario:* a compromised API pins its own K for every account that has never set up team signing (almost all of them). It then signs delegations for an invented member and fills slots that pass all 10 checks. The owner's device never sees a receipt, because the owner never set up team signing. The reset path (`:166-169`) also runs through the API, with a 24 h hold. If the API suppresses the pushes, nobody vetoes inside the hold.
*Fix:* the moderation service must not accept a pin that the account owner's device cannot later detect. For example: the owner's device fetches a moderation-signed "pin status for my account" on every app open, and on any K it didn't make shows a security alert and refuses to trade until the owner resets. A new pin is usable only after a hold, during which that check runs. Also state the residual plainly (an account whose owner never opens the app can be impersonated). With I1(a), this becomes the bootstrap of the account key for all accounts. It also needs a migration story for existing accounts (first owner open after the update registers the key, and member slots are refused until then).

**I3. The holder lease is the only guard against cross-device nonce reuse (R26), and the API controls it.** (`:118`, `:124-129`, `:128`)
Today R26 is met inside one device: a Web Lock per trade (`runtime.ts:11-12`), plus the rule "never resume a save older than the last signature; after any resume, run a fresh exportState/importState round before cosign" (rulings R26). The handover blob is exactly such a save (the `PartyState` with exported nonces), and it now lives on two devices. The design says a lease "cannot sign anything" (`:128`). But a compromised API, or an honest one that moves the lease during takeover while the member's phone is online and mid-round, can let both devices sign from the same saved nonces. *Failure scenario:* the member's device co-signs release attempt n from the saved export. The owner's device imports the blob (same export) and co-signs a different tx set for a refund. The account's key share leaks to the counterparty, who then holds two shares and can sweep alone. That breaks 2-of-3 against a party, not just availability.
*Fix:* the takeover import must never sign from imported nonces. On import, the owner's device discards the blob's exported/cosign state and starts the next attempt with a fresh export (R26's "fresh export after any resume"), and the party protocol's attempt numbers must make the counterpart follow. The member's device must stop for good when it sees a higher holder epoch. Write this as a rule in the doc, mark 42b's security review to check it, and fix `:128` to say what a lease move can and cannot do.

**I4. Two owner questions promise controls the design doesn't deliver, so the owner's consent would be uninformed.** (`:280`, `:289`, `:66-74`; q14 b, f)
- *q14f / Q6 (`:289`):* "your phone keeps an encrypted copy". In the design, X2F's server stores the sealed copy (`PUT /v1/trades/:code/handover`, `:118-120`). The owner's phone can open it, but it does not keep it. This is new key material held by X2F (ciphertext only). It changes spec 8's row "keys never leave the device", and the retention list in 4.1 / R36 must name it. The question must say "X2F's server keeps an encrypted copy that only your phone can open, deleted when the trade ends". Section 5 must list the spec 8 and 4.1 edits next to the 3.3 bullet.
- *q14b / Q2 (`:280`, `:178`):* "Can release coins as seller" can't be enforced by keys. The delegation format (`:66-74`) has no release field. A normal release is seller + buyer with no moderator, so the moderation service never sees it, and the member's device holds the seller key. A member with a modified client can release whatever the toggle says. If the toggle stays, it is an app-side setting only. The question and the copy at `:178` must say so (or drop the toggle and rely on `sides` + caps, which ARE enforced at attestation).

## Minor

- **M1. `walletSet` can't be checked from a hash alone** (`:72`, `:101`). Check 10 needs the list. Specify that the delegation (or the API, per check) carries the sorted list of `sha256(address)`, and that the moderation service recomputes the hash and checks membership.
- **M2. Owner's device lost** (`:162`): members keep trading, but every new handover blob is sealed to a key no device holds, so the stranding risk A-lite describes grows silently. Suggest the moderation service refuse new member slots once the owner's renewal is overdue by N days (or the API shows "backup can't be opened"). At least state it in the table.
- **M3. Caps on attested-but-never-funded trades** (`:99-100`): `per24hAtomic` and `openTrades` count trades attested but cancelled at setup timeout. Say whether those free up (open: yes when cancelled; 24 h: probably count). Otherwise a counterparty who abandons setups can lock a member out.
- **M4. Silent renewal** (`:77`): it re-signs with no confirm-it's-you. Fine, but say that renewal never widens scope, and that it doesn't run for a member the owner removed while the renewal was queued (race with `DELETE`).
- **M5. q14d vs launch slice** (`:275` vs q14d "[yes]" for above-limit approval): the smallest slice refuses above-cap takes. Tell the owner that the "yes" may ship after launch.
- **M6. Section 5 notes** (`:294-300`): add the R44 rewrite text and the spec 8/4.1 edits (see I4). Add that R26's rule extends across devices (see I3). Add a line that 42a's security review covers I1/I2 (account-slot binding and pin bootstrap).

- Task 18 / R44: payout wallets, members and deletion stay owner-only (members only use wallets the owner signed in). 2FA members, the audit in the same transaction, the chat label and Task 21 CantDoThat refusals are all respected.
