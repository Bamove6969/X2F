The return goes out at once (`settling` → `refunded`/`buyer-cancel`). `confirm-cancel` is `too-early` until 10 confirmations are counted by X2F's node, or `cancelConfirmableAt` is recorded. The 48 h auto-close is a `tick` on `cancelConfirmableAt + 48 h`; it is frozen and shifted by pause/resume, and `nextDeadline` names it. The tripwire is green (above).

## Races checked
- **Cancel vs "I've paid", both orders:** `applyEvent` locks the row (`loadTradeRow(…, true)`), so the two events run one after the other. Cancel first → `settling`, and `mark-paid` from `settling` is `wrong-state`. Paid first → every cancel event is `wrong-state` (`paidAt`). After the settle window lapses back to `secured`/`refund_requested`, `mark-paid` is allowed. The late refund then keeps the dispute (I1), and the device has dropped its intent (I2).
- **Cancel refund vs release:** `release-started` is only allowed from `secured`/`paid`, and `buyer-cancel` never from `settling`, so only one settlement is ever started. After a lapse the other one can be started, but only one tx can spend the escrow, and `settled` records whichever landed. A refund that lands while `settling` = release becomes `refunded`/buyer-cancel with `paidAt` null (awaiting), which is correct: the seller has the coins.
- **Auto-close vs confirm:** after a confirm, `cancelAutoCloseAt` is null, so a later tick does nothing. After an auto-close, `confirm-cancel` is `wrong-state`. Neither can close twice.

## New items (Minor)

**N1. The seller's screen still calls a cancel refund that landed after "I've paid" a cancel.** `apps/web/src/screens/trade/SellerCancelConfirm.tsx:135` (`when: (v) => v.settling === 'buyer-cancel'`), text at `:93-95`, button at `:120`.
Scenario: the trade is `refunded`/`buyer-cancel` with `paidAt` set, which is the I1 case. The seller sees "<buyer> cancelled before paying" and "Your input is needed to cancel this trade.". Confirm cancel is enabled once `useConfirmations` reads 10. Every tap gets 409 `wrong-state` → "Couldn't confirm the cancel. Try again." The screen stays "Cancelling" for good (the trade is never awaiting, so it never auto-closes) unless the buyer disputes. Round 1 asked for this so that "the seller isn't told '<buyer> cancelled before paying'"; the machine was fixed, the screen was not.
Fix: `when: (v) => v.settling === 'buyer-cancel' && v.paidAt === null`, so the seller falls through to the generic refunded slot, or give it a "The XMR came back to you after <buyer> marked paid" line with no button. Add a `sellerCancelConfirm.test.tsx` case with `paidAt` set.

**N2. `escalate` can reopen a cancel that is already confirmed: only the watch's SELECT guards it.** `apps/api/src/trades/cancelReturn.ts:49-59`, `packages/trade/src/machine.ts:481-488`.
The machine accepts `escalate` on any closed trade with `receivedAtomic > 0`, and a refunded buyer cancel always has that (the chain total does not decrease). I confirmed with a scratch probe that a confirmed cancel → `escalate` → `disputed`. The watch selects the stale codes and then applies `escalate` without checking again. If the seller's `confirm-cancel` commits in between (possible when the node has just caught up: the route asks it and records `return-confirmed`), or the confirmations route records `return-confirmed`, the trade is pulled out of "Cancelled"/"available" into a system dispute and an active trade (`closed_at` null counts toward the take cap). No coins move and the window is small. The comment "A race (another pass, a confirm) is a rule refusal" is therefore not true.
Fix: pass `applyEvent` a `within` guard that throws `TradeRuleError('wrong-state')` unless `awaitingCancelConfirm(prev) && prev.cancelConfirmableAt === null`. Or, in the machine, refuse `escalate` on a `refunded`/`buyer-cancel` trade with `paidAt` null unless it is awaiting with `cancelConfirmableAt === null`. Add an API test that confirms between the SELECT and the escalate (e.g. a stubbed `db.query`).

**N3. The 24 h escalation does not consult the node or maintenance.** `cancelReturn.ts:47-51`.
The stale SELECT escalates every awaiting refund older than 24 h whatever the reason. Scenario: X2F's node is down or resyncing for more than 24 h, or a long maintenance window (escalate is a system event and goes through while paused). Every buyer cancel settled in that window becomes a moderator dispute, reopened as an active trade for both traders, even though the refunds confirmed normally.
Fix: escalate only a row whose own lookup in this pass *succeeded* and still said null or < 10, i.e. run the lookup for stale rows too and skip on a throw. Also skip rows with `paused_at` set, or count the 24 h from `max(closed_at, last resume)`.

**N4. The buyer's `cosignPolicy` still allows building a mutual cancel in `paid`.** `apps/web/src/escrow/policy.ts:153` (`if (route('mutual-cancel')) return true;`).
The runtime no longer creates one in `paid` (CANCEL_STATES and the dropped intent), but the guard itself does not agree with "no cancel of any kind after I've paid", as I2 asked for buyer-cancel. Fix: for the buyer, `return state !== 'paid' && c.trade.paidAt == null` (or state in `funding|securing|secured|settling`), plus a `policy.test.ts` case. The seller's side (cosigner, coins return to it) can stay as it is.

**N5. Stale "90 days" comments.** `apps/api/src/disputes/routes.ts:207-208` ("a refunded trade only by the buyer within 90 days"), `apps/api/test/disputes.test.ts:407`, `apps/web/test/disputeSlot.test.tsx:4`. Change them to 48 hours (`TIMERS.disputeAfterRefundHours`).
