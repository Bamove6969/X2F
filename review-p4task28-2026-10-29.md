## Checked and found sound

- **Privacy of `GET /v1/news`** (apps/api/src/news/routes.ts): there is no session lookup. `requireSession` is per route and none is attached, so a cookie that comes along is never read and no session row is touched. The read is one SELECT (news.test.ts spies on the SQL). Request logging is off (`disableRequestLogging`), and the req serializer keeps only the method and the route pattern, never the address. `cache-control: no-store` comes from the global /v1 hook (app.ts) and is asserted in the test. No `news_seen` table exists, and `POST /v1/news/seen` answers 404 (tested). The web sends nothing back on reading (the e2e records no non-GET).
- **XSS and markup**: title and body render as React text nodes (News.tsx `Message`). There is no `dangerouslySetInnerHTML` and no link parsing, and the body is split on `\n+` into `<p>` elements. Control characters and U+2028/2029 are refused on the server (store.ts:46-47), and the DB CHECKs enforce the lengths even for a write that skips `cleanDraft`.
- **returnTo**: News reads it through `returnToFrom` → `safeReturnTo` (same-origin path only, no `//`, no backslash, no controls, 2048 max). The nested `/terms?returnTo=/news?returnTo=…` encoding round-trips (unit test plus e2e).
- **afterLogin chain** (authApi.ts:73): Terms first, then News, then returnTo. A failed news read returns false and login goes straight on. Login, backup login and the hold-continue path all use it. Setup does not, so sign-up is unchanged. It cannot loop: once News is visited the mark is set, and returnTo=/news only shows the page a second time with nothing new.
- **localStorage failures**: every access is in try/catch. My probe (storage getter throws) shows the page renders "1 new message." and Continue works.
- **50 cap and order**: `order by published_at desc, id desc limit 50` is covered by the `news_newest` index. An edit sets `edited_at` and keeps its place, and is not new again (tested). Ids only count up (tested).
- **Migration 115**: unique. No other `115_*` exists on any origin/wip/* or origin/claude/* branch, and the main line ends at 111. The plan's file list says `2xx_news.sql`, and 115 follows the lead's instruction.
- **CLI** (tools/news.ts, news/cli.ts): parameterized SQL only. A missing DATABASE_URL gives a message and exit 1, the pool is closed in `finally`, and the output is one JSON line. The missing activity-log entry is stated in the header comment and moved to NEEDS_PLAN4_STAFF_API.
- **Tripwires** (apps/api/test/news-tripwire.test.ts, apps/web/test/news-tripwire.test.ts): they check the local tree only (existsSync/readFileSync under the repo root) and are green now.
- **Accessibility**: h1 then an h2 per article, each `<article aria-labelledby>`, `<time dateTime>`, `aria-busy` while loading, `role="alert"` on the error with a retry button, one primary action, and the phone layout passes at 390 and 360. A 50-character Matrix URL in the body did not overflow at 360 (my probe).

## Minor

- **M1. Nothing in the app links to /news.** App.tsx:159 adds the route, but no menu, nav or other screen links to it. The plan's "the menu shows the count of new ones" is deferred under NEEDS_DESIGN_NEWS, so even a plain entry is missing. Failure scenario: a trader stays logged in for days, the owner posts "Planned upgrade tomorrow 10:00 UTC", and the trader never sees it before the upgrade, because News only opens at the next login and there is nothing to tap. Task 29's "Check the News section" also has no destination in the UI until it adds its own link. Suggest a plain "News" entry made from existing UI-kit parts, or record the gap explicitly in coordination.md at landing. This is the lead's call, since it touches the design rule.
- **M2. The page and the store read the seen mark from different sources.** News.tsx:70 takes `seenBefore = readLastSeen()` (storage), while `markSeen` and `hasUnseenNews` use the cached `seen()` (news-model.ts:84, 89). Scenario 1, storage blocked: a second visit to /news in the same page load shows every message as "New" again, while `hasUnseenNews` already reports none. Scenario 2, two tabs: tab A cached lastSeen = 5; tab B shows up to 8 and stores 8; tab A then opens News, which holds 7, and `markSeen(7)` compares 7 against its stale 5 and writes 7, lowering the mark, so message 8 shows as new again. That is the safe side, but it is wrong. Fix: in `markSeen`, take `Math.max(stored, cached)` before writing, and use `seen()` in News.tsx.
- **M3. `afterLogin` waits on `/v1/news` with no timeout** (authApi.ts:73; `fetchNews()` in `hasUnseenNews` passes no signal). Scenario: the DB pool is saturated or the news query hangs after a successful login, and the login screen sits on its spinner with no way on. Before this change the same was true only of `me()`. Suggest `AbortSignal.timeout(~5 s)`, and on timeout go straight to returnTo.
- **M4. The list order and "new" use different keys.** "New" is `id > lastSeen`, but the list is ordered by `published_at` (store.ts:73). If the server clock steps back between two posts (an NTP correction or a restored VM), the newer id gets the older date. It then sorts below older messages, and its "New" badge sits mid-list, under messages already seen. Ordering by `id desc` (or refusing a `published_at` earlier than the current max at insert) keeps them in step.
- **M5. The CLI takes the next flag as a value** (cli.ts:30, `flag`). `news add --title --body "Server down"` publishes, at once and to every reader, a message titled `--body` with the body "Server down". There is no preview or confirm step. Suggest refusing a value that starts with `--`, or printing the draft and asking for `--yes`.
- **M6. No unit test for storage that throws.** apps/web/test/news.test.tsx covers junk values but not a `localStorage` getter that throws (some private modes and blocked site data). The code handles it (my e2e probe passed), but nothing guards that.
- **M7. The `role="status"` live region is created along with its text** (News.tsx:102). Screen readers often skip a live region whose first content arrives in the same render that inserts it, so "2 new messages." may never be announced. Keep the region mounted from the start, with empty text while loading.

## Nits

- `idOf` accepts 16 digits, which goes past `Number.MAX_SAFE_INTEGER` (cli.ts:35). `delete 9007199254740993` would target …992. This is harmless with identity ids; `{0,14}` is enough.
- Bidi overrides (U+202E…) are explicitly allowed in titles (news.test.ts:133). The owner is the only author, so this is not an injection risk, but the staff editor (Task 16+) might strip or show them.
- URLs in a body are plain text, not links (no link parsing, which is safe). Once the community links go into News, readers have to copy them by hand. That belongs to the design or owner decision.
- `serverNow` is returned but the web ignores it. Fine for now.
- `GET /v1/news` has no rate budget and is an unauthenticated DB read on every call. Other public lists (methods) work the same way, so this is an existing pattern, not a new risk.
