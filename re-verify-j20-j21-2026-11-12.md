## wip/lead-j21 (RED 877832b9, fix ee34125f, on c2975a31)

### F5: grants a role already holds, in staff/members.ts

**The fix.** A new function, `perPersonGrants(role, grants)`, keeps only the grantable permissions
that the role does not already hold, sorted. It is used in three places:

- `listMembers` uses it to build each member's `grants`.
- `PUT …/grants` uses it on the list it stores. The tap still binds the list exactly as sent, and
  the route answers with the list it stored.
- `PUT …/role` uses it to rewrite the stored grants for the new role.

The comment has been corrected as well. The staff-web StaffGrants screen still ticks a box the role
holds from the role itself (`can(member.role, p)`), not from the stored list. Its draft holds only
the stored per-person list and is reset from the server's answer after a save, so the screen and the
stored data stay consistent.

**It is fixed at the cause for new data.** A box the role holds is no longer stored or listed. A
promotion now drops the stored grant, so a later demotion does not bring it back.

**A test pins it.** members.test.ts, "a role-held grant is not stored or shown … (F5)". It covers a
senior's stored Feedback left from before (not listed, and dropped on save), and a moderator who is
ticked, promoted, then demoted (the stored grant is cleared and the feedback page answers 403).

- **Red on the old head:** I ran it with c2975a31's `staff/members.ts` and it failed (1 failed).
- **Green on ee34125f.**

**R1 (low; residual of F5): a grant the role already holds that was stored before this fix still
comes back after a demotion.**

- **Cause:** `set-role` filters the stored grants only by the NEW role. A senior whose stored grants
  already contain `feedback.read` keeps it when demoted to moderator, because a moderator does not
  hold it. While the person is a senior, the list hides that grant, so the owner cannot see it or
  clear it.
- **Reproduced:** a scratch test, not committed, on ee34125f. I stored `{feedback.read}` on a
  senior and demoted them to mod. The stored grants were `['feedback.read']` afterwards, not `[]`.
- **When it can happen:** only on a database where such a row exists. Before J-21 nothing in the UI
  wrote per-person grants, so this is probably empty before launch. It is still the exact F5
  behaviour.
- **Fix (one line):** in `PUT …/role`, also drop what the OLD role held. `lockTarget` already
  returns it:

  ```ts
  perPersonGrants(role, perPersonGrants(target.role, held[0]?.grants ?? []))
  ```

  The alternative is a one-off migration that removes grants each row's role already holds.
- **Test to add:** the scratch case above (senior with a stored Feedback, demoted, stored grants
  `[]`, `/staff/v1/feedback` answers 403).

## wip/lead-j20 (RED 33e9c786, fix e6f1e0dd, on 818bb016)

### N1: migration 380's backfill queued a false "account change" Jabber notice

**The fix.** In migration 380, the `update team_members set first_login_at = joined_at` backfill now
runs after the trigger has been dropped and re-created with `first_login_at` ignored (moved from
line 29 to the end of the file). Nothing earlier in 380 depends on the backfill. The column is
added first and the trigger names it, so the order is valid. 380 has not shipped, so editing it is
fine (as the review said).

**It is fixed at the cause.** The backfill now writes a column the trigger treats as bookkeeping,
so it queues nothing. A real change to a team member row still notifies.

**A test pins it.** The new teamLimitsMigration.test.ts runs against real Postgres:

1. Migrate up to 380.
2. Seed a team account with Jabber on and a joined member, then empty the outbox.
3. Apply 380.
4. Check that the member got `first_login_at` and that the outbox has no row for the team.
5. Check that a real abilities change afterwards queues exactly 1 row.

A second case checks in the source that the first-login notice goes through `jabber_queue`, not a
direct outbox insert.

- **Red on the old head:** with 818bb016's 380 it failed:
  `expected [ { kind: 'account-change' } ] to deeply equal []`. That is the exact spurious notice
  the review reproduced in psql.
