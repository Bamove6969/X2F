## Hunt results (no defect found)

- **IDOR:** both routes filter on `account_id = $1` (the session's account). The SELECT ... FOR UPDATE and the UPDATE both carry it (routes.ts:589-592, the update after the loop). `'all'` expands only from `mine`. Another account's id, a removed id and an unknown id each come back `not-found` and are not touched. Pinned by offersBulk.test.ts:136 and :243.
- **Cap bypass:** none. The caps count live **and** paused offers, so turning an offer on never changes the count. The in-memory `same` and `total` (routes.ts:610-612) equal what `assertMayPost` counts for a relist (all other non-removed offers). The rows are read FOR UPDATE under the account lock, and every insert path (`POST /v1/offers`) takes the same account lock, so no post can slip in between. Concurrent bulk calls, bulk vs relist and bulk vs post all serialize on `accounts(A) FOR UPDATE`. The only writer without the account lock is PATCH pause/remove, which can only lower the count. Pinned by the caps test (:204) and the race test (:285).
- **Deadlocks:**
  - Task 5's take (take.ts:222-233 on wip/lead-p3-task5) locks accounts {taker, poster} in id order FOR NO KEY UPDATE (this conflicts with FOR UPDATE), then the offer FOR SHARE, then site_flags FOR SHARE.
  - Bulk(A) locks accounts(A), then site_flags FOR SHARE, then A's offers.
  - Both take A first before any A offer row. A bulk never waits on another account row, so no cycle exists, including when A is the taker.
  - A hold insert only takes a key-share lock on accounts. The emergency stop only updates site_flags, and FOR SHARE vs FOR SHARE does not conflict. PATCH pause/remove holds only one offer row.
  - No path holds an offer row and then waits on an account.
  - No take-vs-bulk test exists yet, because Task 5 is not on the line. See landing notes.
- **Hold and emergency stop when turning on:** `accountRefusal` runs after the account lock, with a fresh READ COMMITTED snapshot per statement.
  - A hold that committed before the lock is seen; one inserted after it waits on the key-share lock.
  - A stop being set waits on FOR SHARE, or is seen by it.
  - Every paused offer is refused with the reason. Offers that are already live are reported as done, which is correct.
  - Turning off has no guard. Pinned by :157, :176 and the hold/stop race in :285.
- **Behaviour after the `assertMayPost` split:** the checks are identical, in the same order, and give the same 409 codes. Task 4's offers.test.ts still pins post and relist for `trading-hold`, `trading-paused`, `no-wallet` and `too-many-offers` (lines 214, 222, 228-234, 324, 437-472). It passes on the trial merge.
- **Resurrecting a removed offer:** not possible.
  - Both the select and the update carry `status <> 'removed'`.
  - A concurrent PATCH remove either commits first, so the row is excluded, or is in flight. If it is in flight, FOR UPDATE waits and re-checks the row, so it is excluded.
  - A remove that arrives after the bulk waits for the bulk's row lock and then wins.
- **`'all'` racing a new post (API):** serialized by the account lock. The new offer is either in `mine` or created after the commit. This is consistent. For the web side of the same race, see M1.

## Minor

**M1. "Select all" sends `'all'`, which can switch offers the user never saw.**
- Where: apps/web/src/screens/myoffers/model.ts:72-74 (`idsFor`), called from MyOffers.tsx:137 and :140.
- Scenario: the user opens My offers on a phone. On the desktop they then post offer X and pause it. Back on the phone they tap Select all and Turn on. X goes live, and a stranger can take an offer the user meant to keep off.
- The screen reloads afterwards (`!known.has`), but X is already live.
- Fix: always send the explicit ids of the listed offers (the API's `'all'` can stay for other clients). Or, if the reply names an unknown id, say so in the summary.

**M2. Switch and Select names are identical for offers in the same market.**
- Where: MyOffers.tsx:161 (`aria-label`) and :181 (`aria-labelledby={titleId}`).
- The cap allows 3 offers per side, method and currency, and `offerTitle` holds only those three fields.
- Scenario: two "Sell · Zelle · USD" offers at different prices. A screen-reader user hears two switches named "Sell · Zelle · USD" and cannot tell which is which.
- Fix: label by title plus detail, e.g. `aria-labelledby={`${titleId} ${detailId}`}`, with an id on the detail span.

**M3. The Select button's visible text is not inside its accessible name (WCAG 2.5.3, Label in Name).**
- Where: MyOffers.tsx:161 and :166.
- When selected, the visible text is "Selected" but the name is "Select Sell · …".
- Scenario: a voice-control user says "click Selected" to deselect, and nothing matches.
- Fix: put the visible word into the name: "Selected: Sell · …" when pressed, or keep the visible text "Select" and let aria-pressed carry the state.

**M4. An "On" offer may not actually be listed.**
- Where: MyOffers.tsx:184-186.
- Scenario: during a trading hold or an emergency stop, an offer whose status is `live` shows "On", but `LISTED` hides it from everyone. The trader thinks they are visible and waits for trades that cannot come.
- Fix: a note on the screen when the account is held or the site is paused (for example `GET /v1/account/offers` returning `listed: boolean` per offer, or one account-level flag). This can wait for the board (NEEDS_DESIGN_MYOFFERS); note it on the tripwire.

**M5. More than 100 selected ids gives a generic failure.**
- Where: SWITCH_MAX_IDS (routes.ts, `= 100`) against `OFFER_CAP_MAX = 1000` for `offers_max_total`.
- Scenario: the owner raises the total cap above 100, and a user with 150 offers selects 120 (not all). The reply is 400, and the screen says "Something went wrong" every time.
- Fix: either clamp `offers_max_total` to at most SWITCH_MAX_IDS, or have the web send batches of 100. Far off with today's default of 20.

**M6. The e2e stub differs from the API for offers that are already live.**
- Where: apps/web/e2e/myOffers.spec.ts:54.
- With `refuseOn`, the stub refuses offers that are already live. The real API reports them as done, with no `refused` (routes.ts:602).
- The held test starts with all offers paused, so it passes, but a future test with mixed statuses would assert behaviour the API does not have.
- Fix: check `o.status === body.status` first, as the route does.

## Nits

- N1. The refusal precedence differs from PATCH. PATCH checks `method-unavailable` before the account refusals (routes.ts:448). Bulk checks the account first (:584, then :608). A held account with an under-review method gets `method-unavailable` from PATCH and `trading-hold` from bulk. This is harmless; document it or align it.
- N2. An uppercase UUID in `ids` is a 400 for the whole request (:576), while PATCH gives 404. The web only sends API ids, so this is fine.
- N3. The error summary uses `role="status"` for an error (MyOffers.tsx summary `<p>`). That is fine as polite; `role="alert"` would match the load-failure path.

## Question for the lead: R10 Terms vs turning offers OFF

- Both routes use `requireTrader`, so a trader on stale Terms gets 403 `terms-required`, and the web client redirects them to /terms (api/client.ts:134).
- `LISTED` does not check `terms_version`, so their live offers stay listed and takeable (the taker is the one checked).
- Result: when the Terms version bumps, a trader who does not want to accept the new Terms cannot pause their offers. They stay on the board under Terms they have not accepted.
- Options:
  - (a) Allow `status: 'paused'` (and `GET /v1/account/offers`) with `allowStaleTerms`. This needs a second preHandler or a check inside the handler, since `requireTrader` runs first.
  - (b) Hide offers of stale-Terms posters in `LISTED`.
  - (c) Accept it as is.
- I lean towards (b) or (a), because shutting things off should never sit behind new Terms. The same applies to Task 4's PATCH pause. This is a lead or owner call; it is not a finding against Task 36 as specified.
