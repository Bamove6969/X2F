## Important

**I1. A PGP key already on another account loops forever with the wrong message.**
Files: `apps/web/src/screens/setup/PgpChallenge.tsx:414-417` (and `Backup.tsx:317-318` for the second key).

- The server checks the fingerprint only at finish. `insertPgpKey` throws 409 `key-in-use` (apps/api/src/auth/pgp.ts:148), after the code has been proven. `registerStart` says so itself: "only `finish` ... says key-in-use".
- Verify maps every coded error that is not about names to "That code did not work. It may have expired: send a new message and try again."
- Failure scenario: someone pastes a key they already use on another X2F account (or reuses a shared key). They decrypt correctly and are told the code failed. "Send a new message" calls `registerPgpStart`, which succeeds, and the next Verify gets `key-in-use` again, with no end. This is the "no dead end" Revision 2026-10-28 on the shortest (PGP) route.
- Fix: map `key-in-use` to a sentence such as "That key is already used by another X2F account. Use a different key, or log in instead", with a link back to pgp-key and to /login. In Backup's SecondPgpKey, map `key-in-use` and `challenge-expired` separately from `code-invalid`.
- Add an e2e case: pgp/finish stubbed with 409 `key-in-use`.

**I2. After the account exists, browser Back reopens the sign-up steps. Continuing there tells the person their own name is "taken" and can make a second account.**
File: `apps/web/src/screens/setup/SetupFlow.tsx:48-52`. The `need(...)` guards check only `terms` and names, never `state.registered` or the session.

- Every step is `navigate` (push). After a passkey, security-key or password sign-up (`go('backup')`), Back returns to `/setup/login` or `/setup/password` with the flow state still in memory.
- Continue registers again. The server refuses with `display-name-taken`, which reads "That username is taken. Pick another." and offers "Change your names".
- Failure scenario: a phone user presses Back, believes someone took their name, changes names and finishes. That creates a second account and moves the session to it. The first account, with the passkey on this device, is orphaned.
- The PGP path has the same problem: Back from pgp-code to pgp-key, Continue, `registerPgpStart`, "taken".
- Fix: once `state.registered` (or the session is signed in), send `name`, `login`, `pgp-key`, `password` and the not-done `pgp-code` to `backup` with `replace`. Alternatively, use `navigate(..., { replace: true })` for the step after the register call.
- Add a test: register, `page.goBack()`, expect the backup step (or no register call).

## Minor

**M1. Dead branch since the switch to the typed client: the server's PGP key refusal sentence is never shown.**
File: `PgpKey.tsx:298`.

- The check is `e instanceof ApiCallError && e.detail`, but `authApi.registerPgpStart` throws `AuthApiError`, which carries `detail`.
- The server's `KeyRefusal` detail (pgp.ts:451, :605) is replaced by "X2F could not use that key just now. Try again". The person retries a key that will never pass.
- The client-side `inspectPublicKey` catches most cases first, so this is Minor. Use `errorCode`/`AuthApiError` (or check both classes) and add a unit test.

**M2. Rate limits and wait times are not surfaced.**
Files: register.ts, Login.tsx:175-176, Password.tsx:79, PgpChallenge.tsx:416-417.

- 503 `busy` (register/start budgets, limits.ts:59), 429 `slow-down` and `retryAfterSeconds` all fall into generic "try again" lines. `password-weak`'s `missing` is reduced to "does not meet the rules above".
- Task 30's review asked for honest wait sentences (`refusalText`). Reuse it here.

**M3. /terms retry loop.**
File: `Terms.tsx:254-263, 383`.

- If the version changes between `GET /v1/terms` and `POST /v1/account/terms`, the server answers 400 `terms-not-accepted { version }`.
- The screen shows "Could not save that. Try again", and every retry posts the same stale version. The person must reload.
- Fix: on `terms-not-accepted`, reload the version (and reset `read`/`ticked`).

**M4. The accepted version is not tied to the text shown.**
File: `termsText.ts:1-8`.

- The text is bundled in the web build. The version is the server's `X2F_TERMS_VERSION` env var, which can change without a rebuild, and an old cached bundle can stay open.
- A person can then "accept" version N while reading version N-1's text.
- Suggest a `TERMS_TEXT_VERSION` constant in termsText.ts. When `GET /v1/terms` differs, show "The Terms were updated: reload" instead of enabling I accept. A unit test would check the constant against the deploy config.

**M5. No test covers the passkey or security-key sign-up.**
File: `Login.tsx:156-166`.

- `registerWithWebAuthn(authApi, names, kind, deviceLabel(), acceptedTerms)` takes two adjacent `string` arguments, so swapping them would still type-check.
- No test checks that WebAuthn register bodies carry `acceptedTerms` and both names, or the cancel/`webauthn-failed` messages.
- Task 30's soft authenticator (or a stubbed `register/webauthn/*` pair with a stubbed `navigator.credentials.create`) would cover it.

**M6. The `terms-not-accepted` reset during setup is untested.**
Files: Login.tsx:168, Password.tsx:68, PgpKey.tsx:291, PgpChallenge.tsx:409. Add one e2e: the register finish returns `terms-not-accepted`, expect the Terms screen and the new version sent on the retry.

**M7. Integrated addresses get the generic message.**
File: `Wallet.tsx:37, 59`. The regex allows only 95 characters, so a 106-character integrated address gets "doesn't look like a Monero address". The server's `address-integrated` mapping (line 41) can never be shown. Accept 106 characters client-side and let the server answer, or detect integrated addresses locally with the same sentence.

**M8. Accessibility details.**
- The custom `role="radio"` groups (Login.tsx:194, Backup.tsx:204, Wallet.tsx:100) have no roving tabindex and no arrow-key support. Each option is a tab stop, which is acceptable but not the ARIA radio pattern. Native radios would be simpler.
- The "Scroll to the end to continue" hint (Terms.tsx:322) and the name help texts (Username.tsx:64, 85) are not linked by `aria-describedby` to the disabled tick box or the inputs.
- A screen-reader user meets a disabled checkbox with no stated reason.
