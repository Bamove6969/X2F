Recovery code: not a login combination

Everyone should have one, whatever their security level. It's the way back in if every other method is compromised, so keep it somewhere none of your other methods are: buried in the back yard, written on paper inside a fake rock, or in separate online storage. The wording can be funny; Claude Design will help. Using it to log in starts the 24-hour recovery hold.

Required at signup. The person ticks "I've written it down", then the next screen asks them to type it back to prove they did.

The cookie-theft measures you sent

What X2F already has, what's missing, and my view on each.

MeasureX2F todayLead's view
HttpOnly, Secure, SameSite cookiesDONEEvery X2F cookie has all three, plus the stricter __Host- prefix and SameSite=Strict.
HTTPS + HSTSHTTPS YES, HSTS TO ADDCheap. I'll add the HSTS header at deploy. It's a technical fix.
New session ID at login, short timeoutsDONEEach login makes a new session. Traders choose a 2–12 h idle logout (max 30 days in total). Staff get 2 h idle and 12 h in total.
Device-bound sessions (DBSC)NOT YETThe real fix for item 47. The browser holds a key that can't be copied, and the server checks it. A stolen cookie then doesn't work on the thief's computer. Chrome supports DBSC natively. For other browsers we can do the same ourselves with a key the browser keeps uncopyable. Suggest it as a new task before mainnet.
IP / browser fingerprint checksNOT USEDClashes with X2F's privacy promise and with Tor users, whose IP changes all the time. My recommendation: don't store IPs.
WAF / CASBN/ACASB is a tool for big companies watching their own staff, so it doesn't apply. A basic WAF can come with hosting later.
