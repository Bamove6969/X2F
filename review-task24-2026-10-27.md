**What passes:**

- **The API route (focus 2).**
  - `GET /v1/trades/:code/confirmations` (routes.ts:125-143) follows Task 6's rules. It needs a trader session (`requireSession({kinds:['trader']})`). A malformed code, an unknown code and a non-participant all get the same 404 `not-found`, before any node call. A trade with no settlement tx gets 409 `wrong-state`.
  - Only the trade's own `t.txHash` is looked up. Nothing in the request can name a tx.
  - The answer is `{confirmations, target}`, plus `payoutEnd` only for the buyer of a release. No address, amount or tx hash is in it.
  - A failed node call gives 200 with `confirmations: null`, and logs one fixed line. The test at confirmations.test.ts:162-174 proves the line carries no hash, code, address or node host.
  - `daemonConfirmations` (chain.ts:46-109):
    - Only a 64-hex hash is ever sent.
    - It caches each answer for 10 s, and concurrent requests share the pending promise. Failures are not cached. The cache holds at most 1000 answers.
    - A semaphore allows 4 lookups at once with 64 waiting, and each call has a 15 s timeout.
    - The node URL is checked to be a bare http(s) origin.
    - `height − block_height` is Monero's own count (`get_height` is top + 1).
  - The tests cover auth, 404 parity, the forged-query case, a purged payout, refunded trades, the default with no node, the cache, the timeout and the bound.
- **Hold timing and cancel (focus 3).**
  - `HoldButton` is unchanged from the main line. It starts on `pointerdown` (button 0) or on Space/Enter key-down, ignoring auto-repeat. It completes once per mount (`done` ref) after `holdMs` = 1500. `pointerup`, `pointerleave`, `pointercancel`, key-up, blur and becoming disabled all reset it.
  - CSS (`touch-action:none`, `user-select:none`, `-webkit-touch-callout:none`) and the suppressed `contextmenu` keep a long press from turning into a scroll or a callout.
  - The unit test pins 1499 ms (nothing happens) against 1500 ms (fires). It also pins the order: POST `release-started`, then `release()`, each exactly once.
  - On the server, `release-started` is seller-only, needs `secured` or `paid`, and needs `releasable && received ≥ sellerFunds` (machine.ts:478-482 on the main line). The hold is disabled until the box is ticked, while not releasable, and while busy.
  - **User activation does not apply here.** The release runs a `fetch` and a `postMessage` to the escrow worker, and neither needs it. So firing from the timer is correct for this button. Task 22's new `completeOn` defaults to `'hold'`, so merging Task 22 keeps this behaviour. Task 24 must not switch to `'release'`.
- **The explorer link (focus 4).** The href is the constant `https://xmrchain.net/tx/` plus the tx hash and nothing else (Released.tsx:10, 93-94). It has no address, tx key, amount or query. It goes through `ExternalLink`: https only, `target=_blank`, `rel="noreferrer noopener"`, and the global `Referrer-Policy: no-referrer` applies too. The link text, the note, `aria-label`s, `document.title` and history state carry no amount or recipient. The note's wording matches spec line 68.
  - The amounts and the counterparty's public name shown elsewhere on Released are the viewer's own trade facts, which the plan and board require. Only the poster sees the fee rows.
  - The seller never gets the buyer's payout ending: the API leaves it out (routes.ts:141), and the e2e test at release.spec.ts:257-264 checks it.
- **Copy, slots and phone sizes (focus 6).**

  - There is exactly one `data-primary` on SellerConfirm and none on Released (the board's only primary on Review is the Plan 5 rating).

## Important

   - On the main line, Task 12's runtime never resumes a release by itself on the seller's side. `autoKind` gives the seller no `'release'` (runtime.ts:957-962). A release is signed only after `act({type:'release'})` sets the intent (runtime.ts:982-985).
   - Trigger, any one of these:
     - (a) The POST `release-started` is applied, but its response is lost (mobile network). SellerConfirm shows "The release didn't start. Try again". The 5 s / 15 s poll then shows `settling`. A second hold is impossible because the button is now done, so `escrow.release()` is never called.
     - (b) The seller reloads or closes the page between the POST and `release()`.
     - (c) `act` throws before the intent is set (`escrow not running`, or the view not refreshed yet).
   - In each case the seller reads "Both signatures sent. <buyer> will be asked to rate the trade." Nothing is signed. After `settleBy` (15 min, machine.ts:316-317) the trade quietly drops back to `paid`.
   - The comment at :73 ("the escrow runtime keeps the attempt and retries") is only true once `act` has succeeded.
   - Fix:
     - In `settling`/`release`, base the done wording on `escrow.phase` (`signing`, `done`, `settled-without-device`), not on the view alone.
     - While the view says `settling`/`release` and the device phase is `ready` with no release under way, call `escrow.release()` again. It is idempotent at the runtime because `viewSupports('release', settling/release)` is true. Or offer a "Finish the release on this device" action.
     - Show `escrow.keepOpen`.
     - Tests: a lost POST response, then a view that becomes `settling`, still leads to `release()`. A remount in `settling` with a `ready` escrow calls `release()` once.
2. **Released.tsx:20 with seams.ts:39-42 and :52, and slots.tsx:49: a buyer who opens the room during `settling`/`release` never gets confirmations or the payout ending.**

   - Trigger: the board's normal buyer path (the buyer is in the room when the seller releases). The buyer sees "Checking…" forever and "on its way to your external wallet" with no ending, until a reload.
   - Fix: depend on `[code, txHash]` (or the state), and only ask once `txHash !== null`. Treat 409 as "not yet", not as "stop". Add a unit test: settling, then released, then the count shows.
   - In `settling`, the buyer also reads "<amount> is yours / Released by you and <seller>" before their own device has co-signed. Under a Task 12 refusal (`amount-unknown`, `view-mismatch`) it never will. Show `escrow.refusal` and error states here, as Task 25 does.
