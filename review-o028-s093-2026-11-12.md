## Findings

**M1 (moderate, web): after Unblock and then Undo, the screen shows a note the server has deleted.**
In `apps/web/src/screens/settings/Blocked.tsx`, `reblock` calls `mark(name, false)`, which keeps the row's
old `note` (and old `blockedAt`). On the server, the unblock deleted the row and the note, and the re-block
inserted a new row with `note = null` and a new `created_at`. So the user sees their note, with "Only you
can see this note.", and it is gone the next time the page loads. That is silent data loss behind a label
that suggests it was kept. The stale `blockedAt` dates from before this branch, but it is now visible as a
time.

Engineering fix (does not change behaviour): after a successful re-block, reload the list (or set
`note: null, blockedAt: <server value>`), so the screen shows what the server holds. Add a blocked.test.tsx
case: Bob has a note, Unblock, Undo, and no `block-note` is shown.

Whether Undo should *restore* the note is a product question (Q1).

**m1 (minor, API): the control-character check is narrower than S-094's.** `NOTE_CONTROL` refuses C0 and DEL
but allows C1 controls (U+0080–U+009F) and format characters: bidi overrides U+202E and U+2066–2069,
zero-width characters, U+2028/2029 and the BOM. S-094 (`team/notes.ts` `noteText`) refuses
`[\p{Cc}\p{Cf}]` except `\n`, so it also refuses tab. Only the blocker ever sees their own note, so the
risk is low, but aligning the two would keep one rule for "a private note". That is engineering, but it
does change which input is accepted, so it is the lead's call.

**m2 (minor, API):** extra keys in the body are ignored. S-094 refuses any key set other than
`about,text`. This is consistent with the other nudge/blocks handlers, so it is not a defect.

**m3 (minor, web):** the textarea's `maxLength={500}` counts UTF-16 units, but the server counts code
points. Notes with many emoji are capped lower on the client (stricter, never looser). Any 400, such as
a pasted control character, shows the generic "Could not save the note … Try again." text. That is
acceptable, but retrying will not help.

**m4 (minor, tests):** two gaps that are covered by construction but not pinned by a test. First, a
team-member 403 on PUT …/note. Second, a Jabber notice queued by a note-only update.

## Owner questions

- **Q1 (S-093): what happens to the note on Unblock or Undo?** The API deletes the note on unblock (as
  the migration states), and the Blocked screen gives no warning before deleting it.
  - Recommendation: keep the deletion. It is the most private option, and a note on someone you no
    longer block has no use. Fix M1 so the screen is truthful.
  - Optionally add a COPY-UNSIGNED line on rows that have a note: "Unblocking deletes your note."
  - Restoring the note on Undo would need the client to hold it and re-save it. That is possible, but
    it is a behaviour choice.
- **Q2 (design):** the note UI is not drawn (the Block board has no note). It is marked DESIGN and
  COPY-UNSIGNED in the file header and needs design sign-off.
