## Findings

### I-1 (Important, latent): `/internal/proof/read` returns unblurred proof bytes through the API
- `apps/moderation/src/internal/server.ts:65,179-184` sends the image bytes to the caller, which is the API. The API relays them at `apps/api/src/disputes/staffRoutes.ts:504-522` (`POST /staff/v1/disputes/:code/proof`) and `moderationClient.ts:proofRead`.
- **Who can get them:** any staff member who may work the case (`mayWork`: the assignee, a senior or the owner). A compromised API can get them for any trade with a non-closed dispute. It writes `activity_log` and `disputes` itself, so it can write the `proof.unblurred-opened` entry that moderation checks (`useEntry` reads that entry from the API's own database).
- **Today:** this cannot be exploited. `apps/moderation/src/main.ts` starts the server without `proofs`, so every read answers `no-proof`. But the path is built and tested to work as soon as Plan 5 passes a `ProofSource`. That is the same plaintext-through-the-API gap that the chat read was removed for. The design doc's 2.4 step 5 says to re-wrap K to the staff device key instead.
- **Fix:** remove `/internal/proof/read` and the staff `/proof` route, or tripwire them `NEEDS_P4_CHAT_MEMBERSHIP` the way chat read is: no route, plus a test that a signed call with a fresh entry gets 404. Plan 5 must not wire a `ProofSource` into this path.

### I-2 (Important, design-acknowledged): a compromised API can forge moderator messages in any attested chat
- `server.ts:135-148,186-195` with `apiView.ts`. Moderation seals `{text}` as `mod` with the chat's moderator identity whenever the HMAC is valid and an API-database log entry `chat.message-sent` (60 s old at most, never used) names a trade whose current dispute is not closed. All three of those inputs are under the API's control: the secret, `activity_log` and `disputes`.
- **Scenario:** a compromised API inserts a `disputes` row and a log entry, then posts "Moderator: seller, release now / send to X" into a live trade. The traders' apps verify it as genuinely from the moderator. Before Task 11 the API could not produce a valid `mod` envelope at all, so this is a new capability. The design doc's threat table (section 10, "API" row) does not list it among "what remains".
- Separately, the moderator's message text crosses the API in plaintext (`staffRoutes.ts:441-456`). That is interim and expected until design build task 10.
- **Fix:** build task 9 already plans this ("`/internal/chat/send` becomes countersign": moderation seals only text signed by a certified staff device key that its own `mod_chat_access` record shows on the case). Until then, either accept it explicitly in writing as an interim risk and add it to the design's threat table, or keep `/internal/chat/send` dev-only like the old chat read (design line 344).

### I-3 (Important, deployment): the socket's mode 0600 means the API must run as moderation's OS user
- `server.ts:216-240` sets the socket to 0600, and its comment allows "the API, run as the same user". Linux needs write permission on a Unix socket to connect, so a separate API user cannot connect at all.
- **Scenario:** if the two run under the same uid, the API can read `/proc/<mod pid>/environ`. That file holds `MOD_KEYSTORE_KEY` and `MOD_SIGNING_SECRET`, and Yama's ptrace scope does not block reading it. The process separation would be lost.
- **Fix:** keep separate users. Create the socket as 0660 with a dedicated group that only the API user is in, inside a directory owned by moderation (for example `/run/x2f-mod`, mode 0750). Add a `NEEDS_PLAN6_*` tripwire, and correct the comment and `docs/coordination.md:720`.

### I-4 (Important, T16 against owner G3 and owner-page3): the invite page hides the passkey for moderators and lets them finish without one
- `apps/staff-web/src/screens/Invite.tsx:35-38`: `canFinish` accepts PGP plus a key, or two PGP keys, for mod and senior.
- `Invite.tsx:204-208`: the copy says moderators log in "with a hardware security key and a PGP key", and the Passkey row is shown only when `!moderator`.
- Owner G3 says moderators hold all three: security key, PGP key and passkey. owner-page3 (2213ae8a) enforces this at invite finish with `all-three-methods-required` and refuses two PGP keys as a pair for mod and senior.
- **Scenario after both merge:** a moderator invitee has no way to add a passkey and can never finish. The text conflict in `errors.ts` is trivial, but this semantic conflict is not.
- **Fix:** show the Passkey row for every role. Make `canFinish` require keys, passkeys and PGP all at least 1 for mod and senior. Add `all-three-methods-required`, `passkey-is-security-key` and `both-owner-keys-required` to `apps/staff-web/src/refusals.ts`. Reword the moderator line to match G3 (COPY-UNSIGNED).

### M-1 (Minor): invite `resume` before login, and the bearer flow
`apps/api/src/staff/invites.ts:163-182`.
- **Who can fetch it:** only someone holding the 32-byte token (`TOKEN` regex plus a hash lookup). Enumeration is not possible. A replay stops once the invite is used, cancelled or past its 24 h expiry.
- **What it exposes:** factor counts and the first key's check code, both derived from public keys. That is low sensitivity.
- **Pre-existing gap it widens (Task 7 on main):** every post-`account` step takes the token alone, with no tie to the browser that made the account. Anyone the link reaches can add their own key or PGP to a half-made account, and the resuming page now counts those as the invitee's own progress.
- **Fix (optional):** at `/account`, store the device hash on the invite, and require the same `__Host-x2f_dev` cookie for `resume` and every later step.

### M-2 (Minor): log completeness for messages
`staffRoutes.ts:453` writes `chat.message-sent` with detail `{}` before sealing. If moderation or storage then fails, the log says a message was sent when none was, and the entry never carries the envelope id (design section 4 lists it). Suggested fix: log `chat.message-requested` first, then `chat.message-sent {envelopeId}` in the transaction that stores it.

### M-3 (Minor): the owner setup code is a global budget and lives in stderr
- `ownerSetup.ts:145-158`: 10 tries an hour, globally. Anyone who can reach the staff origin can spend them and stall the owner's setup.
- The code is re-printed at every restart until setup finishes (`staff/main.ts`), so anyone who can read the journal or container logs in that window can take the owner role.
- Mitigation exists: `X2F_STAFF_HOST` defaults to 127.0.0.1. Plan 6 should say: keep the staff origin unreachable from outside until setup is locked, and keep stderr out of shipped logs.

## Confirmed safe
- **Who can take or work a case** (`staffRoutes.ts:117-121,203-220`; `packages/staff/src/dispute.ts:407-417`):
  - `take` only ever assigns the caller.
  - A moderator cannot take a case someone already holds (`wrong-state`). A senior or the owner can, and it is logged as `dispute.assigned`.
  - Messages, proof-request, proof and freeze each re-check `mayWork` under the dispute row lock. An unassigned moderator gets 403 `forbidden-case`, and round-1 people are refused in an appeal (R37).
  - There is no route for reassigning a case to someone else.
- **Freeze:** owner 2026-11-02 rules are applied: no-reply only after 48 h plus maintenance time, ignored-ruling only for a seller past the comply time, no freeze while the timers are paused (g62), no end time, lifted only by someone allowed to work the case. Freeze and lift are logged with `{accountId, side, reason}`.
- **Reader role** (migration 208): `x2f_mod_reader` is nologin and can select only `activity_log(id, at, action, trade_code)`, `disputes(code, seq, status)` and `chats(code, trade_code)`. It has nothing on `chat_envelopes` and no writes.
- **Internal socket:** Unix socket only. `separation-check` forbids TCP `port`, `host` and `listen(<n>)` in that file. HMAC covers domain, method, path, the exact body and the time, with 30 s skew, compared in constant time on a fixed-length hex value. Each log entry is single-use (`used_log_entries` primary key). Error answers carry a code only. The socket starts after `startModeration` has taken the instance lock, and a lost lock closes it before exit. A stale socket file is removed only after the lock is held.
- **`moderator-joined`:** sent only by the staff API, on the first message per moderator name, after the message is stored. Nobody is told on case open.
- **Log entries:** `case.opened`, `dispute.assigned {staffId, tradeOpenedAt}`, `proof.unblurred-requested {side}`, `account.frozen` and `account.freeze-lifted` hold no secrets and no text.
- **Trader dispute view** (`disputes/routes.ts`): `proofRequest` appears only for the side it names. `incidentId` is shown to both (G37), and nothing of the other party is added.
- **Staff-web:**
  - CSP is `STAFF_CSP`: `default-src 'none'`, script, connect, style and font from `'self'` only, no `wasm-unsafe-eval`, `frame-ancestors 'none'`, `base-uri 'none'`. The source has no inline styles or scripts, nothing is inlined in the build, and no source maps ship. Pages also send `no-referrer`, COOP same-origin and HSTS.
  - Separate origin, with `__Host-` cookies (host-only, SameSite Strict) and same-origin fetch.
  - `serveStaffWeb` sends an unknown `/staff` path to the API's 404, refuses dot-segments, and traversal is refused (probe above).
- **Owner setup:**
  - The code has about 60 bits. Only its hash and salt are stored, and it is derived under the server key's HKDF subkey.
  - Each try is committed under the row lock before the code is compared.
  - Attested security keys only. Finish needs two keys and PGP (A9, `ownerReady`).
  - One transaction enables the owner, sets `locked_at` (made permanent by a trigger, truncate covered), spends the setup session and logs last. Parallel finishes lock exactly once (tested).
- **KNOWN_A9** (`apps/staff-web/e2e/shell.spec.ts:136-158`): an exact allowlist of three board-copy lines, used only for the OwnerSetup parity check. Any other difference fails. The server still enforces PGP, tested at `ownerSetup.test.ts:198`.
- **Copy-lint over staff-web:** the refusal home is limited to `apps/staff-web/src/refusals.ts`, and its tests are in `apps/web/test/copy-lint.test.ts`.

### I-3: fixed. Can a wrong deploy still expose the socket?
- **World access: no.** `startInternalServer` uses `lstat` on the parent directory and refuses the start unless all of these hold:
  - it is a real directory (a symlink is refused);
  - it is owned by `process.getuid()`;
  - `(mode & 0o027) === 0`, meaning no group write and no other access (0750 and 0700 pass; 0770, 0755 and 0751 are refused, as is /tmp).
- How the socket is created:
  - it is made under umask 0177, so it is 0600 while listening;
  - then `chown(-1, gid)`, then `chmod 0660`, in that order, so it is never open to a group other than the named one;
  - any failure closes the server and throws.
- The gid must be a positive safe integer. The env value must match `^[1-9][0-9]{0,9}$`, so 0, negatives and names are refused. All of this is tested.
- **Group access: only the named gid can connect, and the code cannot check who is in that group.**
  - If `MOD_INTERNAL_SOCKET_GID` names a broad group (such as `users`), every member of it can reach the socket. They still need the HMAC secret and a fresh log entry, so they gain little.
  - "Readable" does not matter for a Unix socket. Connecting needs write permission, and only the owner and that group have it.
  - A non-root moderation user can only `chown` to a group it is in. If moderation's user is not in the group, the start fails with EPERM. That fails closed.
- **R-2 (Minor, doc precision):** coordination.md says "a dedicated group whose only member is the API's user". Moderation must also hold the group, so that its `chown` works and so that a systemd `RuntimeDirectory=` directory gets that group.
  - Suggested wording: "the API's user as its only supplementary member, and moderation's unit `Group=x2f-modsock`".
  - I checked that this does not expose anything else: moderation writes no files, and its only `umask` is the socket's.
  - If the directory is 0700, the API cannot get in and connect fails. That also fails closed.
- **R-3 (note for Plan 6):**
  - The code cannot detect a deploy that runs the API and moderation as the same user. That is the actual `/proc/<pid>/environ` risk.
  - Only the immediate parent directory is checked, not its ancestors. Under /run this is fine.
  - The original fix asked for a `NEEDS_PLAN6_*` tripwire. None was added, and the repo has no Plan 6 tripwire convention yet. The bold DEPLOY REQUIREMENT in coordination.md stands in for it.
  - A cheap later guard: `socketModerationClient` could refuse a socket whose `st.uid === process.getuid()`.
  - None of this blocks the merge.
